# 本体抽取 Skill

> ⚠️ **FDE 必读说明（本文件是三件套的第一件，必须先读）**
>
> 本文件定义了"什么是对的、什么是错的"判断标准。
> 如果你跳过本文件直接填模板，会产生格式正确但内容错误的 SKILL.md——
> 这比空文件更危险，因为它看起来完成了，但 Agent 推理时会系统性走偏。
>
> **三件套必读顺序**：
> 1. **本文件**（`本体抽取-Skill.md`）— 方法论和判断标准 ← 你在这里
> 2. **`示例项目/SKILL-模板.md`** — 结构骨架和填写说明
> 3. **`示例项目/运营商数据安全-agent/SKILL.md`** — 完整真实示例，对照检查

> 这是一个**元 Skill（meta-level Skill）**：它的本体域不是某个业务领域，
> 而是"本体建模方法论"本身。
> FDE 拿来用，不需要自己构建——它的质量判定标准来自 KSTAR 方法论原文。

## 1. 技能定位

把"领域专家脑子里的知识"转化为"机器可执行的结构"。

三类输入 → 三类输出：

| 输入文档类型 | 主要产出 |
|------------|---------|
| 规程 / 标准 / 手册 | T-Box 概念体系 + R-Box 规则 |
| 专家访谈记录 | R-Box 因果规则（含 REASON） |
| 历史事故 / 案例记录 | A-Box 历史实例 |

**关键约束**：R-Box 规则的 REASON 必须经过领域专家逐条确认，
模型生成的内容只是草稿，未经确认不得视为有效规则。

---

## 2. 触发条件

**适用（以下任一触发词出现时启动）：**
- "帮我从这份文档里抽 T-Box"
- "这些规程里有哪些因果规则"
- "帮我建 R-Box，要带原因"
- "从访谈记录里提炼业务规则"
- "这个案例能进 A-Box 吗"

**不适用（先暂停，问清楚再决定是否抽取）：**
- 用户只需要摘要 / 翻译 / 改写文档，不是建本体
- 输入是成熟度框架（CMMI / ISO 27001 / 等保）但场景需要字段级实时判断 → 先要操作规程
- 输入是产品架构图但 Agent 的场景边界不清楚 → 先确认哪些功能在范围内
- 任务是审批发布 / 声明业务价值 / 认证合规达标
- 提供的案例是假设情境，用户希望用它验证规则有效性 → 假设案例不进 A-Box

## 3. 本体引用（本 Skill 自身的知识骨架）

### T-Box · 本体建模概念域

```
本体建模的核心对象：

DomainDocument（领域文档）
  ├── 规程类（Regulation）：国家法规 / 行业标准 / 企业制度
  ├── 经验类（Expert）：访谈记录 / 老师傅经验 / 会议纪要
  └── 案例类（Case）：事故报告 / 处理记录 / 复盘总结

ConceptCandidate（概念候选）
  └── 从文档中识别出的名词 / 对象 / 角色

Entity（通过筛选的实体）           ← 概念候选通过 4 项检查后升格
  属性：entity_id, name, attributes[], relationships[]

RuleCandidate（规则候选）
  └── 从文档中识别出的 IF-THEN 逻辑

ValidatedRule（有效规则）           ← 规则候选经专家确认 REASON 后升格
  属性：rule_id, condition, conclusion, reason, source_doc, expert_confirmed

CaseInstance（历史实例）
  属性：instance_id, timestamp, context, applied_rules[], outcome, delta_r
```

### R-Box · 抽取判定规则（★ 本 Skill 的灵魂）

这些规则来源于 KSTAR 方法论原文（Kstar-V2.4-cn.docx）和
两个真实构建案例（客服补救 + 收入归因）的经验复盘。

```markdown
## T-Box 判定规则

IF 候选概念 无法被长期追踪（没有生命周期）
THEN 不是实体，降级为属性或过程节点
REASON 实体必须能跨时间积累 A-Box 实例；
       无生命周期 = 无法记录历史 = 无法产生 δR 学习信号

IF 候选概念 是一个动作或操作行为
THEN 不是实体，归入执行策略（Execution Procedure）
REASON 动作属于"怎么做"，是执行层；
       实体属于"有什么"，是知识层；混淆导致 Skill 执行逻辑污染本体

IF 候选概念 没有任何属性可以描述它
THEN 不是有效实体，可能只是一个标签
REASON 无属性 = 无法做条件判断 = R-Box 规则无法引用它

IF 候选概念 在其他场景中完全无法复用
THEN 谨慎纳入，标注为"场景专属实体"
REASON 跨场景可复用性是本体的核心价值；
       过度场景特化会让本体碎片化、难以维护

IF T-Box 实体通过 4 项检查、初步确认列表完整
THEN 对每个实体标注层级：T1（主推理链必经）或 T2（容器/后果/二级路径）
REASON T1/T2 分层决定可视化展示优先级和 SKILL.md 执行路径顺序；
       不分层会导致核心实体与支撑实体在 Agent 推理时优先级混乱，R-Box 规则也难以聚焦

IF 同一组织准备构建 3 个以上 Agent
AND 多个 Agent 共享 5 个以上相同基础概念（如 Employee / System / Department）
THEN 建议提取 T3 层（跨 Agent 共享本体），单独定义后供各 Agent 引用
REASON 没有 T3 时每个 Agent 各自定义相同概念，属性列表容易不一致，导致跨 Agent 数据
       无法对齐；T3 是复用原则的工程化实现，试点阶段不强制但要预留扩展空间

IF SOP 文本 / 手册 中描述了"需手动检查" / "依赖操作者确认" / "人工核对清单"等步骤
AND 历史案例显示该步骤存在系统性遗漏（同类遗漏 ≥ 2 个案例，或失误率 ≥ 20%）
THEN 将该隐性机制实体化——从文本描述升格为独立 T-Box 实体，归入 T1
     实体化要求：赋予状态属性（pending / resolved）+ 截止时间 + 绑定到主实体
REASON 隐性机制（写在SOP里的检查步骤）依赖操作者工作记忆，在阶段切换时必然存在遗漏率；
       实体化后每项有生命周期可追踪，门控由系统执行而非依赖记忆；
       判断触发点：历史数据证明隐性机制已失效（可量化）= 实体化条件成立；
       典型案例：招聘SOP中"S3→S4遗留项检查"步骤 → 4/5人案例信息断层 → 升格为StagePendingItem实体（T1）

## R-Box 判定规则

IF 输入文档格式 = 图片 / 截图（PNG / JPG / 微信截图）
THEN 使用 Companion Agent 视觉能力读取，读完后向用户复述关键内容确认无误后再抽取
REASON 图片无法文本提取；视觉读取存在 OCR 误差，关键字段名和数字必须用户确认，
       否则规则数据源头有误，后续所有 R-Box 规则可信度归零

IF 输入文档格式 = PDF / Word
AND 文档为扫描件（无文字层）
THEN 同图片处理流程
REASON 扫描件外观是 PDF 但实质是图片，文字提取返回空值会被误判为"空文档"

IF 输入文档是成熟度/合规评估框架（DSMM / CMMI / ISO 27001 / 等保 等）
AND 场景类型是运营查询（字段级分类 / 实时判断 / 操作决策）
THEN 暂停抽取，向用户提示"文档层级与场景层级不匹配"，说明缺少哪类文档
REASON 成熟度框架描述"组织应该做什么流程和岗位"，无法生成字段级判定规则；
       强行抽取只能产生合规管理规则，KSTAR 验证时 δR 极大，等于浪费一轮抽取

IF 输入文档是产品架构图 / 功能模块图
AND 尚未确认场景边界（哪些功能在本 Agent 使用范围内）
THEN 暂停抽取，先追问场景边界再开始
REASON 架构图展示全量功能，无法判断单个 Agent 的服务范围；
       不追问会导致 T-Box 过宽，R-Box 规则无法聚焦

IF 规则候选 没有 REASON 字段
THEN 不是有效 R-Box 规则，只是业务列表
REASON REASON 是 δR 归因的依据；
       没有 REASON = 规则答错了不知道为什么 = 无法迭代

IF 规则的 REASON 只由模型生成、未经专家确认
THEN 标注为"待验证"，不得用于 Agent 决策
REASON 模型可以猜出合理的 REASON，但合理 ≠ 正确；
       用未经验证的规则驱动 Agent 会产生不可信赖的输出

IF 规则候选 描述的是"应该怎么做"而非"为什么这样做"
THEN 这是执行步骤，不是 R-Box 规则，归入执行策略
REASON R-Box 管因果逻辑；执行步骤管操作顺序；两者混用导致 Skill 失去可解释性

IF 多条规则同时满足触发条件
THEN 按优先级顺序执行：硬约束（门控规则）> 加速规则（优化流程）> 评估规则（参考建议）
     相同优先级内，专家已确认（✅）的规则权重高于待验证（⏳）的规则
REASON 无优先级的规则集合在多条规则同时触发时会产生不可预测的 Agent 行为；
       硬约束一旦被绕过，会产生不可回收的成本（如张女士薪资门控案例：跳过门控的代价
       在下游才暴露，补救成本远高于入口把关）

IF 当前场景没有可用的领域专家来确认 R-Box
AND 场景是自建自用（FDE 自己就是领域专家）
THEN 自用场景下，FDE 本人可以承担专家确认角色，但必须：
     a) 在每条规则的"确认状态"中明确写"自确认"而非"✅专家已确认"
     b) 在 cases.json 的首批3条案例运行完后，根据δR重新检查每条自确认规则
REASON 赋能包设计了专家确认流程，但试点阶段 FDE 即领域专家的情况普遍；
       区分"自确认"和"专家确认"保留了可溯源性，后续引入外部专家时可快速识别哪些规则需要再确认

## A-Box 判定规则

IF 案例是假设情境（"如果发生X，可能会…"）
THEN 不进 A-Box
REASON A-Box 必须经验可追溯；
       假设案例无法验证规则，也无法产生真实 δR

IF 案例缺少结果记录（只有经过、没有结果评估）
THEN 进入 A-Box 但标注为"不完整"，不参与规则验证
REASON 完整案例 = 触发条件 + 处理过程 + 结果评估 + 规则复盘；
       不完整的案例无法驱动 δR 归因

IF A-Box 中的实例是某对象的全量状态快照（记录对象所有信息）
THEN 不是合法的 A-Box 实例，应重构为以"决策事件"为中心
示例（❌ 错误）：{ "name": "候选人A", "经验": "7年", "技能": "Python", "状态": "进行中" }
示例（✅ 正确）：{ "instance_id": "CASE-001", "title": "候选人A S3推进决策", "context": "...", "applied_rules": ["R-04"], "outcome": "...", "delta_r": {...} }
REASON A-Box 的价值在于记录"规则如何在真实情境中触发和产生结果"；
       状态快照只是数据库，无法驱动规则验证；
       判断标准：这条记录能否被拿来验证一条 R-Box 规则是否判断正确？能=合法；不能=重构

IF A-Box 的 delta_r 字段只有"实际结果"而没有"执行前预测"
THEN 这是事后归纳，不是真正的 δR，标注 delta_r.prediction 为空
REASON 真实 δR = 执行前预期 vs 实际结果的偏差；
       如果预测是在结果已知后填写，会因为 hindsight bias 导致偏差被低估；
       正确做法：执行 Skill 前先写下预测，执行后再填实际结果

IF A-Box 实例的 completeness 字段需要填写
THEN 使用以下语义（不可混用）：
     complete   = 真实世界事件已发生 AND delta_r 中 prediction / actual / learning 均已填写
     incomplete = 事件已预测或已启动，但结果尚未确认，OR delta_r 复盘尚未完成
     注意：incomplete ≠ 案例不重要；incomplete = 这条记录还不能用来验证规则
REASON completeness 语义不清会导致验证集混入"进行中"的案例；
       用未复盘的数据验证规则，δR 偏差估计系统性偏低（最有意思的失败尚未发生就被算进去了）；
       判断是否 complete 的最简测试：拿这条记录，能否得出"规则判断是否正确"的明确结论？能 = complete
```

## 4. 执行流程（三轮抽取 + 可视化确认 + 专家签字）

```
输入：一份或多份领域文档
  ↓
轮次 1 · T-Box 抽取
  提示词模板 → Companion Agent 识别名词/对象 → 对每个候选过 4 项检查 → 输出实体树
  ↓
★ T1/T2 实体分层（可视化前完成）
  对通过 4 项检查的实体做层级标注：
  - T1 核心本体：回答主问题时必然经过的实体（主推理链）
  - T2 领域本体：容器 / 后果 / 仅在二级场景出现的实体
  - T3 共享本体（可选）：多 Agent 场景下跨场景复用的基础概念
  注意：层级相对于当前 Agent 主任务；同一实体在不同 Agent 里 tier 可不同，但属性定义保持一致
  ↓
★ 新实体强制确认（有任何 T1 实体时不可跳过）
  对每个标注为 T1 的实体，逐项完成后再进入可视化：
  □ 实体名 + 英文名（确认无误）
  □ T1 升级理由：移除后推理链是否断裂？（推理链断裂 = T1；只是少了记录 = T2）
  □ 实证依据：有哪些真实案例 / 历史数据 / 失误统计支持这个判断？（无实证 = 降级为 T2 候选）
  □ 专家签off：[ ] 领域专家已确认  [ ] 自确认（FDE即领域专家，后续引入外部专家时需复查）
  未完成此确认的 T1 实体，状态标注为"T1候选"，不得作为 R-Box 硬约束规则的触发条件
  ↓
★ T-Box 可视化
  Companion Agent 自动生成 HTML 关系图并打开浏览器
  专家在图上直观确认：实体数量是否完整 / 关系方向是否正确 / 有无明显遗漏
  （比看文字列表快 3 倍，关系错误一眼可见）
  ↓
轮次 2 · R-Box 抽取
  提示词模板 → Companion Agent 识别 IF-THEN 逻辑 → 强制要求 REASON → 输出规则草稿
  ↓
轮次 3 · A-Box 收集
  提示词模板 → 识别文档中的真实案例 → 按格式整理 → 标注完整/不完整
  ↓
专家确认轮（不可跳过）
  逐条过 R-Box 规则 → 专家确认每条 REASON → 未确认的标注"待验证"
  ↓
输出：
  references/ontology_tbox.md   ← T-Box 定稿
  references/rbox_rules.md      ← R-Box（含确认状态）
  data/cases.json               ← A-Box 实例
```

## 5. 输出格式

### T-Box / A-Box 可视化输出（本体可视化-[场景名].html）★

HTML 文件含**两个标签页**，用 vis-network 绘制，生成后自动在浏览器打开，专家确认后归档至 Agent 目录。

**文件命名**：`本体可视化-[场景名].html`（示例：`本体可视化-运营商数据安全.html`）

#### 标签页一：T-Box 本体视图

- **节点**：填色椭圆 + 白色文字；T1 核心实体 = 蓝色实心（带阴影），T2 领域实体 = 青绿色实心（带阴影）
- **连线**：有向箭头 + 关系标签（包含 / 属于 / 具有 / 触发…）
- **右侧边栏**：实体卡片列表（总览），点击卡片可高亮对应节点
- **节点 popup**：点击任意节点弹出浮层，显示该实体的属性定义 + 属性类型 + 关系列表（不是侧边栏）
- **交互**：节点可拖拽，图可缩放（barnesHut 物理引擎布局）

#### 标签页二：A-Box 案例视图

- **顶部标签**：按案例 ID（CASE-DS-001 / 002…）切换，每个案例独立面板
- **左侧案例详情**：
  - 触发情境描述
  - 涉及实体 chip 标注（每个实体一个彩色徽标）
  - Agent 回答摘要
  - δR 记录面板：深色背景 + 金色 badge 编号 + 偏差描述
  - 学习结论（lesson）
- **右侧实体激活 SVG**：静态关系图，根据当前案例涉及哪些实体动态高亮（激活色），其余节点灰化

### T-Box 输出（ontology_tbox.md）

```markdown
# T-Box · [场景名]本体

## [实体名]（[英文名]）
- 定义：[一句话]
- 关键属性：[attr1], [attr2], [attr3]
- 关系：[与哪个实体关联，关联方式]
- 来源文档：[哪份规程第几章]

（每个实体一节，4项检查通过后才写入）
```

### R-Box 输出（rbox_rules.md）

```markdown
# R-Box · [场景名]规则库

## [规则类别]

IF [条件，引用 T-Box 实体属性]
AND [条件2]（可选）
THEN [结论]
REASON [为什么——后果 + 因果逻辑]
来源：[文档名/访谈日期]
确认状态：✅ 专家已确认 / ⏳ 待确认
专家确认问题（可选）：[向专家提问的具体问题]
question_type：threshold（阈值合理性）/ dual_confirm（双人确认场景适用性）/ trigger_condition（触发条件完整性）
```

> `question_type` 说明（P2可选字段）：标注专家确认的问题类型，帮助 FDE 在专家有限时间内优先确认关键类型：
> - `threshold`：规则中有数字边界（如"≥8个月"）需专家确认阈值合理性
> - `dual_confirm`：规则要求多人确认，需专家说明适用场景（如"备选"情形）
> - `trigger_condition`：触发条件是否覆盖完整（有无遗漏的边界情况）

### A-Box 输出（cases.json 单条格式）

```json
{
  "instance_id": "CASE-001",
  "timestamp": "YYYY-MM-DD",
  "context": "触发条件描述",
  "applied_rules": ["R001", "R002"],
  "outcome": "实际结果",
  "involved_entities": {
    "实体名1": "激活的属性值或状态描述（例：status=pending）",
    "实体名2": "激活的属性值或状态描述"
  },
  "delta_r": {
    "prediction": "执行前预期结果（执行前填写）",
    "actual": "实际发生了什么",
    "learning": "这次学到什么"
  },
  "completeness": "complete / incomplete",
  "source": "来源文档或访谈"
}
```

> `involved_entities` 说明：记录本案例激活了哪些 T-Box 实体实例及其关键状态，用于验证本体覆盖度——如果一个 T1 实体在所有案例中都没有出现，说明本体可能过宽或该实体命名偏离实际。

## 6. KSTAR 闭环说明

```
本 Skill 的 δR 归因：

  文档 → 抽取 → 草稿（Situation + Action）
    → 专家确认（Result）
      → δR = 专家修正的条目数 / 总条目数
        → δR 高 = 模型理解偏差大 = 需要在提示词里补充领域背景
        → δR 低 = 抽取质量稳定 = 可以加快节奏
```

δR 归因三问：
1. T-Box 实体判断错？→ 检查提示词里的 4 项检查是否传达清楚
2. R-Box 规则缺 REASON？→ 在提示词里强调"必须追问为什么"
3. A-Box 混入假设案例？→ 在提示词里要求"必须引用原文时间和来源"

## 8. 完工标准（5-Gate）

不得将本体标注为"完成"，除非以下5个门全部通过：

**Gate 1 · 输入**
- [ ] 有场景名 + 核心主问题 + Agent 范围界定（在范围 / 不在范围）
- [ ] 来源文档已列出（规程类 ≥1份，案例类 ≥1份）

**Gate 2 · T-Box**
- [ ] 每个实体通过4项检查（可追踪 / 有属性 / 有关系 / 非动作）
- [ ] 每个实体标注 T1 / T2 层级，关系带方向箭头
- [ ] 每个 T1 实体有：升级理由 + 实证依据 + 确认状态（专家确认 / 自确认）
- [ ] 未确认的 T1 标为"T1候选"，不触发硬约束规则

**Gate 3 · R-Box**
- [ ] 每条规则有 IF / THEN / REASON / 来源 / 确认状态（5项）
- [ ] 硬约束规则的 REASON 已确认（不可处于 pending 状态）
- [ ] 有「规则优先级与冲突仲裁」一节

**Gate 4 · A-Box**
- [ ] 每条是真实决策事件（不是快照 / 不是假设情境）
- [ ] 每条有 `delta_r.prediction`（执行前预写）+ `involved_entities`
- [ ] `completeness` 字段正确（complete = 事件已发生 + δR 已复盘）
- [ ] 至少 3 个 complete 案例

**Gate 5 · KSTAR**
- [ ] prediction 先于执行填写，不是事后归纳
- [ ] δR 归因已完成（归因三问至少覆盖1问）
- [ ] 执行流程无歧义（给定输入能推导出输出）

> 最高自动晋升状态 = 草稿候选（staged candidate），发布到生产使用需要人工审核。

## 9. 常见失败模式速查

| 失败模式 | 症状 | 处置 |
|---------|------|------|
| **动作被当作实体** | T-Box 里有"提交申请"、"确认处理"等动词词组 | 移入执行策略；检查被该动作影响的对象是否才是实体 |
| **T1 过多** | T1 实体从未出现在 A-Box 案例里 | 做移除测试；未出现的 T1 降为 T2 候选 |
| **隐性机制被遗漏** | SOP 有人工确认步骤，历史案例中该步骤屡屡被跳过 | 有实证（≥2案例 / 失误率≥20%）即实体化；见 T-Box"隐性机制"Pattern |
| **REASON 泛化** | REASON 写"因为很重要"/"规程要求"等 | 追问：不遵守会发生什么具体后果？标 ⏳ 等专家确认 |
| **A-Box 混入快照** | 案例记录的是对象的全量属性而非决策事件 | 重构为：什么情境 → 触发了哪条规则 → 结果如何 |
| **事后归纳 δR** | prediction 是结果已知后补填 | prediction 留空；不计入真实 δR；下轮提前写预测 |
| **文档层级不匹配** | 用 CMMI / ISO 控制项直接做字段级实时规则 | 暂停；要求提供操作规程 / 字段定义 / 真实案例 |

---

> 使用前确认：
> - [ ] 已准备好领域文档（至少 1 份规程 + 1 份案例记录）
> - [ ] 已联系到可以确认 R-Box 的领域专家（或确认 FDE 自确认角色）
> - [ ] 完成抽取后，过完工标准 5-Gate 才算本体定稿

## Skill Gate 契约

- `use_when`：用户提供规程/标准/手册/专家访谈记录/历史事故案例，要求抽取 T-Box 概念体系、R-Box 因果规则（含 REASON）或 A-Box 历史实例；触发词如“帮我从这份文档里抽 T-Box”“这些规程里有哪些因果规则”“帮我建 R-Box”。
- `do_not_use_when`：用户只需要摘要/翻译/改写文档而非建本体；输入是成熟度框架但场景需要字段级实时判断（先要操作规程）；产品架构图但场景边界不清；任务是审批发布/声明业务价值/认证合规达标；假设案例用于验证规则有效性（不进 A-Box）；R-Box 规则 REASON 未经领域专家逐条确认不得视为有效。
- `positive_examples`：`帮我从这份安全规程里抽 T-Box，并建 R-Box 因果规则。`；`从这三份事故报告里提炼 A-Box 历史实例。`
- `negative_examples`：`把这份文档翻译成英文。`；`基于假设案例直接建 A-Box，不用专家确认 REASON。`
