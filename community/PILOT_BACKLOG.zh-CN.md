# 社区贡献最小试点：Issue 草案

本文件是供新贡献者选择的十个推荐 Issue 草案，不是 Skill 准入白名单，也不限制
开发者自主选题和直接提交 PR。草案本身不代表任务已经开放认领；试点负责人应逐条
确认导师、验收标准和四周内的评审容量，再创建对应 Issue。所有任务以 `develop`
为目标分支，并遵守 DCO 和 noreply 邮箱要求。

## 社区 Skill 候选

以下五项都限定为声明式、纯文本候选，不联网、不执行脚本、不写入外部系统。

### CS-01 作业评分标准检查器

- 建议 id：`assignment-rubric-checker`
- 用户场景：学生提供作业草稿和明确评分标准，希望知道逐项缺口。
- 预期输出：评分项、草稿证据、满足状态、改进建议、缺失信息。
- 必须拒绝：未提供评分标准仍主观打分；代写完整作业；编造草稿证据。
- 验收：至少覆盖“材料齐全”和“要求代写”两个评测案例。

### CS-02 文献综述提纲审查器

- 建议 id：`literature-review-outline-reviewer`
- 用户场景：用户提供文献笔记和提纲，希望检查主题覆盖、论证顺序和证据缺口。
- 预期输出：主题映射、已有来源、未覆盖问题、提纲调整建议。
- 必须拒绝：自行联网找文献；虚构引用；把未提供的结论写成来源事实。
- 验收：输出中的每项结论都能定位到用户材料，或明确标为待补证据。

### CS-03 演讲文字稿反馈器

- 建议 id：`presentation-script-reviewer`
- 用户场景：用户提供演讲文字稿、受众和预计时长，希望获得结构与表达反馈。
- 预期输出：核心信息、结构问题、可能超时段落、修改优先级。
- 必须拒绝：没有文字稿时声称分析过音视频；替用户捏造事实或数据。
- 验收：至少覆盖“完整文字稿”和“只提供主题、没有稿件”两个案例。

### CS-04 学习计划风险审查器

- 建议 id：`study-plan-risk-reviewer`
- 用户场景：用户提供目标、可用时间、截止日期和当前计划，希望发现不可执行之处。
- 预期输出：约束、负荷冲突、风险、调整方案和需要用户决定的问题。
- 必须拒绝：保证考试结果；提供医疗诊断；在缺少时间约束时伪造精确排期。
- 验收：能将事实、推断和建议分开，并在关键信息缺失时返回澄清问题。

### CS-05 实验报告完整性检查器

- 建议 id：`experiment-report-checker`
- 用户场景：用户提供实验要求、观测数据和报告草稿，希望检查结构与证据链。
- 预期输出：要求覆盖表、数据与结论对应关系、缺失部分、修改建议。
- 必须拒绝：伪造实验数据；替代安全审批；把未观测结果写成事实。
- 验收：覆盖一个完整输入案例和一个“缺少原始数据”的停止案例。

## L0 新手任务

这些任务只改善贡献路径，不修改产品运行行为。

### L0-01 为校验错误补充中英文行动建议

- 路径：`scripts/check-community-skills.mjs` 及其测试。
- 结果：常见失败同时指出应修改的文件和具体动作；不改变当前拒绝规则。
- 验收：为新增提示补测试，运行目标测试和 `npm run community:skills:check`。

### L0-02 补充来源声明校验回归用例

- 路径：`test/scripts/check-community-skills.test.ts`。
- 结果：覆盖重复 eval id、非 HTTPS 第三方来源和缺失许可证三种失败。
- 验收：每种失败都断言明确错误信息，不使用跳过测试。

### L0-03 编写首次贡献常见问题

- 路径：`community/skills/` 下的中英文指南。
- 范围：Fork、目标分支、noreply 邮箱、`git commit -s`、CI 失败后的修正方式。
- 验收：中英文含义一致，命令与根贡献指南不冲突，通过 README 链接检查。

### L0-04 记录 Windows 干净环境演练

- 路径：社区 Skill 指南或其 `references/` 文档。
- 范围：从新 Fork 到校验通过；只能记录真实执行过的命令和结果。
- 验收：标明 Windows 版本、Node/npm 版本、失败与恢复步骤；不得包含真实用户名路径。

### L0-05 记录 macOS 干净环境演练

- 路径：社区 Skill 指南或其 `references/` 文档。
- 范围：从新 Fork 到校验通过；只能记录真实执行过的命令和结果。
- 验收：标明 macOS、Node/npm 版本、失败与恢复步骤；不得包含真实用户名路径。

## 将草案创建为推荐 Issue 前必须补充

每个正式 Issue 还需要负责人填写：导师 GitHub 用户名、预计工作量、认领截止日期、
允许修改的精确路径，以及首次响应的值班安排。缺少导师或评审容量时，不应创建该
Issue，也不应在宣传文章中把该草案标为可认领。这不影响开发者按照社区指南自主
设计并直接提交其他 Skill。
