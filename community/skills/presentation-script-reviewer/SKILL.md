# 演讲文字稿反馈器

对已成文的演讲稿做提交前的自查：核对核心信息是否清晰、结构是否完整、表达是否匹配受众，并按稿件长度与目标时长标记可能超时的段落，最后给出有优先级的修改建议。本 Skill 只处理用户明确提供的文字内容。

use_when:
- 用户提供了完整的演讲文字稿、目标受众与预计时长，希望在正式演讲前获得结构、表达与时长方面的反馈；
- 用户希望把一段口播稿压进指定时长，需要知道哪些段落可能超时、大致要压缩多少字；
- 用户提供了文字稿，询问核心信息是否清晰、开场结尾是否完整。

do_not_use_when:
- 用户只给出主题、大纲或想法，尚未提供文字稿——此时停止并索取文字稿，不得基于主题虚构分析，也不得声称分析过音频或视频；
- 用户只提供音频或视频文件而没有文字稿——停止，请用户先转写成文字；
- 用户要求代写演讲稿，或要求补充事实、数据、经历、来源——拒绝编造，只对已有稿件给出修改建议；
- 用户要求评估台风、声音、表情、现场互动等无法从文本观测的要素——说明超出文本审查范围；
- 用户要求联网查找资料、执行脚本或写入外部系统——拒绝。

## 输入

必需输入（任一缺失即停止，在输出中列出缺失项并追问，不得自行假设或补造）：

1. 演讲文字稿：用户明确提供的成文稿件；
2. 目标受众：影响措辞正式度与术语深度的判断；
3. 预计时长：以分钟计的口播目标时长。

可选输入（缺失时按通用正式场合处理，并写入输出的待确认问题中，声明该假设）：

- 演讲目的（说服、汇报、教学、致辞等）；
- 场合（内部评审、公开演讲、答辩、晨会等）；
- 表达风格要求（口语化程度、术语容忍度）；
- 用户自己的语速或"字数/时长"偏好（用于覆盖默认语速假设）。

## 工作流

1. 输入校验：逐项核对三个必需输入，任一缺失即停止，不做部分分析；
2. 逐段拆解：将文字稿按语义段落编号（P1、P2……），标注每段承担的角色（开场、主体、过渡、结尾）；
3. 四维检查，每个维度分别给出结论：
   - 核心信息：一句话能否复述这场演讲想让听众记住什么；核心信息是否在开场出现、是否得到重复强化；
   - 结构：开场是否给出主线、主体分点是否清晰、过渡是否衔接、结尾是否有收束与行动号召；
   - 表达：长句、书面化措辞、术语密度是否与受众匹配；
   - 时长占用：按"时长估算规则"（见 references/duration-estimation.md）逐段估算，标记可能超时的段落；
4. 优先级排序：将全部发现按 P0（必须改：核心信息缺失或结构性超时）/ P1（建议改：结构断层、表达冗余）/ P2（可选：措辞打磨）分组；
5. 按输出结构（见 references/review-output-template.md）组织结果，并在结尾列出缺失信息与需要用户决定的问题。

每条发现必须标注来源类型：稿件事实（稿件中明确写出的内容）、合理推断（由稿件内容推出的判断）、修改建议（建议的改法），三类不得混淆。

## 输出

固定为六段结构，完整模板见 references/review-output-template.md：

1. 总体判断：核心信息复述、清晰度结论、预计时长区间与目标对比、假设声明；
2. 核心信息与清晰度；
3. 结构问题：按段落定位逐条列出，注明属于开场、主体、过渡还是结尾；
4. 可能超时段落表：段落号、字数、估算时长区间、目标占比、判定与压缩提示——时长问题与内容质量问题分开列出，不得混在一条建议里；
5. 按优先级排列的修改建议：P0/P1/P2 分组，每条带段落定位与来源类型标签；
6. 缺失信息与待确认问题：固定结尾，列出尚未提供的输入、已做出的假设、需要用户决定的事项。

每条问题必须给出段落定位（P 编号或首句引用）；无法定位的观察不纳入结果。完整的正向示例（5 分钟技术评审汇报稿）见 examples/tech-review-walkthrough.md。

## 边界

- 只处理用户明确提供的文字内容，不联网、不执行脚本、不写入外部系统；
- 时长一律为区间估算而非精确测量，必须显式声明语速假设，禁止表述为"精确需要 X 分 Y 秒"；
- 不替用户捏造事实、数据、经历或来源；稿件中未经核实的数据只标注"源自稿件、未核实"，不补全也不删除；
- 不分析音频或视频，不评估台风、声音、表情等文本外要素；
- 不代替专业演讲教练或人工审稿，输出仅供参考，不直接覆盖用户的正式稿件。
