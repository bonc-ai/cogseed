# Community Agent Pilot

[简体中文](./README.zh-CN.md)

A community Agent hands a complete task to the AI: a workflow describes what to do in
which order, and the Agent calls the Skills it ships with for individual steps. This
pilot accepts declarative, text-only Agents. The submission format follows the CogSeed
client's Agent package format (`agent-package-v1`).

Users cannot yet install community Agents directly in the CogSeed client, so this pilot
**does not require an installation test**; review is based on format and content quality.
A merged PR only means "repository-reviewed community candidate". It does not mean the
Agent is published to CogSeed Hub or bundled with a release.

## Contribution flow

1. Choose either path:
   - claim a recommended `community agent` Issue; or
   - design your own Agent. No pre-approval or linked Issue is required.
2. Search existing Agents and open PRs to avoid obvious duplicates.
3. Copy `_template/` to `community/agents/<agent-id>/`. Use lowercase ASCII kebab-case for
   `agent-id`.
4. Write `agent.json` and `README.md`. Put any new Skill the Agent needs under
   `skills/<skill-name>/`.
5. Replace every template placeholder and provide at least one positive and one negative
   case in `evals/evals.json`.
6. Record the GitHub author and all third-party material in `provenance.json`.
7. Go through the self-check list at the end of this document.
8. Sign off commits with DCO (`git commit -s`) and open a PR against `main`. If you claimed
   an Issue, add `Closes #<issue number>` to the PR description.

The repository-wide environment, email, and DCO rules still apply; see
[CONTRIBUTING.md](../../CONTRIBUTING.md).

## Required layout

```text
community/agents/<agent-id>/
├── agent.json                  # Agent definition (read by the client)
├── README.md                   # Use cases, example task, expected result (read by the client)
├── skills/                     # Skills shipped with this Agent (read by the client, optional)
│   └── <skill-name>/
│       └── SKILL.md
├── evals/
│   └── evals.json              # Example tasks and acceptance points (for community review)
└── provenance.json             # Authorship and sources (for community review)
```

The client reads only `agent.json`, `README.md`, and `skills/`; `evals/` and
`provenance.json` are for community review. As in the Skill pilot, each package may contain
at most 30 files and 1 MiB in total. Symbolic links, executables, scripts, binaries, real
absolute machine paths, and unreplaced template placeholders are rejected.

## `agent.json` fields

| Field | Required | Notes |
|---|---|---|
| `name` | Yes | Letters, digits, underscores, hyphens, and CJK characters only; no spaces or surrounding whitespace; display width ≤ 60 (CJK counts as 2); reserved names such as "指挥官", "commander", and "cogseed" are not allowed |
| `description_zh` / `description_en` | At least one | Who the Agent is for, what it handles and delivers, and typical user phrasing; ≤ 800 characters. The client uses it to decide when to dispatch to this Agent, so be specific |
| `workflow` | Yes | Markdown workflow. Refer to Skills by name only (for example "call skill study-plan-builder"), never by file or install path |
| `category` | Yes | Category code: one of `education`, `ecommerce`, `rnd`, `creation`, `data`, `office`, `general`. Use `education` for study and teaching scenarios |
| `agent_id` | Required when shipping Skills | Must match the `<agent-id>` directory name; letters, digits, underscores, and hyphens only, up to 64 characters |
| `skill_list` | No | Skills this Agent may use; see the next section. Omit for no restriction; `[]` means no Skills |
| `icon` | No | Icon name, for example `graduation-cap`, `book-open`, `pen`, `calculator`, `users`, `briefcase`, `document`, `chart`, `code`, `target`; `crown` is not allowed |
| `color` | No | One of `gold`, `coral`, `mint`, `lavender`, `peach`, `sky`, `sunshine`, `rose`, `sage`, `periwinkle`, `butter`, `blush`, `cyan`, `violet`, `lime`, `salmon`, `emerald` |
| `knowhow` | No | Core capabilities, one sentence each, 2–5 recommended |
| `standards` | No | Observable delivery standards, one sentence each, 2–5 recommended |
| `inputs` | No | Form fields the user fills in before the run; each has `id` (lowercase letters, digits, underscores, up to 32), `label`, `type` (`text`, `textarea`, `select`, `multiselect`, `number`, `boolean`, `file`, `directory`), and `default` |
| `interactive` | No | Boolean |
| `output_format` | No | One of `auto`, `text`, `dashboard`, `artifact`; use `auto` if unsure |
| `runtime` | No | Only `{"kind": "in_process"}` |

Do not write `version`, `created_at`, or `updated_at`, and do not add connectors, accounts,
keys, or any field not listed above. Versions and publish times are generated by the
platform; unexpected fields are rejected.

## Skill reference rules

Each `skill_list` entry must be one of:

| Form | Meaning | In this pilot |
|---|---|---|
| `<skill-name>` | A Skill shipped with this Agent; must match `skills/<skill-name>/SKILL.md` | Accepted; counts as a Skill contribution |
| `builtin:<name>` | A built-in client capability | Disabled by default in the client and not accepted yet; we will announce when it opens |

This pilot does not accept references to Hub Skills (12-character hexadecimal IDs) or to
community Skills in other directories or PRs. If you need an existing capability, write a
new Skill under this Agent's `skills/`.

## Writing shipped Skills

- Use lowercase ASCII kebab-case for the directory name; it must not be exactly 12
  hexadecimal characters.
- `SKILL.md` must have frontmatter whose `name` matches the directory name and whose
  `description` is at least 20 characters.
- Follow the [community Skill template](../skills/_template/SKILL.md): state `use_when`,
  `do_not_use_when`, inputs, workflow, output, and boundaries.
- Do not write ownership fields such as `ownerAgent`; the platform adds them on import.

## Content boundary

Only declarative, text-only content is accepted: no scripts, network access, external
writes, binaries, or new dependencies. Examples and eval material must not contain real
personal data, customer material, or restricted course material.

## Review and status

Review checks format, user value, the split between workflow and Skills, trigger and
refusal boundaries, example tasks, originality and attribution, privacy, and safety. We aim
to respond within one working day, without promising acceptance or a merge date.

Status stages match the [community Skill pilot](../skills/README.md); this pilot stops at
"community candidate accepted" by default. Once the client supports installing Agents,
merged Agents still need a separate import verification.

This format follows the client's draft Agent package format. If the format changes,
maintainers migrate merged Agents; contributors are not asked to redo their work.

## Self-check list

- [ ] The directory is `community/agents/<agent-id>/` and `agent_id` matches it.
- [ ] `agent.json` is valid JSON with `name`, `workflow`, `category`, and at least one description.
- [ ] `name` has no spaces; `category`, `icon`, and `color` use listed values.
- [ ] No `version`, `created_at`, `updated_at`, or other unlisted fields.
- [ ] Every `skill_list` entry has a matching `skills/<skill-name>/SKILL.md`, and the workflow uses the same Skill names.
- [ ] Each shipped Skill's frontmatter `name` matches its directory name.
- [ ] `README.md` covers use cases, non-goals, an example task, and the expected result.
- [ ] `evals/evals.json` has at least one positive and one negative case.
- [ ] `provenance.json` lists the author and any third-party material.
- [ ] All template placeholders are replaced; no absolute machine paths or personal data.
- [ ] Commits carry a DCO sign-off and the commit email matches your GitHub account.
