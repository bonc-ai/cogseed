# 侧边追问栏（Ask Aside）框架与实施方案

| 项 | 值 |
|---|---|
| 目标 | 在不污染主线的前提下，就主对话内容追问并获得解释 |
| 定位 | 只读旁听问答，**不是**第二条执行链路 |
| 成文日期 | 2026-08-05 |

---

## 1. 要解决的问题

用户在任务对话里拿到一个方案但没看懂。当前两条路都不好：

- 在主对话追问 → 打断主线、污染任务上下文、把解释性内容混进交付记录
- 换一个对话问 → 没有上下文，得手工复述半天

侧边追问栏解决这个：**能看到主对话上下文，但问答不进主对话历史。**

---

## 2. 已确认的设计决定

| # | 决定 |
|---|---|
| 1 | 问答**不进**主对话历史 |
| 2 | 上下文 = 选中消息 + 前 5 后 2 |
| 3 | 侧栏常驻，展开按钮开合 |
| 4 | 固定解释 Agent，只借模型配置 + 人格提示词 |
| 5 | **只读** —— 不改文件、不跑命令、不写记忆 |
| 6 | 问答记录跟随会话持久化 |

---

## 3. 架构决策：为什么必须绕开群聊总线

主对话发送链路是 `conversations.sendStream` → `groupChat.send` → `bus.ts`。侧栏**不能复用**，两条硬性原因：

1. 进总线必然写入主消息文件 —— 直接违反决定 1
2. AGENTS.md 规定群聊调度只有 `bus.ts::enqueue` 一条路径，禁止并行调度路径

因此侧栏走独立通道，直接调 `model/client.ts::streamChatWithModel`。

**这与决定 5 天然契合**：不接总线 → 没有工具注册、没有 worker 唤醒、没有并发写入。只读不是靠运行时检查实现的，是靠**不接入**实现的 —— 比事后拦截可靠得多。

```
主线：  用户 → sendStream → groupChat.send → bus.enqueue → worker → 主 jsonl
侧栏：  用户 → aside.askStream → streamChatWithModel → aside.jsonl
                                  ↑ 无工具、无总线、无 worker
```

## 4. 存储

### 4.1 落位

会话有两种布局（项目内 / 项目外），`conversationLayout()` 已统一处理，且每会话已有独立 `groupDir`。追问文件挂在同一布局下：

```
conversationLayout(uid, cid, projectHint).groupDir + '/aside.jsonl'
```

**必须复用 `conversationLayout`**，不得自行拼路径 —— 否则项目内会话的追问会写到错误位置（该布局是 v4 修复后的唯一权威）。

选择 `groupDir` 而非新目录的理由：会话删除时 `_purgeDeletedConversationFiles` 已调 `purgeGroupDir`，追问文件**自动随会话清理**，不需要额外挂钩。

### 4.2 记录结构

```ts
export interface AsideTurn {
  turnId: string;
  /** 触发本轮的主对话消息序号 */
  anchorIndex: number;
  /** anchor 文本快照（截断）。主对话分页后 anchorIndex 可能不在当前页，
   *  没有快照的话侧栏历史会失去指向。 */
  anchorExcerpt: string;
  question: string;
  answer: string;
  /** 回答者身份，供审计 */
  agentId: string;
  model: string;
  createdAt: string;
}
```

append-only jsonl，与主消息文件**物理隔离**。

## 5. 上下文构造

### 5.1 窗口

选中第 N 条 → 取 `[N-5, N+2]`，共 8 条。

前 5 后 2 的理由：用户没看懂的是**已经读到的内容**，之前的铺垫是理解所需；之后的内容他还没看到，多带等于剧透且浪费 token。

边界：N<5 时从 0 起，N+2 超出则截断。不足 8 条不补齐。

### 5.2 复用既有读取

```
chats.getMessagesPageAtIndex(userId, cid, anchorIndex, limit, projectId)
```

`conversations.history` 的 `around_index` 分支已经走这条路，侧栏直接复用，不新写读取逻辑。

### 5.3 注入形态

```
[主对话上下文 · 只读]
<8 条消息，带角色标注>

[用户选中的内容]
<anchor 全文>

[用户的问题]
<question>
```

系统提示词固定三条：只解释不执行、不臆造上下文外的信息、不确定就说不知道。

### 5.4 同线程连续追问

第二轮起带本线程历史问答（上限 6 轮，超出丢最早），但**主对话上下文只注入一次**。否则第五轮的 prompt 会臃肿到影响回答质量。

---

## 6. 解释 Agent 解析

三级回退：

1. 会话绑定的 `conv.agent_id`（存在且 `isAgentEnabled`）
2. 群聊场景：最后发言的 agent
3. 都没有：默认模型配置

只取**模型配置 + 人格提示词**，不加载技能、工具、记忆写入能力。

结果是风格一致，但它不是"那个 agent 在替你干活"，而是"用同样的模型解释刚才那段"。

## 7. 交互

### 7.1 入口

消息气泡已有溢出菜单 `chat-bubble-more-menu`（复制 / 选择 / 归档），在其中**追加一项「追问」**，不新造入口。

点击后：侧栏展开 → 以该条为 anchor 起新线程 → 输入框聚焦。

### 7.2 侧栏本体

参考 `chat-md-drawer` 的抽屉模式（CSS 与开合逻辑可循）：

```
┌─ 追问 ─────────────── [收起] ┐
│ 关于：<anchorExcerpt 截断>   │
│ ──────────────────────────  │
│ Q: 为什么要先冻结基线？      │
│ A: 因为……                    │
│ ──────────────────────────  │
│ [输入框]             [发送]  │
└─────────────────────────────┘
```

- 常驻但默认收起，展开按钮在对话区右上
- 切换会话时重载该会话的 aside 记录
- 流式输出复用现有 SSE 渲染

### 7.3 视觉边界

侧栏必须与主对话明显区分（不同底色 + 「只读解释」标识）。否则用户会误以为在这里说的话能影响任务 —— 这个误解的代价比多写几行 CSS 大得多。

---

## 8. IPC

```
aside.list       { cid }                          → { turns }
aside.askStream  { cid, anchorIndex, question }   → 流式 answer
aside.clear      { cid }                          → 清空
```

`askStream` 注册到 `streamHandlers`（与 `conversations.sendStream` 同机制，独立通道）。

IPC 层只做校验：`cid` 走 `safeId`、`anchorIndex` 非负整数、`question` 非空且有长度上限。业务逻辑全在 feature。

---

## 9. 分层落位

| 文件 | 职责 |
|---|---|
| `features/conversation_aside.ts` | 存储读写、上下文构造、模型调用 |
| `ipc/index.ts` | 参数校验 + 转调 |
| `renderer/modules/chat-aside.js` | 侧栏 UI |
| `renderer/modules/conversation.js` | 菜单追加一项 |
| `renderer/index.html` / `style.css` | 抽屉容器 + 样式 |
| `locales/{zh,en,ja,pt}.json` | 文案 |

`conversation_aside.ts` 只依赖 `chats`（读消息）+ `model/client`（调模型）+ `project-layout`（路径），不反向依赖 UI。

---

## 11. 测试

核心不变量优先：

- **追问不出现在主消息文件中**（最重要，必须有）
- **不触达总线**：mock `bus.enqueue`，断言零调用
- 上下文窗口边界：anchor 为 0 / 末条 / 越界索引
- `anchorExcerpt` 在主对话分页后仍可读
- 线程内多轮裁剪（超 6 轮丢最早）
- 解释 Agent 三级回退
- 会话删除后 aside 文件不残留
- 渲染转义（问答含 HTML）
- 参数校验：非法 cid / 负索引 / 空问题
- 项目内会话与项目外会话都落到正确路径

---

## 12. 硬性禁止

- 追问写入主消息文件
- 接入 `bus.ts` / `groupChat.send`
- 给侧栏任何工具调用、文件写入、记忆写入能力
- 自行拼接会话路径（必须走 `conversationLayout`）
- 每轮追问重复注入主对话上下文
- 主对话上下文无上限注入（固定 8 条）
- 在 IPC handler 内写业务逻辑
