## 2. 远程协作原则

1. **所有任务必须可异步验收**：优先交付文档、录屏、截图、日志、Schema 样例。
2. **不依赖线下口头确认**：确认动作必须落成可追溯记录。
3. **每天只做短同步**：只对齐阻塞、依赖和当天验收结果，不开长会。
4. **先证据，后结论**：没有实物证据的任务，不进入 Gate 材料。
5. **真实运行优先**：US-05 不能用静态文本冒充。

## 4. 任务分发

### 4.1 牛保康：远程入口、导入、确认层

#### 负责任务

- **US-01 Mac端快速启动**
- **US-02 导入项目并掌控上下文**
- **US-04 执行前确认目标和 Context**
- **US-10 Personal Ontology 确认**

#### 远程交付要求

- 启动录屏
- 环境记录
- Known Issues
- 固定 Repo / 固定 Commit 导入记录
- ReferenceManifest
- TaskContract 确认记录
- PersonalOntologyRef 确认/修订记录

#### 远程协作方式

- 任务推进通过异步文档和录屏完成。
- 每次交付都写清：输入、操作、结果、卡点、下一步。
- 如需产品判断，只在短同步里确认，不拉长会。

#### 为什么这样分

- 这些任务最偏入口体验和用户确认。
- 远程情况下最适合用可回放材料验收。

### 4.2 吴嘉宇：理解、运行、评估层

#### 负责任务

- **US-03 校准系统对项目的理解**
- **US-05 启动真实 Agent 并掌握运行状态**
- **US-11 Skill 展示与评价基线**
- **EN-01 统一 KSTAR 运行与评估记录**（主责）
- **反假调度 / 失败可见**（US-05 前置）

#### 远程交付要求

- ProjectContext
- 修正前后 diff
- AgentRun
- RunEvent
- 真实运行日志
- SkillManifestRef
- SkillRun
- EvaluationRecord
- 统一 Schema 样例

#### 远程协作方式

- 先把字段和样例定死，再做运行。
- 所有运行结果必须能落日志和结构化记录。
- 失败要显式可见，不允许“看起来成功”。

#### 为什么这样分

- 这是“理解 → 运行 → 评估”的主链路。
- 需要把真实执行证据做扎实。

- 这部分负责把“能不能信”收口。
- 远程情况下特别适合由证据包驱动审查。

## 8. 一句话结论

在牛宝康远程的前提下，任务分发不能再按“人在一起协作”来设计，而要改成 **“远程异步交付 + 短同步对齐 + 证据驱动验收”**。这样才能把“导入 → 理解 → 确认 → 真实运行 → Evidence → Gate”这条链真正做实。
