# NSEAP Skill 标准（对外发布版）

**版本**：v1.0（对外发布版）　**日期**：2026-07-02
**文档性质**：规范性技术标准（specification）。本文规定"一个受治理的企业 AI 技能（Skill）应当是什么"——它的定义、结构、分级、生命周期、治理门禁、证据要求与演进纪律。

---

## 0. 适用性与限制声明

1. 本标准是**治理框架规范**，描述的是对技能资产的**要求**，不构成对任何具体系统当前能力、部署状态或客户价值的声明。
2. 实施本标准不等于生产就绪。本标准定义的最高自动化状态是 **staged（暂存）**；任何生产发布都必须经过标准之外的独立人类决策流程（第 9 章）。
3. 依据本标准做出的任何能力宣称，必须以真实或脱敏证据为条件（第 11 章证据标准、第 14 章宣称边界）。
4. 本标准借鉴了公开发表的神经符号企业 AI 研究成果（第 2 章），不宣称与任何第三方标准的正式符合性。

**规范性用语**（沿用 RFC 2119 惯例）：**必须/不得**＝强制条款，违反即不合规；**应当**＝除非有充分记录的理由否则遵守；**建议**＝推荐做法；**可以**＝可选。凡进入第 13 章合规评定的阈值一律为"必须"级。

---

## 1. 范围

**适用于**：在企业环境中，以"技能（Skill）"为最小能力单元来构建、评测、治理和演进 AI 能力资产的组织与系统，包括：业务技能的研发方、技能生产流水线（元技能）的建设方、以及对技能资产实施治理的职能。

**全量适用、无豁免**：本标准适用于体系内**所有**技能与元技能。其依据是本标准的同构公理——**元技能本身就是一个技能**（MetaSkillPackage is-a SkillPackage，第 6.2 节）：is-a 关系使本标准对元技能自动成立；元技能不因其"生产其他技能"的身份豁免任何条款，第 6.2 节附加条款是子类的额外约束，只加严、不减免；元技能的每个一等子技能自身也必须符合本标准（不能只是函数名、配置声明或界面页签）；复合技能（技能组）的每个成员技能独立适用本标准。

**不覆盖**：基础模型训练、算力基础设施、具体产品实现方式、生产环境发布流程（后者由实施方的独立发布治理约束）。

## 2. 理论基础与参考文献

**NSEAP** 为发布方使用的架构与标准名称（Neuro-Symbolic Enterprise AI Platform，神经符号企业 AI 平台），非第三方标准。

本标准的方法论基础：

- **公开文献**：《NEOLAF, an LLM-powered neural-symbolic cognitive architecture》（Never-Ending Open Learning Adaptive Framework），arXiv:2308.03990（2023）。本标准使用的 KSTAR 情境化知识表示（以 K 知识、S 情境、T 任务、A 行动、R 结果五元组刻画一次能力执行，以预测与实际之差作为学习信号）其定义源出该文献。
- **发布方自有方法论**：神经符号企业 AI 架构（符号层与神经层分工的企业级认知治理架构）为发布方在上述公开研究基础上发展的自有方法论，本标准即其规范化表述。

本标准参考了 IEEE 在智能体系统方向的标准化进展（如 IEEE P3394 大模型智能体接口等工作组进程）作为设计对照；**不宣称与任何第三方标准的符合性**。

## 3. 术语与定义

| 术语 | 定义 |
|---|---|
| **Skill（技能）** | 可触发、可执行、可验证、可回放、可归因、可治理、可进化的能力单元。不是一次性 prompt、脚本、聊天模板或 Agent 外壳。 |
| **SkillPackage（技能包）** | Skill 的最小可审计资产包：技能本体切片、工作流、工具绑定、评测、演进钩子与治理契约的封装。技能体系的主产物。 |
| **Meta-Skill（元技能）** | 生产技能的生产过程技能：从业务情境出发，创建、验证、执行、评测、治理和演进 SkillPackage 资产。元技能自身也是一个 SkillPackage（同构原则）。 |
| **Ontology（本体）** | 技能的世界模型，由 TBox（概念/类）、ABox（实例/事实）、RBox（规则/关系）三部分构成。每个技能持有自己的本体切片。 |
| **EndUseSkill（最终使用技能）** | 被业务用户或任务智能体直接调用、完成业务/交付任务的技能。 |
| **ProductionProcessSkill（生产过程技能）** | 生产、验证、治理、演进其他技能资产时使用的技能。元技能属于此类。 |
| **Owner（属主）** | 对技能的业务正确性负责、拥有语义验收权的业务责任人。业务事实基准（Ground Truth）的提供者。 |
| **staged（暂存态）** | 通过治理门禁后技能可达到的最高自动化状态。staged ≠ 发布。 |
| **release_ready（发布就绪）** | 锁定态之一：自动流程不可达，仅可由独立的人类发布决策流程置入（第 9.2 节）。 |
| **金丝雀（Canary）验证** | 在代表性/小范围场景先行验证候选变更不劣化的做法；本标准中金丝雀门是**暂存前**的最后校验，不是发布批准。 |
| **HITL** | Human-in-the-loop，关键动作的强制人工确认。 |
| **KSTAR Episode** | 一次能力执行的完整学习记录：情境、任务、预测（Â、R̂）、实际（A、R）、偏差（ΔA、ΔR）与归因。 |
| **ΔR / ΔA** | ΔR = 实际结果 − 预测结果（核心学习信号）；ΔA = 预测行动与实际行动之偏差（信任门控信号）。 |

## 4. 总则（五条公理）

一切条款由以下公理推出：

1. **能力成为资产包**：可复用的能力必须封装为 SkillPackage；证据、决策、执行轨迹保持为治理记录，不封装为技能。
2. **无本体不成技能**：没有本体切片的"技能"只是脚本或提示词，不是可治理的能力资产。
3. **符号裁决对错，神经建议好坏**：大模型可以起草候选、润色措辞、提出建议，但不得裁决良构性、支持度、门禁通过或知识提交——这些裁决必须由确定性的符号层做出。
4. **证据先于宣称**：任何能力宣称必须能回溯到可复验的证据；合成/模拟证据必须诚实标注，不得表述为业务价值。
5. **暂存封顶**：自动流程（包括技能的自我演进）最高只能把资产推进到 staged；生产发布是独立的人类决策，永远不被任何评测分数、回放通过或学习信号自动触发。

## 5. Skill 定义与九要素契约

### 5.1 定义

> **Skill = 可触发、可执行、可验证、可回放、可归因、可治理、可进化的能力单元。**
> **SkillPackage = Skill 的最小可审计资产包**，含 schema、本体切片、工具绑定、评测集、属主与更新策略、演进钩子。

### 5.2 九要素契约（每个 L3 级以上技能必须显式具备）

```text
Skill =
  触发语义（含反触发）        Trigger Semantics
+ 业务上下文映射              Business Context Mapping
+ 可执行工作流                Executable Workflow
+ 工具/资源绑定               Tool / Resource Binding
+ 验证契约                    Validation Contract
+ 评测/回放/回归契约          Eval / Replay / Regression Contract
+ 失败归因                    Failure Attribution
+ 演进钩子                    KSTAR Evolution Hook
+ 治理边界                    Governance Boundaries（含禁止宣称清单）
```

业务上下文的构成公式：

```text
Business Context = relevant(TBox) + applicable(RBox) + current(ABox)
```

**分级适用说明**：L3 技能必须**声明**全部九要素（结构存在，允许占位模板）；自 L4 起，评测/回放/回归契约与演进钩子必须**一等运行**（有预测/实际/偏差的闭环数据）。

### 5.3 触发语义是硬性要求

技能必须同时声明**何时使用**（use_when，含正例）与**何时不得使用**（do_not_use_when，含反例）。缺少反触发语义的技能不得进入注册表——只知道自己能做什么、不知道自己不该做什么的能力单元是治理风险。

### 5.4 输入/输出契约是硬性要求

每个技能**必须**声明非空的输入 schema 与输出 schema，并各自落盘为契约件（`references/input-contract.md`、`references/output-contract.md`）：调用方靠输入契约知道传什么，验证门与工具绑定靠双契约判定执行合法性。此要求**无一例外，元技能同样适用**（元技能的输入 = 业务材料/情境/能力资产，输出 = 技能包草稿等制品）。schema 骨架应当由工具从工作流/工具绑定派生，人只定业务字段语义。输入/输出契约非空是 Level B（注册准入）的机检项。

## 6. 技能分类与元技能附加条款

### 6.1 顶层二分

| 类别 | 作用对象 | 发布边界 |
|---|---|---|
| **EndUseSkill** | 业务/交付任务 | 可 staged 供沙箱/演练环境的任务智能体消费验收；**不得直通生产环境**，生产消费须独立发布决策 |
| **ProductionProcessSkill** | 技能/本体/评测/治理等能力资产 | 只能产出候选、暂存资产与发布证据，**不能自动发布任何最终技能** |

固定关系：生产过程技能生产/验证/治理最终使用技能；元技能是生产过程技能的一种。

四条禁止混淆：生产过程技能的成功 ≠ 业务价值已验证；最终技能一次运行成功 ≠ 生产线成熟；元技能的自我演进能力 ≠ 用户可调用的业务能力；某个技能进入 staged ≠ 允许生产线自动发布更多技能。

### 6.2 元技能附加条款（同构原则）

元技能必须与普通技能**同构**——同样是 SkillPackage，满足全部九要素，接受同样的治理。在此之上追加身份与安全子句：

```yaml
skill_class: meta_skill
is_skill_of_skill: true            # 造技能的技能
operates_on: [Skill, OntologySlice, EvalCase, Workflow, Policy, MetaSkill]
promotion_ceiling: staged          # 晋升天花板锁死
production_release_allowed: false
mutation_surface_policy:           # 可变面 / 保护面
  mutable_surface: [配置键, 阈值权重, 策略开关]
  protected_surface: [形式化规则结构, HITL 要求, 审计机制]   # 永不可被补丁修改
recursive_guard:                   # 自我演进递归护栏
  max_self_patch_ops: ≤2           # 必须有界（规格上限）；实现可更严——参考实现的自我演进补丁预算取 1
  max_self_patch_depth: 1          # 一次自审至多一层补丁，禁止无界递归自改
  self_patch_must_pass_gates: [验证门, 治理门, 金丝雀门]
  rejected_self_patch_buffered: true   # 被拒补丁永久留痕，防重复提交
```

元技能还必须证明：自身可被审计、回放、评测、治理与暂存；自我演进只产生 staged 候选；不存在对生产资产（技能/本体/元技能）的热更新路径。**元技能的每个一等子技能自身也必须满足本标准的合规评定**（第 13 章）——尚未独立成包的子技能只能作为登记在册的过渡形态存在，且必须记录其合规差距与成包计划。

## 7. 能力分级与风险路由

### 7.1 六级能力分级

| 等级 | 含义 | 最低判据 |
|---|---|---|
| L0 | 临时 prompt | 不沉淀为持久技能 |
| L1 | 清单/SOP | 有步骤，无本体、无验证契约 |
| L2 | 操作型技能 | 有工作流 + 工具/资源绑定 |
| L3 | 本体接地技能 | 有 TBox/RBox/ABox 映射和验证契约 |
| L4 | 因果演进技能 | L3 + 一等评测/回放/回归 + 预测/实际/偏差/归因/更新候选 |
| L5 | 受治理技能系统 | L4 + 注册表、审批、发布、回滚、晋升、审计门 |

进入共享注册表的技能必须达到 **L5**。元技能恒为 L5——因为它影响共享能力资产、本体、评测与发布语义。

### 7.2 风险路由三档

| 路由 | 适用 | 晋升上限 |
|---|---|---|
| Core | 个人、低风险、本地学习 | 本地候选 |
| Lite | 可逆的项目级复用技能 | 回放 + 属主评审后至多暂存（staged） |
| Full | 元技能、共享注册表、客户/私有数据、跨租户、**涉及生产/对外能力宣称的变更**、权限与政策、TBox/通用 RBox | **晋升上限恒为 staged**；release_ready 及以上属锁定态（第 9.2 节），仅可由独立的人类发布决策流程另行开启；生产发布必须单独审批 |

硬边界不等式（任何实现不得混淆）：

```text
候选 ≠ 暂存        staged ≠ release_ready        release_ready ≠ 生产发布
ΔR ≠ 发布指令      执行成功 ≠ 发布批准            属主验证 ≠ 生产审批
```

## 8. 技能包制品规范

### 8.1 标准目录

一个合规的技能包至少包含：

```text
skill-name/
├── SKILL.md                        # 技能说明：业务描述、触发语义、边界
├── agents/<runtime>.yaml           # 运行时代理声明（执行器、权限、治理段）
├── evals/
│   ├── evals.json                  # 机器可读评测集（正/反/边界例）
│   ├── forecast_model.md           # 预测模型说明
│   ├── outcome_evaluation.md       # 结果评估说明
│   ├── replay_dataset.md           # 回放数据集说明
│   └── regression_tests.md         # 回归测试说明
└── references/
    ├── skill-spec.yaml             # 机器可读技能规格（身份/分级/路由/边界）
    ├── ontology-mapping.md         # 本体映射
    ├── kstar-evolution.md          # 演进机制说明
    ├── validation-contract.md      # 验证契约
    ├── input-contract.md           # 输入契约（§5.4，硬性要求）
    ├── output-contract.md          # 输出契约（§5.4，硬性要求）
    ├── governance-boundaries.md    # 治理边界与禁止宣称
    ├── eval-cases.yaml             # 评测用例（机器可读）
    └── failure-modes.md            # 失败模式
```

元技能包在此之上增加：`ontology/`（自身的五层本体：实体/事件/规则/动作/状态机）、`scripts/`（合规校验器与工具）、`config/`（可调配置与规则覆盖）。

### 8.2 分发排除清单

可分发的技能包内**禁止**包含：真实执行记录实例、真实客户轨迹、真实属主/发布决策记录、会话记忆、运行态缓存、日志、密钥与凭证。包内只允许 schema、模板、测试夹具（fixture）、合成样例和脱敏且获批的示例。

### 8.3 易用性要求（对实施方的强制约束）

- **默认值即合规**：技能生产工具的默认产物必须直接满足基础合规档（第 13 章 Level A），不得让作者面对"默认配置过不了门"的陷阱。
- **模板自动生成**：上述制品中的多数应由元技能生成模板；人必须亲手写的只应是业务描述、触发/反触发语义、正/反例、业务评测用例与输入/输出契约的业务字段语义（五件，与附录 A 第 3 步一致）。
- **复杂度预算**：实施方向标准追加任何必备制品或门禁前，必须回答三问——谁消费它？缺了它会发生什么坏事？能否由工具自动生成？答不出任何一问，不得追加。

## 9. 生命周期与晋级语义

### 9.1 状态机

技能资产带唯一 ID 走同一状态机。参考主链：

```text
intake（收案）→ 材料整备 → 本体草案 → 本体评审 → 技能包草稿
→ 运行画像绑定 → 工厂交接就绪 → 沙箱注册 → 执行演练 →（执行验证 | 执行阻断）
→ 评测回放 → 学习记录 → 补丁候选 → 治理评审 → staged | rejected
```

### 9.2 锁定态

以下状态被**默认锁定**，任何自动流程请求即拒：

```text
release_ready（发布就绪）、production_release（生产发布）、published（已发布）
```

仅当独立的发布决策流程（含明确发布意图、证据清单、已验证回滚方案、责任审批人）另行批准时，资产才可进入更高发布路径。实现上建议采用**请求级硬锁**：对锁定态的任何请求直接拒绝并记入审计。

## 10. 治理门禁与审计

### 10.1 三门固定顺序

```text
验证门（Validation）→ 治理门（Governance）→ 金丝雀门（Canary，暂存前门）
```

- **验证门**：候选变更在回放集上整体改善、且逐场景无回归。
- **治理门**：保护不变量零违反（形式化规则结构、HITL 要求、审计机制不可被任何补丁触碰）。
- **金丝雀门**：代表性场景金丝雀验证不劣化（术语见第 3 章）。此门是**暂存前**的最后校验，通过后资产至多进入 staged，**不是**生产发布批准。

任一门未过 → 变更被拒，且被拒补丁进入**拒绝缓冲**永久留痕，防止同一变更反复提交。

### 10.2 治理回执

走 Full 路由的变更在进入 staged 前必须集齐结构化回执：**回放报告、属主验证决定、治理决定、独立治理门决定、发布决定（进入 staged 前必须为"阻断/非发布路径"）、回滚方案（已验证）、数据边界批准、审计账本**；版本账本为 Level C（发布评估）必备回执。

- **属主验证 ≠ 发布批准**；**回放通过 ≠ 发布批准**。
- 涉及客户/私有数据的学习与复用，必须有显式的**数据边界批准**；客户私有语义数据默认**不回流**共享资产。
- 审计与版本账本 **append-only**（只增不改）；高风险写操作一律"预览 → 人工确认 → 执行"三段式并记录确认人。

## 11. 证据与评测标准

### 11.1 一等评测契约

每个 L4 级以上技能的评测遵循 `预测 → 实际 → 偏差 → 回放/回归` 闭环：执行前给出预测（预期结果/置信度/成本/时延），执行后记录实际值，偏差进入学习管线；回放、回归、基线三者必备。

### 11.2 证据诚实标注

每条证据必须标注来源档位：`real（真实）| desensitized（脱敏）| synthetic（合成）| manual（人工）| stub（桩）`。合成/人工/桩证据必须附带非宣称说明，且业务价值声明位恒为否。**执行返回码为 0 不构成验证通过**；准备态（prepared/dry-run）不得记为验证通过。

### 11.3 数量门槛（两级）

| 档 | 门槛 | 适用 |
|---|---|---|
| 登记最低档 | ≥10 条评测用例，其中 ≥4 条反例 | 单个技能进入注册表 |
| 发布评估档 | ≥20 条评测 + ≥5 条失败用例 + ≥10 条完整学习记录（每条必须含预期偏差信号与结果归因键——缺归因键不得宣称"系统学会了"）+ ≥3 个补丁提案 | 技能系统整体发布评估 |

回归测试必须覆盖五条红线：发布绕过、数据边界、偏差信任门、属主否决、回放失败。

## 12. 演进纪律（KSTAR）

技能不是固定 prompt，是活的、可演进的资产——但演进必须守纪律：

1. **信号定义**：ΔR = 实际结果 − 预测结果；ΔA = 预测行动与实际行动的偏差。
2. **ΔA 门控 ΔR**：执行走样（ΔA ≠ 0）时，ΔR 不可信，只能用于诊断执行/工具/权限问题（"先修身体，再学脑子"），不得作为知识更新依据。
3. **单证据单信号**：一份证据 → 一条学习记录 → 至多一个学习假设；单条记录永不直接触发知识更新。
4. **符号聚合**：学习假设按符号层稳定键聚合为候选，不按自由文本聚合；候选须达到最低支持度（≥2 条独立证据）方可进入提案。
5. **有界补丁**：变更以补丁提案表达，操作数**必须**受编辑预算约束（≤2），只能触碰声明的可变面（配置、阈值、策略开关），永不触碰保护面（形式化规则结构、HITL、审计）。
6. **三门后提交**：补丁通过验证门、治理门、金丝雀门后才回写知识资产，回写伴随版本递增与审计记录；任一门失败即拒绝并入拒绝缓冲。
7. **元技能自我演进**：只产生元知识层的 staged 候选，在沙箱副本上验证，受递归护栏约束，人工评审是硬环节。

## 13. 合规等级与评定

三级向上兼容的合规等级（实施方自评 + 独立复核）：

| 等级 | 名称 | 要求 | 面向 |
|---|---|---|---|
| **Level A** | 最小良构 | 本体切片、规则、状态机、manifest 清单、可变面/保护面声明五项齐备；机器校验通过 | 每个技能草稿 |
| **Level B** | 注册准入 | Level A + 九要素契约完整 + 触发/反触发与正反例 + **输入/输出契约非空**（§5.4）+ L5/Full 画像 + 8.1 制品齐备 + 登记最低档评测 | 进入共享注册表的技能 |
| **Level C** | 发布评估 | Level B + 治理回执全集（含版本账本）+ 发布评估档证据 + 可复现的发布证据清单（必须可由工具从现行制品自动重新生成并独立复验，不接受不可复验的人工汇总） | 申请进入发布路径的技能系统 |

每级都必须有**机器可执行的合规校验器**；不可机检的条款须给出人工检查清单与责任角色。

## 14. 实施方边界与禁止宣称

采用本标准的组织，在对外表达中：

**可以说**（前提：以第 13 章相应等级评定通过为条件——机器校验器结果 + 独立复核记录在案；未经评定不得使用以下表述）：已按 NSEAP Skill 标准建立受治理的技能研发与验证流程；技能资产经评定达到本标准 Level A/B/C 合规；系统实现了 staged 封顶与独立发布决策分离。

**必须满足条件才能说**（须真实或脱敏证据支撑）：技能在某业务场景验证有效；学习闭环从真实业务中产生了被采纳的改进。

**不得说**：实施本标准即等于生产就绪或已投产；评测/回放通过等于业务价值已验证；系统具备"自主进化/无人值守进化"能力（本标准明确禁止无监督的知识自动提交）；合成或演示证据代表客户价值；已获得任何第三方标准的正式认证（除非确已获得）；未经真实/脱敏或第三方证据，不得宣称基于本标准的系统超越任何具名竞品或业界方案。

## 附录 A：快速合规指南（技能作者视角）

造一个合规技能的最短路径：
1. **给材料**：把业务材料（SOP/专家修正/样例）交给技能生产元技能；
2. **预览确认**：生成的技能草稿经你确认——默认产物即满足 Level A；
3. **补五件**：亲手写业务描述、触发/反触发语义、正反例、业务评测用例、输入/输出契约的业务字段语义（骨架已由工具生成）——即达 Level B 候选；
4. **走门禁**：三门与回执由治理流程执行，不需要技能作者操心。

## 附录 B：与常见实践的区别

（本表为**概念边界对照**，帮助读者理解本标准的适用范围，不构成对任何具体产品或方案的优劣评价。）

| 常见实践 | 与本标准的差异 |
|---|---|
| Prompt 库 | 无本体、无验证契约、无演进纪律——L0/L1，不是受治理技能 |
| Agent 框架编排 | Agent 是运行时视图；本标准的主资产是技能包，运行画像由技能包派生 |
| 自动 prompt 优化 | 无 ΔA 信任门、无有界补丁、无三门治理的自动优化不满足第 12 章 |
| 模型微调 | 本标准演进的是"文档与规则"（技能资产），不是模型权重 |
