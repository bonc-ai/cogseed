# 消息平台设置页高密度布局设计

## 目标

针对桌面端消息平台设置页，提升右侧配置区的信息密度，使已绑定实例的主要配置在常用 Electron 窗口高度内尽量完整展示；收窄左侧平台菜单，把释放出的横向空间交给右侧配置区；将消息平台页面的白色块面调整为与应用整体浅绿主题兼容的局部背景。

本次只调整消息平台设置页的视觉布局和样式，不改变消息平台的 IPC 契约、绑定流程、扫码状态机、实例启停、解绑、删除和偏好保存逻辑。

## 现状与约束

- 消息平台 DOM 由 `src/renderer/modules/messaging-settings.js` 动态渲染。
- 设置页入口位于 `src/renderer/index.html` 的 `data-settings-pane="messaging"`。
- 消息平台专属样式位于 `src/renderer/style.css` 的 messaging settings 区段。
- 消息平台是菜单加详情面板的双栏布局，当前菜单宽度为 `280px`。
- 右侧内容在 `.messaging-page` 内滚动，卡片和输入控件大量使用全局 `--surface` 白色背景。
- 渲染器使用原生 HTML/CSS/JavaScript；不引入依赖，不改变现有动态渲染方式。
- 当前应用主题变量为浅绿背景、森林绿文字和主色；全局主题变量不应因本次页面调整而改变。

## 设计

### 1. 双栏布局

消息平台工作区继续使用现有两列结构，但将列宽调整为：

- 左侧菜单：约 `224px`，允许在合理范围内使用 `minmax(218px, 232px)` 约束。
- 右侧配置：`minmax(0, 1fr)`，占据全部剩余空间。
- 两列间距收紧到适合桌面设置页的值，避免菜单与详情之间出现过大的空隙。

消息平台外层 shell 和详情页面铺满设置内容区。外层不再用明显纯白大框包住整块内容，保留边框作为工作区边界；详情内容仍保持可滚动兜底，但在正常桌面窗口高度下通过压缩垂直间距减少滚动需求。

### 2. 左侧平台菜单

保留现有“已开放 / 即将支持”分组、品牌图标、选中态和已绑定状态。

- 减小菜单横向 padding、平台行间距和单行高度。
- 图标保持可辨识尺寸，平台名称继续使用省略保护，已绑定状态不挤压名称。
- 活动项仍使用 `--primary-soft`，禁用项继续保留低饱和度和不可点击状态。
- 不修改频道顺序和点击行为。

### 3. 右侧详情面板

右侧详情面板保持现有动态组件和业务状态，只调整布局规则：

- 顶部平台标题、连接状态和开关压缩垂直留白，保持单行级别的紧凑头部。
- 配置卡片的外部间距收紧为约 `6–8px`，内部 padding 控制在约 `10–12px`。
- 绑定实例列表保持纵向实例行，实例数量增加时自然扩展，不隐藏解绑和启停操作。
- 在桌面高密度断点下，关联机器人与机器人归属使用两列布局；若当前状态显示二维码或绑定状态，区域在同一列内自然展开。
- 回复颗粒度与工作区访问范围使用两列紧凑偏好行，标题、说明和控件保持可扫描关系。
- 删除操作继续使用独立危险操作区域，保留现有确认流程和危险色。
- Telegram、企业微信和未绑定状态复用紧凑卡片规则，不复制新的渲染逻辑。

如果现有 DOM 无法支撑并排布局，只增加消息平台专属的最小结构 class；不重写渲染器组件，不把业务判断移入 CSS。

### 4. 局部配色

不修改全局 `:root` 颜色变量，只在消息平台范围内重新组合现有主题 token：

- 外层工作区和详情背景使用 `var(--bg)` 或与其接近的主题混合色。
- 左侧菜单使用略深的 `var(--surface-2)`，与右侧内容形成低对比度分区。
- 活动项使用 `var(--primary-soft)`。
- 卡片使用主题浅色混合背景和现有边框变量，避免大面积纯白块面。
- 输入框、选择器、按钮继续保持足够对比度；成功、错误和危险状态沿用现有语义颜色。
- 二维码容器必须保持高对比度白色背景，以保证二维码可扫描；这是功能性例外，不视为页面主体白底。

## 响应式策略

- 桌面高密度规则面向截图对应的常用 Electron 窗口尺寸，优先让已绑定实例的主要配置完整出现在一个屏幕内。
- 当窗口高度明显不足时，保留详情页的外层滚动，避免固定高度导致内容裁切。
- `760px` 以下继续缩小头部和品牌图标，`560px` 以下回退为纵向卡片、全宽选择器和纵向二维码布局。
- 桌面端的两列配置只在有足够横向空间时启用，窄窗口不强行并排，避免输入框和按钮不可用。

## 数据流与错误处理

本次不改变数据流：

1. `initMessagingSettings` 继续通过 `messaging.list` 加载实例。
2. 菜单点击继续只更新 `selectedChannel` 并触发重新渲染。
3. 绑定、扫码、启停、解绑、删除和偏好选择继续通过现有 `window.orkas.invoke` 通道调用 main。
4. 状态通知继续由现有 `state.notice` 和 `appendNotice` 渲染。

样式改动不得隐藏错误提示、扫码状态、禁用状态或进行中的操作状态。动态内容出现时允许面板高度增加，不能通过 `overflow: hidden` 截断。

## 实现范围

预期修改：

- `src/renderer/style.css`：消息平台专属布局、间距、背景、卡片和响应式规则。
- `src/renderer/modules/messaging-settings.js`：仅在 CSS 无法区分布局单元时补充最小 class 或 wrapper。
- 相关 renderer 测试：补充或调整布局契约检查，确保消息平台专属选择器和现有动态结构一致。

不修改：

- `src/main/ipc/messaging.ts`。
- `src/main/features/messaging/**`。
- 全局主题变量。
- 频道数据、文案、IPC 名称和业务状态机。

## 验证

### 自动验证

- 使用项目约定的 `npm test`，不直接运行 `npx vitest`。
- 检查现有消息平台 renderer 测试和布局相关测试。
- 对修改后的 CSS 做 diff 检查，确认规则限定在 messaging settings 命名空间，未误改全局样式。

### 真实环境验证

- 按项目约定重启当前工作树的 Mate 客户端。
- 在常用桌面窗口尺寸检查：菜单收窄、右侧扩展、主要配置单屏可见、背景与整体浅绿主题一致。
- 检查已绑定飞书、未绑定飞书、Telegram、企业微信和二维码流程的可见性与可操作性。
- 检查启用开关、解绑、删除、选择器和错误提示没有因压缩布局而被遮挡。
- 缩小窗口验证 `560px` 以下的纵向布局和必要滚动仍然有效。

## 验收标准

- 左侧消息平台菜单明显小于当前 `280px`，目标约 `224px`。
- 释放的横向空间全部被右侧配置区利用，右侧没有无意义的固定空白。
- 消息平台主体不再呈现与整体主题割裂的大面积纯白背景；主要卡片层次仍清晰。
- 常用桌面窗口高度下，已绑定实例的主要配置无需滚动即可看到；动态二维码、多实例和错误提示不被截断。
- 现有消息平台交互和 IPC 行为保持不变。
- 窄窗口仍可用，文字、按钮、输入框和二维码不发生重叠或溢出。
