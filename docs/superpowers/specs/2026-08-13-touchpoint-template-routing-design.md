# 触达审批模板与消息实例路由设计

## 目标

让审批类飞书/Lark 触达具备可持久化的场景模板和明确的机器人实例路由，解决审批卡片内容无法自定义、同时存在多个飞书/Lark 机器人时发送目标不确定的问题。

## 已确认的产品语义

- 模板按触达场景保存，而不是只有一份全局模板；当前覆盖 `task_approval`、`ontology_confirmation`、`daily_briefing`、`external_send` 等已存在或可扩展的场景。
- 每个用户有一个全局默认消息实例；每个场景可以选择一个实例覆盖全局默认。
- 实例候选来自当前用户已配置的 `feishu_lark` 实例，展示飞书/Lark 品牌、显示名、连接状态和绑定身份。
- 场景未配置覆盖时跟随全局默认实例。
- 场景覆盖实例被删除、禁用、未连接或未绑定时，发送明确失败，不自动切换到其他机器人，避免误投递。
- 模板可编辑标题、正文和按钮显示文字；按钮的内部动作、签名、动作 ID 和审计状态保持系统固定值。
- 模板只允许白名单变量；未知变量、空标题、超长文本、重复或缺失必需动作在保存时拒绝。
- 模板预览使用代表性输入，不会把预览标记为真实发送成功。

## 架构

新增触达配置 feature 作为模板与路由的唯一业务边界：

1. `features/touchpoints/config.ts` 负责用户级 JSON 配置的读取、规范化、校验、原子写入和按场景解析。
2. `features/touchpoints/template.ts` 负责白名单变量替换和从安全模板生成 `TouchpointIntent` 的展示内容/按钮文案。
3. `features/touchpoints/routing.ts` 负责全局默认与场景覆盖的解析，并校验实例属于当前用户、平台正确且在发送时仍可用。
4. IPC 只负责校验 payload、注入 `userId` 和调用上述 feature；renderer 通过现有 `window.cogseed.invoke` 访问配置。
5. 现有 `buildTouchpointCard` 保留动作签名和回执结构，只从配置后的 intent 读取标题、正文和按钮显示文字。

## 数据

配置存储在当前用户的 `cloud` 触达配置文件中，版本化并支持缺省回退：

```json
{
  "version": 1,
  "defaultInstanceId": "instance-id-or-null",
  "templates": {
    "task_approval": {
      "title": "{{actor}} 请求你确认任务",
      "body": "{{summary}}\n影响范围：{{impact}}",
      "buttons": { "approve": "同意执行", "reject": "退回补充材料" }
    }
  },
  "routes": { "task_approval": "instance-id-or-null" }
}
```

未配置模板时使用代码内置默认模板；未配置场景路由时使用 `defaultInstanceId`。保存配置时不允许写入凭据、完整 open id 或其他敏感字段。

## 错误与恢复

- 配置文件不存在：返回空配置并使用内置默认模板；首次成功保存时创建文件。
- 配置 JSON 损坏：记录带用户范围的脱敏告警，拒绝使用损坏内容并回退默认模板/无路由状态。
- 保存参数非法：返回字段级错误，不写入部分结果。
- 发送前重新读取并验证实例实时状态；实例不满足平台、enabled、connected、owner bound 任一条件时返回稳定错误码。
- 实例被删除或禁用后，配置保留其 ID 以便界面显示“已失效”，但解析不会选择它；用户必须主动改选或清除覆盖。

## 测试与验收

- 配置读写：缺省、原子写入、损坏回退、字段校验、并发写入。
- 模板：白名单变量替换、未知变量拒绝、长度限制、动作固定、缺省模板回退。
- 路由：场景覆盖优先、全局默认回退、实例不存在/禁用/未连接/未绑定均 fail-closed、不跨用户读取。
- 发送链路：审批卡片使用自定义标题/正文/按钮文字，回执仍归一化为固定动作；测试发送和定时简报都传递明确实例 ID。
- Renderer contract：实例选择、模板编辑、保存成功/失败、失效实例提示和预览渲染。
- 真实环境：重启当前 messaging worktree，确认启动日志、设置页加载、选择两个实例分别发送测试卡片；不把 Mock 或单元测试当作真实投递完成证据。
