# 协作概览抽屉设计规范

> 日期：2026-07-25
> 版本：v0.1
> 适用产品：Mate Agent / 协作概览抽屉
> 状态：设计稿，待确认后进入实施计划

## 1. 目标

为**当前会话**增加一个轻量的**协作概览抽屉**，让用户在不离开主会话的前提下，快速理解多 Agent 协作的进展状态。

这个抽屉不是第二个会话界面，也不是独立工作台。它是**当前会话协作状态的结构化概览层**。

## 2. 产品定位

Mate Agent 现在已经有不少和协作相关的能力，但用户视角仍然偏碎：

- 主会话历史
- Wake Gate 卡片
- KSTAR Review 卡片
- Patch Candidate 审核面板
- 新做的 Agent Activity

问题不是这些能力不存在，而是：

> 用户很难在一个地方快速看清“当前这场协作整体在发生什么”。

`协作概览抽屉` 的作用，就是把这些分散的协作状态收成一个**轻量、统一、不会打断主会话的总览层**。

主会话依然是工作的核心空间；抽屉负责的是：

- 总览
- 定位
- 解释

## 3. 和主会话的关系

主会话仍然是事实源。

推荐关系定义：

```text
主会话 = 事件流与真实操作面
协作概览抽屉 = 当前会话的结构化投影
```

这意味着：

- 会话历史是唯一的正式账本
- 抽屉读取并组织当前会话里的协作事实
- 审批动作继续留在主会话
- 抽屉可以提示、定位、跳回主会话的相关位置

这个抽屉不能变成第二套并行工作流状态。

## 4. 范围

### 4.1 本阶段纳入范围

- 为当前会话增加一个**协作概览抽屉**
- 提供当前会话协作状态的结构化总览
- 复用现有 conversation、runtime、collaboration、KSTAR、wake、patch candidate 等事实数据
- 将已经设计好的 `Agent Activity` 作为抽屉中的一个模块，而不是单独终点
- 集中展示当前会话中哪些地方被阻塞、哪些地方值得用户关注
- 保持所有真正的审批动作继续在主会话中完成

### 4.2 本阶段不纳入范围

- 独立全宽协作工作台
- 主会话之外的第二审批流
- 跨会话的全局协作看板
- 新的后端编排语义重构
- 深度协议控制台 / 调试台

## 5. 用户结果

当用户打开当前会话的协作概览抽屉时，应该能够快速回答这些问题：

- 当前协作目标是什么？
- 现在进行到哪个阶段？
- 哪些 Agent 正在活跃？
- 哪些地方卡住了？
- 哪些地方需要我关注或介入？

用户不应该必须先通读整段聊天历史，才能知道当前协作状态。

## 6. 抽屉结构

这个抽屉建议由三块组成：

```text
协作概览
  - 任务概览
  - Agent 活动
  - 待处理事项
```

整体感受应当：

- 比独立工作台轻很多
- 比当前消息混合展示更有结构

### 6.1 任务概览

这一块提供当前协作的宏观结构。

建议展示：

- 当前目标
- 当前阶段
- 顶层 workflow 状态
- 当前协作是运行中、阻塞中、失败中还是已完成
- 如果已有 workflow step 状态，则展示一份紧凑的步骤概览或进度摘要

这不是完整项目管理面板，而是当前会话下的简洁协作地图。

### 6.2 Agent 活动

这一块把已经设计好的 `Agent Activity` 纳入更大的协作抽屉中，作为其中一个模块存在。

建议展示：

- 当前 / 最近活跃的 Agent
- 运行中 / 已加入 / 失败 / 完成 等状态
- 紧凑的活动列表
- 可选的分发上下文
- 可选的处理轨迹
- 可选的技术详情

这一块仍然保持当前会话范围，且以“状态可读性”为主，不变成协议页。

### 6.3 待处理事项

这一块回答：

> 当前有哪些地方值得用户注意或需要用户介入？

建议展示：

- 被阻塞的 workflow gate
- 待批准的 wake approval
- 待验收的 KSTAR review
- 待处理的 patch candidate
- 失败且需要 follow-up 的步骤

这块的关键点是：

**它负责提示和定位，不负责真正执行审批。**

第一版里，这些项的动作应该以“带用户回到主会话对应位置”为主，而不是在抽屉里再做一套完整审批系统。

## 7. 审批边界

审批仍然留在主会话。

这是第一版必须明确写死的规则。

抽屉可以展示：

- 有什么需要审批
- 这是什么类型的审批
- 为什么它重要
- 它在主会话中对应哪里

但抽屉在这一版**不应该成为第二套审批系统**。

这样可以避免：

- 两个审批入口并存
- 用户不知道到底该在哪点确认
- 抽屉与主会话状态发生偏离

## 8. 信息架构原则

这个抽屉是当前会话状态的**结构化投影**，不是新的事实源。

推荐优先级：

1. collaboration runtime / workflow state
2. runtime status
3. 当前会话 message / process evidence
4. 现有 KSTAR / wake / patch-candidate 数据
5. renderer 侧的派生摘要

任何无法高置信度重建的信息，都应该缺省或优雅降级，而不是猜出来。

## 9. 数据来源

这一版优先复用现有数据，不新增独立持久化域。

主要数据来源：

- `groupChat.runtimeStatus`
- 现有 group-chat collaboration snapshot
- 当前会话已加载的 conversation history
- 已暴露在系统中的 wake request / KSTAR / patch candidate 数据
- 当前会话成员 / actor roster

这个抽屉应当从这些来源组合出一个 view model，而不是创造第二份并行状态。

## 10. 交互与体验要求

这个抽屉应该：

- 打开足够快
- 足够轻，不打断主会话工作流
- 让用户感觉“主会话还是主场”
- 在需要时帮助用户理解协作状态，而不是强迫切换模式

它不应该给用户造成“进入了另一个复杂系统”的感觉。

推荐的体验特征：

- 紧凑的头部
- 分块清晰的概览结构
- 低摩擦的折叠 / 展开
- 明确的空状态
- 明确的 blocked / attention 状态

## 11. 错误处理

抽屉需要处理这些情况：

- 当前没有选中会话
- collaboration 状态不可用
- runtime 状态不可用
- 当前没有活跃协作
- 当前没有待处理事项
- 某些 section 可用、某些 section 不可用的部分失败状态

应当做到**分区降级**，而不是整个抽屉一旦有一块失败就整体瘫掉。

## 12. 集成策略

这一版不应该推翻已经完成的 `Agent Activity` 工作。

推荐实现方向：

- 保持 `Agent Activity` 的逻辑模块化
- 把它挂进更高一层的协作概览抽屉
- 让它成为抽屉中的一个 section
- 在它的上方和下方增加协作概览相关模块

这样既不浪费现有成果，也能提升整体信息架构。

## 13. 非目标与陷阱

- 不要在这一版做全宽独立工作台
- 不要把审批从主会话迁出去
- 不要创造第二套协作状态机
- 不要把抽屉做成协议调试控制台
- 不要把所有可能的协作信息一股脑塞进抽屉
- 不要让用户在“主会话”和“抽屉”之间产生两个主界面的错觉

## 14. 成功标准

- 用户不需要先读完整段会话，就能理解当前多 Agent 协作状态
- 抽屉能清楚展示当前目标、活跃 Agent、阻塞点和待关注项
- 抽屉补充主会话，而不是和主会话竞争主导权
- 审批和介入动作仍然清晰地回到主会话完成
- `Agent Activity` 成为更大协作概览里的一个一致模块
