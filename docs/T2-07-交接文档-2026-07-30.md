### 2. OpenCode CLI 环境搭建（真实踩坑）
本机原本没装 OpenCode CLI。安装过程踩了两个坑：
- `npm i -g opencode-ai@latest` 装的是个空壳包，真正的二进制要靠它自己的 `postinstall.mjs` 去下载平台专属包（`opencode-darwin-arm64`）。
- 全局 npm 安装的两个包互相不在依赖树里，`postinstall.mjs` 用 `require.resolve` 找不到平台包，报错"package manager 装错了"。
- 解决：手动 `npm i -g opencode-darwin-arm64@1.18.9`，再手动把二进制 `cp` 到 `opencode-ai/bin/opencode.exe`，再手动建软链接 `/opt/homebrew/bin/opencode`。
- 最终版本：`opencode-ai@1.18.9`，已登录 DeepSeek（`~/.local/share/opencode/auth.json`）。

四项逐一结果：

1. **Context 注入 — ✓ 通过**（修复 bug 之后）
   - 方法：往工作目录放一个含随机 token 的 `probe.txt`，让 OpenCode 读出来。
   - **中途发现真实 bug**：OpenCode 1.18.x 不继承 `child_process.spawn` 传的 `cwd`，必须显式加 `--dir` 参数，否则文件工具（read/write/glob）解析到错误目录（观察到的是 Mate Agent 自己的项目目录 `/Users/wu.j.y/Desktop/Mate-Agent/`，不是我们指定的目录）。
   - 修复：`src/main/features/local_agents/backends/opencode.ts` 的 `buildOpencodeArgs` 加了 `if (opts.cwd) args.push('--dir', opts.cwd);`。
   - 修复后重跑，探针 token 原样出现在输出里，验证通过。
   - Evidence: `/tmp/t2-07-opencode-verify/context-injection.jsonl`

2. **结果回收 — ✓ 通过**
   - 方法：让它创建一个 JSON 文件，检查磁盘上文件是否真实存在、内容对不对，以及我们的事件流（`tool-event`/`file-change`）是否真实捕捉到。
   - Evidence: `/tmp/t2-07-opencode-verify/result-recovery.jsonl`，`/tmp/t2-07-opencode-verify/workdir/result2.json`

3. **权限 — ✗ 真实负面结论（本次 Spike 最重要的发现）**
   - 方法：让它执行 `rm -f xxx` 这种破坏性 shell 命令，观察是否有确认/拦截。
   - 结果：**完全没有任何人机确认机制**。加不加 `--dangerously-skip-permissions`（这个 flag 在当前版本 `opencode run --help` 里已经不存在了，是过期参数，被 CLI 静默忽略）都一样——`bash` 工具直接无阻拦执行。
   - 对比：codex/claude/hermes 三个后端已经接了 `bridge_permissions.ts` 的人机确认闸门（fail-closed，超时默认 deny）；opencode 后端目前完全没有接入这层，因为它压根没有走 bridge/MCP 调用路径（`opencode.ts` 里没有任何 mcp/connector/bridge 相关代码）。
   - 这是一个需要在生产化前解决的真实风险，不是"待补充"这么轻描淡写。

4. **可复现性 — ✓ 通过**
   - 方法：同一个 prompt+cwd 跑两次，对比工具调用序列是否一致。
   - Evidence: `/tmp/t2-07-opencode-verify/reproducibility-run-a.jsonl` / `-run-b.jsonl`

### 4. Spike 结论

**Conditional**——OpenCode 可以作为本地 Task Agent 使用（Context/结果回收/可复现性三项扎实），但权限维度是真实缺口，接入生产使用前必须补上确认闸门（参照 codex/claude/hermes 已有模式）。
