# 侧边追问栏（Ask Aside）实施规划

| 项 | 值 |
|---|---|
| 目标 | 在不污染主线的前提下，就主对话内容追问并获得解释 |
| 定位 | 只读旁听问答，非第二条执行链路 |
| 成文日期 | 2026-08-05 |

---

## 1. 问题与定位

用户在任务对话中拿到一个方案但没看懂。当前只有两个选择，都不好：

- 在主对话追问 → 打断主线、污染任务上下文
- 换一个对话问 → 没有上下文，得手动复述

侧边追问栏解决这个：**能看到主对话上下文，但问答不进主对话历史。**

关键约束：它是"解释器"，不是第二个干活的 Agent。

---

## 2. 已确认的设计决定

| # | 决定 |
|---|---|
| 1 | 问答**不进**主对话历史 |
| 2 | 上下文 = 用户选中的那条消息 + 前 5 后 2 |
| 3 | 侧栏常驻，通过展开按钮开合 |
| 4 | 固定一个解释 Agent，只借其模型与系统提示词 |
| 5 | **只读** —— 不能改文件、不能跑命令、不能写记忆 |
| 6 | 问答记录跟随会话持久化 |

---

## 3. 关键约束：必须绕开群聊总线

主对话发送走 `conversations.sendStream` → `groupChat.send` → `bus.ts`。侧栏**不能复用这条链路**，原因有两条且都是硬性的：

1. 进总线就会写入主消息文件，直接违反决定 1
2. AGENTS.md 明确规定群聊调度只有 `bus.ts::enqueue` 一条路径，禁止并行路径

因此侧栏需要一条独立的轻量问答通道，直接调 `model/client.ts::streamChatWithModel`，绕过总线。

这与决定 5（只读）天然契合：不进总线 → 没有工具调用、没有调度、没有并发写入。**只读不是靠检查实现的，是靠不接入实现的。**

---

## 4. 数据模型

### 4.1 存储

```
<uid>/local/conversations/<cid>/aside.jsonl
```

- 一会话一文件，append-only，与主消息文件**物理隔离**
- 放 `local/` 而非 `cloud/`：追问是理解过程而非交付物，不需要跨设备同步（若后续要同步，迁移成本仅为改路径）
- 主对话删除时一并清理

### 4.2 记录结构

```ts
export interface AsideTurn {
  turnId: string;
  /** Anchor: which main-conversation message triggered this thread. */
  anchorIndex: number;
  /** Snapshot of the anchor text, so the thread stays readable even if the
   *  main conversation is later trimmed or the anchor scrolls out of range. */
  anchorExcerpt: string;
  question: string;
  answer: string;
  /** Which agent's model answered — recorded for auditability. */
  agentId: string;
  model: string;
  createdAt: string;
}
```

`anchorExcerpt` 是刻意的冗余：不存快照的话，主对话分页加载后侧栏历史会失去指向。

---

## 5. 上下文构造

### 5.1 窗口

选中第 N 条 → 取 `[N-5, N+2]`，共 8 条。

前 5 后 2 的理由：用户没看懂的是**已经读到的内容**，之前的铺垫是理解所需，之后的内容他还没看到，带太多等于剧透且浪费 token。

### 5.2 复用既有读取

```
chats.getMessagesPageAtIndex(userId, cid, anchorIndex, limit, projectId)
```

`conversations.history` 已经支持 `around_index` 参数走这条路，侧栏直接复用，不新写读取逻辑。

### 5.3 注入形态

```
[主对话上下文 · 只读]
<8 条消息，含角色标注>

[用户选中的内容]
<anchor 消息全文>

[用户的问题]
<question>
```

系统提示词明确三件事：只解释不执行、不臆造上下文外的信息、不知道就说不知道。

### 5.4 同一线程内的追问

侧栏支持连续追问。第二轮起把本线程的历史问答也带上（上限 6 轮，超出丢弃最早的），但**主对话上下文只取一次**，不随每轮重复注入。

---

## 6. 解释 Agent 的选择

固定一个解释 Agent，按以下顺序解析：

1. 会话绑定的 `conv.agent_id`（若存在且已启用）
2. 群聊场景：最后发言的 agent
3. 都没有：默认模型配置

只取该 Agent 的**模型配置 + 人格提示词**，不加载其技能、工具、记忆写入能力（决定 4A）。

风格一致，但它不是"那个 agent 在替你干活"，而是"用同样的模型解释刚才那段"。

---

## 7. 交互

### 7.1 入口

消息气泡已有溢出菜单（`chat-bubble-more-menu`，含复制/选择/归档）。在其中**追加一项「追问」**，不新造入口。

点击后：侧栏展开 → 以该条为 anchor 起一个新线程 → 输入框聚焦。

### 7.2 侧栏本体

参考 `chat-md-drawer` 的抽屉模式（已有 CSS 与开合逻辑可循）：

```
┌─ 追问 ────────────────── [收起] ┐
│ 关于：<anchorExcerpt 截断>       │
│ ──────────────────────────────  │
│ Q: 这个方案为什么要先冻结？      │
│ A: 因为……                        │
│ ──────────────────────────────  │
│ [输入框]                 [发送]  │
└─────────────────────────────────┘
```

- 常驻但默认收起，展开按钮在对话区右上
- 切换会话时重新加载该会话的 aside 记录
- 流式输出，复用现有 SSE 渲染

### 7.3 明确的视觉边界

侧栏需要与主对话在视觉上明显区分（不同底色 + "只读解释"标识），避免用户误以为在这里说的话会影响任务。

---

## 8. IPC

```
aside.list      { cid }                      → { turns }
aside.askStream { cid, anchorIndex, question } → 流式 answer
aside.clear     { cid }                      → 清空该会话追问记录
```

`askStream` 走 `streamHandlers`（与 `conversations.sendStream` 同机制但独立通道）。

参数校验在 IPC 层：`cid` 走 `safeId`、`anchorIndex` 为非负整数、`question` 非空且长度上限。

---

## 9. 分层与落位

| 文件 | 职责 |
|---|---|
| `features/conversation_aside.ts` | 存储读写、上下文构造、模型调用 |
| `ipc/index.ts` | 参数校验 + 转调（不含业务逻辑） |
| `renderer/modules/chat-aside.js` | 侧栏 UI，纯渲染 + 事件 |
| `renderer/modules/conversation.js` | 溢出菜单追加「追问」一项 |
| `locales/{zh,en,ja,pt}.json` | 文案 |

`features/conversation_aside.ts` 只依赖 `chats`（读消息）与 `model/client`（调模型），不反向依赖任何 UI。

---

## 10. 测试

- 追问记录**不出现**在主消息文件中（核心不变量，必须有测试）
- 上下文窗口边界：anchor 为第 0 条、最后一条、越界索引
- `anchorExcerpt` 在主对话分页后仍可读
- 线程内多轮追问的历史裁剪（超 6 轮丢最早）
- 解释 Agent 解析的三级回退
- 会话删除时 aside 文件一并清理
- 侧栏渲染转义（问题/回答含 HTML）
- 参数校验：非法 cid / 负索引 / 空问题

---

## 11. 硬性禁止

- 侧栏问答写入主消息文件
- 侧栏接入 `bus.ts` / `groupChat.send`
- 给侧栏任何工具调用、文件写入、记忆写入能力
- 在 IPC handler 内写业务逻辑
- 每轮追问都重新注入主对话上下文（只注入一次）
- 主对话上下文无上限注入（固定 8 条窗口）
