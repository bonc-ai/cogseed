## 1. 文档目的

本文完整说明 CogSeed 当前认知资产链路，从一次会话如何被判断为完成开始，一直到内容被提取、筛选、审核、写入正式资产、在后续会话中被检索和注入、记录使用反馈、形成验证证明，以及可复用方法如何转化为 Skill。

本文可用于：

- 产品演示：解释“数据从哪里来、现在到哪一步、下一步该做什么”。
- 产品设计：明确哪些对象需要用户确认，哪些步骤可以自动完成。
- 研发联调：核对状态、字段、IPC、存储位置、幂等和恢复策略。
- 测试验收：覆盖正常链路、失败链路、来源撤权、重复操作和应用重启。
- 后续迭代：识别当前已实现能力与仍需补齐的边界。

## 2. 一页看懂完整链路

```text
用户与 Agent 会话
  -> Group Chat 判断本轮任务终态
  -> 仅 completed 进入自动沉淀
  -> 内部静默观察，不立即显示任务
  -> 会话空闲检查 + 新消息检查
  -> 第一层价值预筛选
  -> 创建 RecallView 来源快照
  -> 模型提取最多 3 个候选
  -> 第二层确定性质量校验
  -> 合格候选进入 pending_review
  -> 用户保存 / 修改后保存 / 稍后 / 拒绝 / 忽略 / 保持当前版本
  -> 确认时写入 ReviewDecision
  -> 创建、更新、缩小范围或暂停正式认知资产
  -> 写入资产交接回执、版本记录和审计记录
  -> 新会话按语义相关度检索正式资产
  -> 生成 ContextProjection 并注入系统提示词
  -> 成功回答展示引用并写入 UsageRecord
  -> 任务终态形成 TransferProof
  -> 用户反馈形成 EffectivenessProof
  -> 资产成熟度逐步升级
  -> skill_method 资产自动生成 Skill 草稿
  -> 用户点击“加入技能库”后成为自定义 Skill
```

链路的核心原则是：

1. **会话完成不等于值得沉淀。** 完成后还要经过静默观察和价值筛选。
2. **模型提取不等于正式资产。** 模型只能生成候选，不能直接替用户写入长期资产。
3. **用户确认不等于已验证有效。** 新资产初始为 `User Confirmed / Unverified` 和 `seed`。
4. **召回不等于全部注入。** 只注入当前任务相关、状态有效、来源仍可用的资产。
5. **使用不等于有效。** 使用记录、迁移成功和效果更好是三个不同层次的证据。
6. **生成 Skill 不等于发布 Skill。** 系统先生成并校验草稿，用户确认后才进入本地技能库，且仍是 staged 状态。

## 3. 总体架构与责任边界

### 3.1 运行架构

CogSeed 是单进程 Electron 应用：

- Renderer：原生 HTML、CSS、JavaScript，负责认知资产页面和用户操作。
- Main：Node 后端，负责会话终态、沉淀调度、模型调用、候选和资产持久化。
- IPC：Renderer 只能通过 `window.cogseed.invoke(...)` 调用 Main。
- 数据存储：以用户为根目录的 JSON / JSONL 文件；认知资产数据位于用户 cloud 数据域。
- 模型调用：通过进程内 `core-agent`，沉淀和 Skill 生成均禁用工具并使用临时会话。

### 3.2 主要模块

| 模块 | 主要职责 |
| --- | --- |
| `group_chat/bus.ts` | 判断会话运行终态、会话是否真正空闲、发出 `TaskTerminalEvent`；在新回合注入 Recall 上下文 |
| `recall/capture-service.ts` | 创建沉淀任务、静默调度、价值预筛、模型提取、候选保存、失败恢复 |
| `recall/capture-value-screening.ts` | 会话价值预筛和候选确定性质量校验 |
| `recall/recall-view-service.ts` | 创建有界、可追踪、可过期的来源快照 |
| `recall/candidate-service.ts` | 候选字段、去重、状态决策、确认和正式资产交接 |
| `cognition/review-decision.ts` | 追加式保存用户审核决定和资产写入结果 |
| `recall/asset-service.ts` | 正式资产创建、更新、暂停、恢复、撤销、版本与审计 |
| `recall/source-*` | 来源目录、状态、暂停、恢复、移除与影响预览 |
| `recall/context-projection.ts` | 选择本次任务要使用的资产，生成 ContextProjection |
| `recall/prompt-injection.ts` | 将确认资产安全地构造成系统提示词上下文和引用信息 |
| `recall/usage-*` | 记录实际引用和用户“有帮助/需改进”反馈 |
| `recall/proof-service.ts` | TransferProof、EffectivenessProof 和成熟度升级 |
| `recall/skill-draft-service.ts` | 从 `skill_method` 资产生成、校验和安装 Skill 草稿 |
| `recall/tree-service.ts` | 从来源、候选、资产和使用记录重建派生认知树快照 |
| `renderer/modules/skills*.js` | “认知资产”四个页面及用户交互 |

### 3.3 当前两套并行对象

项目中仍存在两套认知对象体系，必须区分：

1. **当前主链路：Recall 正式资产链路**
   - 数据对象：Capture、RecallView、RecallCandidate、ReviewDecision、AbilityAsset、Projection、Proof、SkillDraft。
   - 当前“认知资产”页面的主数据和后续会话注入都来自这条链路。

2. **兼容链路：较早的 Cognition / Personal Ontology 链路**
   - 数据对象：`personal_ontology_candidates`、Personal Ontology groups、早期 cognition receipt。
   - 仍保留部分 IPC、适配器和兼容展示。
   - `cognition.assets.list` 会聚合 Recall 正式资产和 Personal Ontology groups。

这两条链路当前不是完全统一的同一存储。新的 `personal` 资产会显示在“关于我”分类，但不会自动把内容拆分并回填到旧个人本体的身份、角色等字段。

## 4. 核心对象字典

| 对象 | 作用 | 何时创建 | 是否需要用户确认 |
| --- | --- | --- | --- |
| `TaskTerminalEvent` | 描述一次会话运行的终态 | Group Chat 全部工作静止后 | 否 |
| `RecallCapture` | 一次可恢复的沉淀任务 | completed 后自动创建，或用户手动创建 | 任务本身不需要 |
| `RecallView` | 本次提取可用的来源快照 | 模型提取前 | 否 |
| `RecallCandidate` | 尚未成为长期资产的认知候选 | 模型提取或用户教学信号产生 | 是 |
| `ReviewDecision` | 用户对候选的不可变审核记录 | 保存、稍后、拒绝、忽略等动作时 | 由用户动作产生 |
| `AbilityAsset` | 可在后续任务中复用的正式认知资产 | 候选确认并成功交接后 | 是 |
| `AssetHandoffReceipt` | 证明候选已真实写入哪个资产 | 资产创建或更新成功后 | 否 |
| `ContextProjection` | 某次任务实际选择使用的资产集合 | 新对话自动检索或用户手动预览时 | 自动路径不需要；手动预览需要 |
| `UsageRecord` | 某资产在某回答中实际被引用的记录 | 成功回答落盘后 | 否 |
| `TransferProof` | 资产是否成功迁移到另一次任务 | 带投影的任务达到终态时 | 否 |
| `EffectivenessProof` | 迁移后效果是否更好 | 用户或系统提交效果评价时 | 用户反馈路径需要 |
| `RecallSkillDraft` | 由方法类资产形成的 Skill 草稿 | `skill_method` 资产确认后自动准备 | 安装前需要 |
| `CognitionTree` | 来源到候选、资产、使用的派生关系快照 | 显式 rebuild 时 | 否 |

## 5. 阶段一：如何判断一轮会话结束

### 5.1 终态不是“用户停止输入”

系统不通过简单计时猜测任务完成，而是由 Group Chat 运行时形成 `TaskTerminalEvent`。事件只有在以下条件同时满足时发出：

- 当前会话没有正在运行的 worker。
- 所有 worker 队列均为空。
- 没有正在进行的 `enqueue()`。
- 本轮已经得到一个终态分类。

`isQuiescent(userId, conversationId)` 是会话真正空闲的运行时判断。它避免在 Agent 之间转交任务的短暂空隙中误判会话完成。

### 5.2 四种会话终态

| 终态 | 判断依据 | 对自动沉淀的影响 |
| --- | --- | --- |
| `completed` | 没有中止、没有开放表单/计划交互、没有运行错误 | 创建或更新自动沉淀任务 |
| `waiting_input` | 存在表单、开放的计划交互或明确等待用户输入 | 不创建新自动任务；已有任务转为 `waiting_completion` |
| `failed` | 模型/运行错误、Actor failure、持久化失败消息 | 不创建新自动任务；已有任务转为 `waiting_manual` 并记录原因 |
| `cancelled` | 用户中止或会话状态为 aborted | 不创建新自动任务；已有任务转为 `waiting_manual` 并记录原因 |

### 5.3 `completed` 的实际定义

当前实现中，一次 Actor 回合满足以下条件时被分类为 `completed`：

- 未被中止；
- 没有输出需要用户继续填写的表单；
- 没有开放的 `plan-interaction`；
- Actor 没有显式要求 `waiting_input`；
- 没有模型错误或运行失败；
- 持久化结果不是 failure。

多个顶层接收者属于同一用户触发运行时，系统会保留更需要处理的状态，优先级为：`cancelled` > `waiting_input` > `failed` > `completed`。

### 5.4 事件携带的信息

`TaskTerminalEvent` 只携带运行和边界信息，不携带对话正文：

- `run_id`
- `user_id`
- `conversation_id`
- `status`
- `started_at_ms`
- `finished_at_ms`
- `anchor_message_id`：启动本轮的第一条用户消息
- `finished_message_id`：本轮静止时最后一条持久化消息
- 可选的 `logical_run_id`、`execution_id`、`projection_id`、`wake_request_id`

这样既能建立可追踪边界，也避免把对话内容广播给系统监听器。

## 6. 阶段二：创建沉淀任务

### 6.1 默认设置

| 设置 | 默认值 | 含义 |
| --- | --- | --- |
| `enabled` | `true` | 开启会话沉淀 |
| `executionPolicy` | `smart` | 完成后先等待静默期 |
| `reviewPolicy` | `auto` | 自动整理候选，但不自动写正式资产 |
| `quietMinutes` | `10` | 静默等待 10 分钟 |
| `nightlyStart` | `02:00` | 夜间窗口开始 |
| `nightlyEnd` | `06:00` | 夜间窗口结束 |
| `catchUpMissed` | `true` | 错过夜间窗口后允许空闲补跑 |

静默分钟可配置范围为 1 到 120 分钟。

### 6.2 三种执行策略

| 策略 | 初始状态 | 是否立即显示 | 执行方式 |
| --- | --- | --- | --- |
| `smart` | `waiting_quiet` | 否，保持 `internal` | 静默结束且会话空闲后执行 |
| `nightly` | `scheduled` | 否，保持 `internal` | 静默结束后进入最近夜间窗口 |
| `manual` | `waiting_manual` | 是 | 用户点击“立即执行” |

旧值 `immediate` 会被兼容转换为 `smart`，当前不再代表真正的无静默立即自动执行。

### 6.3 自动任务为什么一开始看不到

自动任务初始写入时：

- `visibility = internal`
- `screeningStatus = pending`

认知资产页面只列出 `visibility = visible` 的任务。因此，静默期和价值预筛之前的内部观察不会制造用户待办，也不会让普通问候立即出现在“沉淀任务”列表。

### 6.4 会话范围与消息边界

一次提取最多使用：

- 2,000 条历史消息用于查找边界；
- 实际选中最多 32 条消息；
- 总文本约 22,000 字符；
- 第一条用户消息和最后一条消息优先保留；
- 系统消息、分发消息、失败消息、删除消息和空文本不参与；
- 选中内容必须从用户消息开始；
- 自动任务最后一条必须是助手回复。

### 6.5 合并与防重复

同一会话在仍处于以下状态时，会继续合并到已有自动任务：

- `waiting_quiet`
- `waiting_completion`
- `waiting_manual`
- `scheduled`
- `paused`

任务 ID 根据 `conversationId + anchorMessageId` 生成稳定哈希。同一终态事件和相同消息集合不会重复创建任务。

### 6.6 手动选择历史会话

用户可以在“沉淀任务”页面选择历史会话并点击“立即沉淀”：

- 系统选择从首条用户消息到最后一条助手消息的完整可用范围；
- 如果已有任务覆盖最后一条消息，复用现有任务并将其改为可见；
- 手动任务直接标记 `qualified`，使用 `manual_selection` 信号；
- 手动任务绕过第一层自动价值预筛，但仍需要模型提取、候选质量校验和用户确认。

## 7. 阶段三：静默观察与重新调度

静默结束后，任务不会直接调用模型，而是先再次确认会话状态。

### 7.1 空闲检查

调度器检查：

1. 当前会话是否 `isQuiescent`。
2. 原消息集合之后是否出现新消息。
3. 最新消息是否为助手回复。
4. 当前任务的计划时间是否真正到达。

### 7.2 用户继续对话时

如果静默期间出现新消息：

- 重新计算从原 anchor 到最新消息的范围；
- 如果最后一条仍是用户消息，状态进入 `waiting_completion`；
- 每 60 秒重新检查；
- 当助手完成回复后，更新消息集合；
- 清空旧 RecallView 和候选引用；
- 重新计算新的静默截止时间或夜间计划时间。

这解决了旧实现中 `waiting_completion` 无法重新调度的问题。

### 7.3 夜间策略

夜间任务必须同时满足静默结束和夜间窗口。如果执行时已经错过窗口：

- `catchUpMissed = true`：可以立即补跑；
- `catchUpMissed = false`：推迟到下一个夜间窗口。

## 8. 阶段四：第一层价值预筛选

第一层筛选完全由确定性代码完成，在模型调用之前执行，目标是避免低价值会话消耗模型并打扰用户。

### 8.1 直接过滤的内容

- 问候，例如“你好”“hello”。
- 感谢，例如“谢谢”“辛苦了”。
- 简单确认，例如“好”“收到”“OK”“同意”。
- 状态查询，例如“到哪阶段了”“完成了吗”。
- 没有用户消息或没有助手消息的对话。
- 最终结果明确失败，且没有产物或可复用完成结果的对话。
- 内容过短，且没有任何复用价值信号的对话。

### 8.2 可识别的价值信号

| 信号 | 典型内容 |
| --- | --- |
| `preference` | 用户偏好、习惯、希望以后如何处理 |
| `rule` | 必须、不要、默认、约束、原则 |
| `decision` | 决定采用、最终选择、批准的方案 |
| `template` | 模板、固定格式、字段、清单、范例 |
| `method` | 流程、步骤、工作流、排查顺序、校验方法 |
| `artifact` | 会话产生了可追踪 Artifact |
| `reusable_outcome` | 已完成、已实现、已修复、已验证的结果 |
| `substantive_exchange` | 没有显式关键词，但对话长度和内容足够实质 |
| `manual_selection` | 用户主动选择历史会话沉淀 |

### 8.3 实质性长对话阈值

没有显式信号时，满足以下任一条件仍可进入模型提取：

- 非琐碎用户内容至少约 48 个有效字符，全部内容至少约 140 个有效字符；
- 至少 2 条非琐碎用户消息，用户内容至少约 36 个有效字符，全部内容至少约 110 个有效字符。

### 8.4 筛选结果

- 合格：`screeningStatus = qualified`，继续构建 RecallView。
- 不合格：任务变为 `no_candidate`、保持 `internal`，用户列表中不显示。
- 来源无法读取：任务变为 `failed`、保持 `internal`，错误为 `source_unavailable`。

## 9. 阶段五：构建 RecallView

RecallView 是“本次提取允许看到哪些来源”的有界快照，不是长期资产。

### 9.1 会话沉淀 RecallView 包含

- 会话 session 引用；
- 本次选中消息的 message 引用；
- 消息中的 Artifact 引用；
- 同一会话最近的执行与评价来源；
- 与本次消息关联的有效用户教学信号；
- 会话所属 workspace/project 标识；
- 降级来源列表；
- 30 天有效期。

### 9.2 RecallView 不保存什么

- 不复制完整原文到来源引用；
- 不持久化绝对路径；
- 不持久化 token、密码、cookie 等秘密；
- 不把所有用户数据无界聚合到一个提示词中。

### 9.3 复用与重建

已有 RecallView 只有在以下条件满足时才复用：

- 尚未过期；
- `purpose = conversation_capture`；
- workspace 未变化；
- 有效用户教学信号集合未变化。

否则系统使用持久化的消息 ID 重建新的 RecallView。

## 10. 阶段六：模型提取认知候选

### 10.1 模型运行方式

- 使用配置的默认模型；
- 模型未配置时进入 `configuration_required`；
- OAuth 授权失效时进入 `configuration_required`；
- 使用临时 session，不保留模型会话；
- 禁用工具；
- 不加载 Skill；
- `thinkingLevel = off`；
- `cacheRetention = none`。

### 10.2 模型输出约束

模型必须返回严格 JSON，最多 3 个候选：

```json
{
  "candidates": [
    {
      "judgment": "需要长期保留的认知内容",
      "value": "未来如何减少重复工作或风险",
      "summary": "短标题",
      "suggestedType": "personal | rule | template | skill_method",
      "suggestedScope": "作用范围",
      "suggestedAction": "create | update | limit_scope | pause | keep_current | reject",
      "targetAssetId": "非 create 动作必填",
      "risk": "low | medium | high",
      "evidence": ["m1"],
      "uncertainty": "可选"
    }
  ]
}
```

每个候选必须：

- 表达可复用的偏好、约束、决定、模板或方法；
- 说明未来价值，而不是重复标题；
- 明确建议动作；
- 至少引用一条有效消息标签；
- 至少引用一条用户消息作为证据；
- 使用与会话相同的语言；
- 不得虚构事实。

没有值得保留的内容时必须返回 `{"candidates":[]}`。

## 11. 阶段七：第二层候选质量校验

模型输出不会直接制造用户待办。每个候选还要经过确定性质量校验。

### 11.1 质量校验项

| 校验失败原因 | 含义 |
| --- | --- |
| `missing_value` | 未说明未来价值，或价值说明过短 |
| `missing_action` | 未提供明确建议动作 |
| `missing_target` | 更新、缩小范围或暂停却没有目标资产 |
| `missing_user_evidence` | 没有任何用户消息证据 |
| `candidate_too_short` | 判断或摘要过短 |
| `value_not_explanatory` | 价值只是重复判断或摘要 |
| `candidate_not_reusable` | 没有复用信号、没有 Artifact 且整体内容过短 |

### 11.2 校验结果

- 通过：候选可进入 `pending_review`，沉淀任务变为可见的 `review_ready`。
- 不通过：候选保存为 `weak_observation`，不进入沉淀任务的待审核列表。
- 模型返回候选但全部不合格：任务为 `no_candidate`，过滤原因 `candidate_quality`。
- 模型返回空数组：任务为 `no_candidate`，过滤原因 `model_no_candidate`。

弱观察保留证据，未来出现新 Evidence 或风险变化时可以重新打开，但不会立刻打扰用户。

## 12. 阶段八：RecallCandidate 及其状态机

### 12.1 核心字段

| 字段 | 作用 |
| --- | --- |
| `id` | 稳定候选 ID |
| `status` | 候选当前状态 |
| `judgment` | 要保留的认知内容 |
| `value` | 为什么未来有价值 |
| `summary` | 简短标题 |
| `uncertainty` | 不确定性说明 |
| `suggestedType` | 建议资产类型 |
| `suggestedScope` | 建议作用范围 |
| `sourceRefs` | 来源引用 |
| `evidenceRefs` | 直接证据引用 |
| `suggestedAction` | 创建、更新、缩小范围、暂停等动作 |
| `risk` | 低、中、高风险 |
| `targetAssetId` | 非 create 动作的目标资产 |
| `taskRunId` | 来源任务运行 ID |
| `captureKey` | 自动提取幂等键 |
| `expiresAt` | 候选有效期，默认 90 天 |
| `cooldownUntil` | 稍后处理冷却期，默认 7 天 |
| `promotedAssetId` | 成功确认后的正式资产 ID |
| `reviewDecisionId` | 对应审核决定 ID |
| `failureCode` / `failureMessage` | 入库失败原因 |

### 12.2 状态机

| 状态 | 业务含义 | 用户可执行动作 |
| --- | --- | --- |
| `observed` | 已观察但尚未形成完整候选 | 无正式审核动作 |
| `weak_observation` | 证据或内容不足，内部保留 | 等待新证据 |
| `pending_review` | 已满足审核条件 | 保存、编辑、稍后、拒绝、忽略、保持当前版本 |
| `deferred` | 用户选择稍后处理 | 冷却期后自动视为可审核，或手动恢复 |
| `confirmed` | 已成功交接正式资产 | 查看资产 |
| `rejected` | 用户明确拒绝 | 终态，不入库 |
| `ignored` | 用户忽略或保持当前版本 | 终态，不入库 |
| `expired` | 超过有效期 | 终态，不入库 |
| `failed` | 来源或资产写入失败 | 保留候选，可修复后重试 |

### 12.3 去重策略

候选指纹由以下字段组成：

- `judgment`
- `value`
- `suggestedType`
- `suggestedScope`
- `suggestedAction`
- `targetAssetId`

完全相同的候选不会重复创建：

- 新来源会合并到 `sourceRefs` 和 `evidenceRefs`；
- 风险只会取更高值；
- 弱观察、稍后或失败候选在出现新证据或更高风险时可以重新打开；
- 已拒绝、忽略、过期的候选只有出现实质新证据或风险变化时才可能重新形成新待办；
- 已确认候选不会因相同内容再次创建资产。

自动提取还使用 `captureKey = capture-{captureId}-{index}` 生成稳定候选 ID，重复运行不会重复落候选。

## 13. 阶段九：用户轻量确认

### 13.1 用户动作

| 页面动作 | 候选结果 | 是否写正式资产 |
| --- | --- | --- |
| 保存 | `confirmed` | 是 |
| 修改后保存 | 更新候选后 `confirmed` | 是 |
| 稍后 | `deferred`，7 天冷却 | 否 |
| 拒绝 | `rejected` | 否 |
| 忽略 | `ignored` | 否 |
| 保持当前版本 | `ignored` | 否，不修改目标资产 |
| 高风险保存 | 需要用户额外确认风险 | 是 |

### 13.2 ReviewDecision

每次用户决策会写入追加式 ReviewDecision 账本，关键字段包括：

- `decision_id`
- `target_ref`
- `antecedent_ref`
- `decision_type`
- `decision`
- `scope`
- `reason`
- `modified_content`
- `idempotency_key`
- `asset_id`
- `outcome`
- `failure_code`
- `timestamp`

短确认语，例如“确认”“是”“OK”，必须绑定明确的 `antecedent_ref`，否则不能生效。

### 13.3 高风险候选

`risk = high` 的候选不能直接确认，调用方必须传入 `riskAcknowledged = true`。这是一道独立的用户风险确认，但当前实现仍是布尔确认，不是完整的高风险 Gate 工作流。

### 13.4 批量确认

批量操作只处理 `pending_review` 候选：

- 每个候选独立执行；
- 单项失败不阻断其他项；
- 返回 `succeeded[]` 和 `failed[]`；
- 当前批量确认路径不会自动调用 Capture 包装层的 Skill 草稿准备逻辑，这是需要注意的实现差异。

## 14. 阶段十：正式资产交接

### 14.1 确认前检查

候选正式入库前检查：

1. 操作者必须是用户。
2. 候选不是弱观察或 observed。
3. 候选没有过期。
4. 高风险候选已经单独确认。
5. 来源仍处于 active，未暂停、移除或撤权。
6. 至少存在可用 Evidence。
7. 非 create 动作必须有目标资产。
8. 目标资产类型必须与候选类型一致。
9. 内容不能包含禁止持久化的敏感信息。

### 14.2 支持的资产交接动作

| `suggestedAction` | 正式资产操作 |
| --- | --- |
| `create` | 创建新资产 |
| `update` | 更新目标资产内容并增加版本号 |
| `limit_scope` | 更新目标资产并缩小作用范围 |
| `pause` | 暂停目标资产 |
| `keep_current` | 不写资产，使用非资产决策路径 |
| `reject` | 不写资产，使用非资产决策路径 |

### 14.3 幂等设计

确认幂等键由候选 ID、内容、类型、范围、动作、目标资产和证据集合生成。系统进一步使用：

```text
asset_id = hash(candidate_id + review_decision_id)
```

保证：

- 重复点击不会创建第二个资产；
- 重试会找到同一 ReviewDecision；
- 同一决定再次写入只返回原资产；
- 更新目标资产时通过 `appliedReviewDecisionIds` 防止同一决定重复增加版本。

### 14.4 成功回执

资产写入成功后保存 `AssetHandoffReceipt`：

- `assetId`
- `assetType`
- `version`
- `lifecycleStatus`
- `scope`
- `sourceRefs`
- `reviewDecisionId`

只有回执、ReviewDecision outcome 和资产均成功后，候选才标记为 `confirmed`。

### 14.5 失败恢复

如果正式资产写入失败：

- ReviewDecision outcome 标记为 `asset_failed`；
- 候选保留为 `failed`；
- 保存 `asset_write_failed` 和失败消息；
- 页面恢复到待审核状态并提供重试；
- 不会出现“前端显示成功但资产没有落库”的正常成功路径。

## 15. 阶段十一：正式认知资产

### 15.1 四类正式资产

| 类型 | UI 分类 | 适合承载的内容 |
| --- | --- | --- |
| `personal` | 关于我 | 长期角色、稳定偏好、个人边界、身份相关信息 |
| `rule` | 规则与判断 | 决策原则、禁止项、默认约束、判断标准 |
| `template` | 模板与范例 | 固定结构、字段、清单、示例、输出格式 |
| `skill_method` | 可复用方法 | 多步骤流程、工具组合、验证方法、可迁移工作方式 |

### 15.2 初始治理状态

新建资产固定为：

- `status = active`
- `lifecycleStatus = user_confirmed_unverified`
- `maturity = seed`
- `version = 1`

用户确认只证明“这是用户同意保留的内容”，不证明该内容已经跨场景有效。

### 15.3 资产状态

| 状态 | 含义 | 是否参与自动召回 |
| --- | --- | --- |
| `active` | 正常使用 | 是 |
| `paused` | 暂停使用但保留记录 | 否 |
| `revoked` | 已撤销，不允许恢复或修改 | 否 |

### 15.4 资产成熟度

| 成熟度 | 含义 | 形成条件 |
| --- | --- | --- |
| `seed` | 用户已确认，尚未证明可迁移 | 资产创建时 |
| `bud` | 预留的中间成熟度 | 当前主流程没有自动升级规则 |
| `transfer_validated` | 已在另一次任务中成功迁移 | TransferProof 为 succeeded |
| `effectiveness_validated` | 有证据表明使用后效果更好 | EffectivenessProof outcome 为 better |

### 15.5 版本与审计

- 创建和内容更新会写版本快照；
- 更新会使整数版本号加 1；
- 暂停、恢复、撤销和系统建议写入审计日志；
- 撤销后的资产不能再次修改或恢复；
- 每个版本保留标题、正文、类型、范围、Evidence、状态、成熟度和 ontologyRefs。

### 15.6 “关于我”当前边界

当前新的 `personal` 资产已经能：

- 显示在“记忆内容 > 关于我”；
- 参与语义召回；
- 保留 Evidence、范围、版本和使用记录。

当前尚不能自动：

- 把一条个人资产识别为“身份 / 角色 / 专业背景 / 沟通偏好”等具体字段；
- 更新旧 Personal Ontology group；
- 合并同一身份字段的冲突版本；
- 在“关于我”中形成稳定的结构化个人画像。

因此，“个人画像沉淀”当前完成了长期资产层，尚未完成结构化身份模块的自动落点。

## 16. 阶段十二：数据来源治理

### 16.1 五类正式来源

| 来源类型 | 子类型 | 当前用途 |
| --- | --- | --- |
| `conversation` | `session`、`message` | 会话沉淀的主要正文来源 |
| `artifact_file` | `artifact`、`context_file` | 会话产物和上下文文件 |
| `execution_evaluation` | `execution`、`evaluation` | 执行过程和结果评价 |
| `user_teaching_signal` | `teaching` | 用户明确要求记住、偏好、避免或纠正的内容 |
| `authorized_external_system` | `connector_record` | 已授权外部连接器的目录状态 |

### 16.2 来源生命周期

页面生命周期状态：

- `pending`
- `processing`
- `ready`
- `failed`
- `paused`

治理可用性状态：

- `active`
- `paused`
- `removed`

### 16.3 来源操作

- 暂停：后续候选确认和自动召回不能使用该来源。
- 恢复：恢复来源可用性。
- 重试：目前主要用于失败的 context file 索引。
- 重新连接：用于恢复外部连接器。
- 删除前预览：显示会影响多少正式资产。
- 删除：可选择只删除来源，或同时撤销依赖该来源的资产。

### 16.4 来源撤权后的行为

- 新自动沉淀不会读取暂停或移除的会话来源；
- 正在排队的任务会转为 paused；
- 候选确认会失败并保留 `source_unavailable`；
- 自动投影会排除来源不可用的资产；
- 提示词注入前再次检查来源状态；
- 如果用户选择“同时撤销资产”，系统逐个撤销并返回部分失败清单。

### 16.5 当前接入边界

“数据来源”页面已经统一展示五类来源，但自动候选提取的主入口仍是 completed 会话：

- Artifact、执行评价和教学信号可作为会话 RecallView 的补充来源；
- context file 和外部连接器目前主要完成目录、状态和治理展示；
- 尚没有一个与会话沉淀等价的“单独文件/连接器 -> 自动候选”完整调度链路。

## 17. 用户教学信号

当用户在对话中明确表达以下意图时，可形成教学信号：

- `remember`：记住；
- `prefer`：偏好；
- `avoid`：避免；
- `correct`：纠正。

教学信号的特点：

- 与 conversationId 和 messageId 绑定；
- 有 personal、project、agent 三种范围；
- 在原 Memory 写入成功后记录；
- 同时形成一个 Recall 候选；
- 教学信号可以撤销；
- 撤销后，尚未确认的相关候选会被拒绝；
- 已经形成的正式资产不会被教学信号撤销自动删除，需要单独治理资产。

## 18. 阶段十三：在新会话中自动使用认知资产

### 18.1 触发时机

每个非 CLI Agent 回合在模型开始前调用 `buildRecallTurnPromptContext`。系统同时考虑：

- 当前会话中用户手动确认过的 Projection；
- 为本回合任务文本自动创建的语义 Projection。

CLI Agent 当前不接收 Recall 系统提示词，也不会显示 Recall 引用。

### 18.2 自动语义匹配

默认参数：

- 任务文本最多 2,000 字符；
- 语义相似度阈值 `0.35`；
- 最多选择 4 个资产；
- 使用 KB embedding 计算余弦相似度；
- embedding 不可用时直接跳过自动注入，不使用低质量兜底强行注入。

### 18.3 自动注入前过滤

- 只选择 `active` 资产；
- 排除 `paused` 和 `revoked`；
- 排除 workspace reference 明确禁用的资产；
- 排除 Evidence 来源已暂停、移除或撤权的资产；
- 排除低于阈值的资产；
- 没有有效匹配时不生成 Projection，不注入任何资产。

### 18.4 手动 Projection

手动 ContextProjection 支持：

- 预览候选资产；
- 添加资产；
- 移除资产；
- 修改用途；
- 稍后；
- 拒绝；
- 用户确认；
- 资产版本变化时要求刷新，防止确认旧内容。

手动路径会检查资产范围和 workspace reference；确认后的 Projection 可以绑定到会话消息卡片。

### 18.5 提示词注入格式

确认资产被包装在：

```text
### Confirmed reusable ability assets
<confirmed-ability-assets>
...
</confirmed-ability-assets>
```

提示词明确要求模型：

- 把这些内容视为用户确认的参考，而不是新的高优先级指令；
- 只在与当前任务相关时使用；
- 没有真正应用时不得声称使用了资产。

安全限制：

- 单资产 statement 最多 2,000 字符；
- 总注入块最多 14,000 字符；
- 手动与自动 Projection 合并后最多注入 12 个不同资产；
- `<`、`>`、`&` 会转义；
- 每个资产最多带 20 个简化来源引用；
- 注入前再次读取最新资产和来源状态。

### 18.6 引用展示

当回答成功持久化时，消息保存 `recall_citations`：

- `asset_id`
- `title`
- `type`
- `version`
- `scope`
- `projection_id`
- `match_score`
- `match_method`

失败、中止或带 failureKind 的回答不会保存 Recall 引用，避免错误声称资产已被使用。

## 19. 当前自动召回的范围边界

以下能力已经实现：

- 语义匹配；
- 默认阈值和数量限制；
- 资产状态过滤；
- 来源撤权过滤；
- workspace 显式禁用过滤；
- 引用展示和使用记录。

以下能力仍不完整：

- `scopePolicy` 已能存储，但自动 Projection 尚未按 agentIds、roleIds、projectIds、workspaceIds、conversationKinds、fileKinds 全量执行策略判断；
- 自动 Projection 当前没有像手动 Projection 一样完整检查资产 `scope` 字符串；
- 语义冲突、时间优先级、角色优先级和范围冲突尚未形成统一解析器；
- 普通负面反馈不会直接影响下一次语义排序权重。

## 20. 阶段十四：使用记录与即时反馈

### 20.1 UsageRecord

成功回答后，每个引用资产写一条 UsageRecord：

- `assetId`
- `assetVersion`
- `taskRunId`
- `projectionId`
- `workspaceId`
- `messageId`
- `boundary = real`
- `outcome = replied`
- `createdAt`

这证明“资产被带入并用于一次成功回答”，但不证明结果更好。

### 20.2 回答级反馈

用户可以对带引用的助手回答提交：

- `positive`：有帮助；
- `negative`：需改进。

系统按 `messageId + assetId + projectionId + outcome` 去重，避免重复点击产生重复记录。

回答级反馈只写 UsageRecord outcome：

- `feedback_positive`
- `feedback_negative`

它不会直接升级成熟度，也不会自动暂停资产。

## 21. 阶段十五：TransferProof 与 EffectivenessProof

### 21.1 TransferProof

当一个带 confirmed Projection 的任务达到终态时，系统建立 TransferProof。

| 任务终态 | TransferProof 状态 |
| --- | --- |
| `completed` | `succeeded` |
| `waiting_input` | `degraded` |
| `failed` | `rejected` |
| `cancelled` | `rejected` |

TransferProof 保存：

- Projection ID；
- execution ID；
- 预期结果快照；
- 本次使用的资产 ID 和版本；
- 实际迁移观察；
- 可选 receipt ID 和 wakeRequestId；
- 创建与完成时间。

`succeeded` 后：

- 相关资产成熟度升级为 `transfer_validated`；
- 写入 outcome 为 `succeeded` 的使用记录。

当前自动 TransferProof 主要证明“带入资产的任务成功到达 completed”，还不是对业务质量的充分证明。

### 21.2 EffectivenessProof

TransferProof 成功后才能创建 EffectivenessProof。支持结果：

- `better`
- `no_improvement`
- `worse`
- `insufficient_evidence`
- `invalid`
- `rework`

结果影响：

- `better`：资产成熟度升级为 `effectiveness_validated`；
- `worse`：产生“建议暂停”；
- `rework`：产生“建议返工”；
- `invalid`：Proof 标记无效；
- 负面结果不会自动替用户暂停或撤销资产。

### 21.3 两条反馈路径的区别

| 路径 | 输入 | 结果 | 是否影响成熟度 |
| --- | --- | --- | --- |
| 回答级反馈 | 对一条带引用回答点“有帮助/需改进” | UsageRecord | 否 |
| 完整效果反馈 | 对成功 TransferProof 提交效果评价和证据 | EffectivenessProof | `better` 时是 |

## 22. 阶段十六：从认知资产生成 Skill

### 22.1 触发条件

只有满足以下条件的资产才能生成 Skill：

- `type = skill_method`；
- `status = active`；
- 资产存在可追踪 Evidence；
- 已配置可用模型且授权有效。

通过沉淀任务确认 `skill_method` 资产后，系统会自动准备 Skill 草稿。此时不会直接加入技能库。

### 22.2 基于 Recall 上下文生成

系统不是只把一条资产标题改成 Skill，而是：

1. 以主 `skill_method` 资产为核心；
2. 对全部 active 资产进行语义匹配；
3. 使用较低阈值 `0.2`，最多选 6 个相关资产；
4. 合并相关 Evidence 来源；
5. 固化资产 ID、版本、来源和 fingerprint；
6. 将这份 Recall 上下文交给模型生成结构化 Skill 提案。

如果语义选择不可用，系统会降级为只使用主资产，但仍要求存在可追踪来源。

### 22.3 模型生成的 Skill 提案

严格 JSON 提案必须包含：

- description；
- useWhen；
- doNotUseWhen；
- requiredInputs；
- workflowSteps；
- outputs；
- validationChecks；
- failureModes；
- ontology concepts / relations；
- mutableSurfaces。

### 22.4 Level A 文件集

当前实现固定生成 15 个 Level A 文件：

1. `SKILL.md`
2. `agents/openai.yaml`
3. `evals/evals.json`
4. `evals/forecast_model.md`
5. `evals/outcome_evaluation.md`
6. `evals/replay_dataset.md`
7. `evals/regression_tests.md`
8. `references/skill-spec.yaml`
9. `references/ontology-mapping.md`
10. `references/validation-contract.md`
11. `references/input-contract.md`
12. `references/output-contract.md`
13. `references/governance-boundaries.md`
14. `references/eval-cases.yaml`
15. `references/failure-modes.md`

### 22.5 校验与治理

草稿生成后校验：

- 文件是否齐全；
- 是否存在重复或额外文件；
- 每个文件内容哈希是否匹配；
- `skill-spec.yaml` 是否包含业务上下文、规则、状态机、文件清单、可变和保护面；
- ontology 是否包含 TBox、RBox、ABox；
- 每个文件是否通过现有 Skill 质量校验。

生成的 Skill 明确限制为：

- `lifecycle_state = staged`
- `promotion_ceiling = staged`
- `production_release_allowed = false`
- `owner_review_required = true`
- `capability_level = L1`

一次成功会话不会直接产生“已验证、可发布”的 Skill。

### 22.6 用户加入技能库

“加入技能库”时再次检查：

- draftHash 未变化；
- 所有文件哈希未变化；
- Recall 上下文资产仍为 active；
- 资产版本未变化；
- 来源 fingerprint 未变化；
- Level A 校验仍通过。

通过后：

1. 创建自定义 Skill；
2. 逐个写入校验后的文件；
3. 草稿状态从 `draft` 变为 `installed`；
4. 保存 `installedSkillId`；
5. 失败时尽力删除已创建的半成品 Skill。

## 25. 异常、暂停与应用重启恢复

### 25.1 典型错误码

| 错误码 | 原因 | 恢复方式 |
| --- | --- | --- |
| `model_not_configured` | 未配置模型 | 配置模型后重试 |
| `model_auth_required` | 模型授权失效 | 重新授权后重试 |
| `source_unavailable` | 原消息或会话不可读 | 恢复来源后重试 |
| `source_paused` | 来源被暂停 | 恢复来源 |
| `source_removed` | 来源已移除 | 重新接入或放弃任务 |
| `recall_view_failed` | 来源快照构建失败 | 重试 |
| `model_failed` | 模型执行失败 | 重试 |
| `invalid_model_output` | 模型未返回严格结构 | 重试或更换模型 |
| `candidate_save_failed` | 候选持久化失败 | 重试 |
| `asset_write_failed` | 正式资产写入失败 | 保留候选并重试入库 |
| `asset_write_interrupted` | 写资产时应用退出 | 回到审核态重新确认 |
| `candidate_expired` | 候选超过 90 天 | 重新形成候选 |
| `evidence_insufficient` | 缺少有效证据 | 补充证据 |

### 25.2 暂停和取消边界

- `waiting_*`、`scheduled`、`queued`、安全阶段的 `extracting` 可以暂停；
- `candidate_save` 阶段不允许暂停或取消，避免产生半写候选；
- `writing` 不允许取消，避免用户确认后出现不确定资产状态；
- 正在模型提取时的暂停/取消通过 AbortSignal 和控制请求协作完成。

### 25.3 应用重启恢复

应用启动后扫描所有 Capture：

- `writing` -> `review_ready`，错误标记 `asset_write_interrupted`；
- `extracting` / `queued` -> `queued` 并重新调度；
- 可重新判断的 `waiting_completion` 补上 `activity_changed` 和计划时间；
- `waiting_quiet`、`scheduled` 和可调度 `waiting_completion` 重新注册后台任务；
- `paused`、`review_ready`、`no_candidate`、`cancelled` 保持原状态。

## 28. 权限、隐私与安全

### 28.1 已实现保护

- 所有私有数据均按 userId 隔离；
- 来源引用只持久化稳定元数据，不复制完整正文；
- 绝对路径不会写入 v2 来源引用；
- excerpt 会对 Bearer token、API key、password、secret、cookie 等内容脱敏；
- 候选和正式资产写入前调用敏感信息持久化检查；
- 来源暂停、移除或撤权会阻止确认和自动注入；
- Prompt 数据使用 JSON 编码和字符转义；
- CLI Agent 不使用 Recall 注入；
- 模型提取和 Skill 生成禁用工具；
- Skill 草稿明确禁止打包原始对话、客户数据、凭证、日志和缓存。

### 28.2 当前 Gate 边界

`cognition/gate.ts` 已实现确定性安全 Gate，可识别：

- 指令覆盖；
- 角色重定义；
- 系统提示词窃取；
- Skill red flag 规则；
- 可选语义深度审查。

但当前源码中 `evaluateCandidate(...)` 主要属于旧 Cognition 候选链路，新 Recall 候选确认并没有完整复用这套 Gate。新链路目前依靠敏感信息持久化检查和高风险布尔确认，尚未形成完全统一的安全准入结果。这是需要优先补齐的安全一致性缺口。

## 29. 当前已实现、部分实现和未打通项

### 29.1 已实现

- completed 终态触发，waiting_input/失败/取消不直接自动沉淀；
- 智能静默、夜间和手动三种调度；
- 内部观察任务不进入用户列表；
- 用户继续对话后重新计时；
- `waiting_completion` 活动变化后的重新调度；
- 问候、感谢、简单确认、状态查询和无结果对话预筛；
- 严格 JSON 模型提取、消息和字符上限、最多 3 个候选；
- 模型后确定性质量校验；
- 弱观察、待审核、稍后、确认、拒绝、忽略、过期和失败状态；
- 候选精确去重、Evidence 合并和稳定 captureKey；
- ReviewDecision、资产交接回执和确认幂等；
- 创建、更新、缩小范围、暂停资产；
- 资产版本、审计、暂停、恢复和撤销；
- 来源暂停、恢复、删除影响预览和可选资产撤销；
- 自动语义召回、阈值、数量限制和无匹配不注入；
- 回答引用、UsageRecord 和回答级反馈；
- TransferProof、EffectivenessProof 和成熟度升级；
- 方法资产基于 Recall 上下文生成并校验 Skill 草稿；
- 用户确认加入技能库；
- 应用重启恢复未完成沉淀任务；
- 总览、沉淀任务、记忆内容、数据来源四个主页面。

### 29.2 部分实现

1. **ReviewPolicy**
   设置和 UI 已存在，但 `auto` 与 `manual` 目前没有完整不同的后端候选审核调度行为；两者都不会自动写正式资产。

2. **个人画像落点**
   `personal` 资产可沉淀和召回，但不会自动拆分到结构化身份字段，也不会自动更新旧 Personal Ontology group。

3. **统一安全 Gate**
   新 Recall 候选尚未完整调用旧 Cognition `evaluateCandidate` Gate。

4. **ScopePolicy 执行**
   字段已经存储和校验，但自动 Projection 未完整执行所有细粒度策略。

5. **文件与外部连接器提取**
   目录和治理状态已统一，但独立的文件/连接器自动候选提取链路尚未与会话链路等价。

6. **冲突解析**
   当前有精确指纹去重，没有完整的语义重复、时间优先级、角色优先级和范围冲突决策器。

7. **普通反馈学习**
   正负反馈能记录，但不会直接调整检索分数、自动暂停资产或驱动新候选。

8. **认知树**
   当前是显式 rebuild 的派生 JSON 快照，不是实时更新的图数据库。

9. **生命周期命名**
   `lifecycleStatus` 当前固定为 `user_confirmed_unverified`；后续验证通过主要体现在 `maturity`，两条轴尚未形成完整迁移规则。

10. **批量确认后的 Skill 自动准备**
    单项通过 Capture 确认会准备 Skill 草稿；候选服务的批量确认直接调用资产晋升，当前没有同等的自动 Skill 准备包装。

### 29.3 兼容层，不应视为主链路

- 旧 `personal_ontology_candidates` 的确认与拒绝；
- 旧 Cognition candidates/receipts IPC；
- `cognition.assets.list` 对 Recall 资产和 Personal Ontology groups 的聚合展示；
- 旧来源类型 memory/context/ontology/execution/message/artifact；
- 部分旧 UI 文案和别名路由。

## 30. 推荐验收用例

### 30.1 自动沉淀

1. 完成一段包含明确偏好和方法的会话。
2. 确认静默期内页面不出现任务。
3. 静默期内继续对话，确认计划时间顺延。
4. 停止对话并等待静默结束。
5. 确认出现 review_ready 任务和可解释候选。

### 30.2 低价值过滤

分别测试：

- “你好”；
- “谢谢”；
- “OK”；
- “现在到哪阶段了”；
- 一次没有完成结果的失败会话。

验收：不会生成可见沉淀任务，不会产生 pending_review。

### 30.3 候选确认与幂等

1. 对同一候选快速重复点击保存。
2. 模拟第一次响应超时后重试。
3. 验收只存在一个 ReviewDecision 结果和一个 assetId。
4. 在记忆内容中能查询资产、版本、范围和来源。

### 30.4 拒绝与忽略

1. 分别拒绝和忽略候选。
2. 验收没有创建正式资产。
3. 相同内容和相同 Evidence 不再次提醒。
4. 新 Evidence 出现时按规则决定是否重新形成候选。

### 30.5 来源撤权

1. 暂停会话来源后等待任务运行。
2. 验收任务暂停或候选确认失败。
3. 恢复来源后重试。
4. 删除来源并选择同时撤销资产。
5. 验收后续新会话不再注入相关资产。

### 30.6 对话调用闭环

1. 创建并确认一条与新问题明显相关的规则资产。
2. 在新会话提出相关问题。
3. 验收相似度达到阈值后注入。
4. 验收回答显示引用资产。
5. 验收 UsageRecord 包含 assetId、version、projectionId 和 messageId。
6. 提交“有帮助”，验收只增加一次反馈记录。

### 30.7 Proof 与成熟度

1. 使用 confirmed Projection 完成另一个任务。
2. 验收 TransferProof 为 succeeded。
3. 验收资产成熟度为 transfer_validated。
4. 提交 positive effectiveness feedback。
5. 验收资产成熟度为 effectiveness_validated。
6. 提交 negative feedback，验收只生成暂停建议，不自动暂停。

### 30.8 Skill 转化

1. 确认一个 `skill_method` 候选。
2. 验收自动生成 Skill 草稿。
3. 验收草稿引用主资产、相关资产和来源。
4. 验收实际 15 个 Level A 文件和校验结果。
5. 修改原资产版本，验收旧草稿不能安装。
6. 重新生成并点击“加入技能库”。
7. 验收技能库出现一个自定义 Skill，状态仍为 staged。

## 31. 推荐后续优化顺序

1. 将新 Recall 候选接入统一确定性安全 Gate。
2. 完整执行自动 Projection 的 scope 和 scopePolicy。
3. 将 `personal` 资产映射到结构化“关于我”字段，并设计冲突、版本和用户确认方式。

7. 让回答级反馈在可解释、可撤销前提下影响排序和返工建议。
8. 将认知树改为事件驱动更新，或明确保持派生快照定位。

## 33. 结论

当前项目已经形成一条可运行的认知资产主链路：会话完成后不会立即打扰用户，而是经过静默、价值预筛、模型提取和候选质量校验；用户确认后通过 ReviewDecision 和幂等交接形成正式资产；正式资产能在新会话中按语义相关度被选择、注入、引用并记录使用；进一步可以通过 TransferProof 和 EffectivenessProof 提升成熟度；方法类资产还能生成经过结构校验的 Skill 草稿并由用户加入技能库。

当前最重要的剩余工作不是继续增加页面，而是统一几个关键边界：新旧候选安全 Gate、自动召回作用域、个人画像结构化落点、文件与外部系统提取、语义冲突处理，以及反馈对后续排序的可解释影响。完成这些边界后，整个系统才能从“可以沉淀和召回”提升为“稳定、可控、可解释地形成个人认知资产”。
