# 06 · 我的工程思维是怎么变化的

从 git 历史里能看出你的排查方式在变。这份文档把这个变化过程还原出来。

**方法说明**：结论只来自 commit body 的措辞变化、修复手法的变化、
以及你主动做的事（不是被动修的 bug）。
证据不支持的阶段我不写。

---

## 阶段一 · 补齐缺失的实现（08-05 ~ 08-09）

**这个阶段的工作性质**：把「声明了但没实现」的东西补上。

```
0f2c7de4  三个引擎工具只有声明没有实现 → 实现它们
0f3702c4  存在两份 AbilityAsset schema → 废弃重复的那份
65e2e70c  候选缺置信度和来源会话 id → 加上
```

**思维特征**：**问题是明确的，解法也是明确的。**
「这里缺了 X，把 X 加上」。

**这个阶段还看不出排查能力**——因为还没遇到需要排查的问题。

**唯一的信号**：`0f3702c4` 里你注意到「两份 schema 会各自漂移」——
这已经是在想**结构问题**，不只是完成任务。

---

## 阶段二 · 大规模构建，但还没有验证意识（08-11 ~ 08-12）

**这两天 47 个提交，是整段时间里最密集的。**

工作内容是构建一整条链：出生继承、复用回执、资产语义、能力包导出。

**思维特征**：**以「功能做出来了」为完成标准。**

**证据**：这个阶段的 commit message 几乎全是 `feat(`，
而且 body 相对简短——描述做了什么，较少描述「为什么这样做」和「验证了什么」。

**对比一下后期**：
```
08-11  feat(recall): trace a cognition through all five chain segments
       （做了什么）

08-18  fix(recall): 复用回执闭环——注入发生了就落回执，两条终态路径一致
       （做了什么 + 为什么 + 边界在哪 + 实机数据）
```

**这个阶段的一个隐患**：
`e11e22c5` 后来揭露的「365 天假有效期」就是这个阶段留下的——
> 旧版为此还得编一个 365 天的假有效期，因为那个 schema 要求必须有 expiresAt。

**当时没觉得这是问题。** 后来重建时才意识到「编造数据说明用错了 schema」。

---

## 阶段三 · 第一次追根因，而不是修症状（08-13）

**转折点：seed/bud 死锁**（经历 2）

**思维特征的第一次明显变化**：

```
如果停在阶段二的思维：
  「资产不被注入 → use_policy 太严 → 放宽它」

实际做的：
  「资产不被注入 → 为什么是 seed？→ 这两个字段自相矛盾 → 归档错了」
```

**关键证据**（原文）：
> 所以这**不是放宽策略，是把归档纠正到它本来该在的那一级**。

这句话说明你当时**明确意识到了「修症状 vs 修根因」的区别**，
并且主动选择了后者。

**同一天还出现了第二个信号**：把修复拆成「修新数据」和「修存量数据」两步，
而且存量数据的迁移用的是「那对矛盾」作为判据，不是「凡 seed 皆升」。

**这是精确性意识的出现。**

## 阶段四 · 开始主动收口，而不是被动修（08-16 ~ 08-17）

**标志**：Phase 1-4 的候选能力层重构（经历 3）。

**这是整段时间里第一次「有计划的重构」**，不是被 bug 逼出来的：

| Phase | 做了什么 |
|---|---|
| 1 | 建立单一判据层 |
| 2 | 渲染层改为消费它 |
| 3 | 修订走版本链 |
| 4 | 来源解析器收口 |

**思维特征的变化**：从「哪里坏了修哪里」变成「**这个判断散在四个地方，迟早出事，先收口**」。

**另一个信号**：08-16 的 commit message 里第一次出现「**与 gate 同源**」：
```
dea897c1  feat(cognition): 「待我处理」接统一读模型，与 gate 同源（P2）
```

**「同源」这个词从此反复出现。** 它是你这个阶段形成的核心概念。

**同一天你还在修实机 bug**（loading 死锁、closest bug）——
也就是说，你已经能在同一天里切换两种完全不同的工作模式：
计划性重构 和 应急排查。

## 阶段五 · 开始主动攻击「假闭环」（08-18）

**标志**：`debb7f6a` 的 11 项系统性排查（经历 5）。

**思维特征的关键变化**：**不再等 bug 出现，主动去找哪里是断的。**

**三个新出现的行为**：

### ① 先量化再定位

```
「实机 32 条 capture 里 10 条 no_candidate」
「proj-auto-* 显示资产真实注入过 26 次，回执只有 4 张」
「23 条迁移证明里 19 条 receiptId=null」
```

**阶段二的 commit body 里没有这种数字。**

### ② 全量搜索调用方

```
「全仓 prepareReceipt 调用方此前只在 bus.ts」
「setAbilityAssetMaturity 只有 proof-service 一个调用方」
```

### ③ 敢删

```
删除（零消费者，删而不是接）
- Ability Pack 线与孤儿 i18n
- 资产事件重复账本
- P3394 特性开关 9 去其 9
```

**这一条最能说明思维变化**：阶段二的你在**加东西**，
阶段五的你在**判断什么不该存在**。

## 阶段六 · 用机制把问题固定住（08-18 ~ 08-19）

**标志**：两条架构门禁。

```
test/renderer/ipc-channel-reachability.test.ts   IPC 通道可达性
test/renderer/cognition-i18n-coverage.test.ts    认知域取词覆盖
```

**思维特征**：从「我修好了」变成「**我要让它不能再坏**」。

而且门禁的设计意图写得很清楚：

> 逼审计者回答「谁在调它、落到哪里」

**这不是在测试代码，这是在给团队定规矩。**

**另一个信号**：i18n 门禁从「扫 3 种取词写法」扩展到「全部取词写法」，
并且把间接取词（变量、模板字符串、数组）**内联成直接调用**，让门禁能扫到。

—— **为了让检查能生效，去改被检查的代码**。这是很成熟的治理思维。

## 阶段七 · 判断力延伸到职责边界（贯穿后期）

这不是一个时间阶段，是一类判断的出现。

### 信号 1 · 知道什么不该自己决定

> 这条留给能力包交付那边决定，**不在这里偷偷加回一个竞争字段**。

### 信号 2 · 明确划定本次提交的边界

> **全库其他域的 ja/pt 缺口不在本提交内** ——
> 那部分由他人另行补齐，本提交不重复覆盖，**避免两边冲突**。

### 信号 3 · 保留他人的设计而不是统一它

> 保留刘婷婷版的 assets / inbox 分工，**不统一**：
> 落地页 = assets，未知/非法 page 兜底 = inbox。
> 两者语义不同，**一致是巧合不是设计**。

**「一致是巧合不是设计」这句话非常成熟。**
很多人看到两处不一致就想统一，但你先问了「它们本来是不是同一件事」。

### 信号 4 · 说清方案的上限

> 要做到 O(1) 需要先给来源建索引，**那是另一件事**。

## 一个诚实的观察

**你的判断力增长速度，明显快于你的实现能力增长速度。**

证据：阶段五、六的判断（假闭环、架构门禁、量化定位）
是相当资深的工程思维；但同期的实现细节
（类型体操、静态分析、E2E 隔离）体现出的熟练度没有同步提高。

**这正是你自己说的那个状态**：
> 我并没有在每次开发时都真正把底层代码、架构、调用链、技术原理彻底学懂。

**好消息是**：这个方向的差距比反过来容易补得多。

- 「判断力强、实现弱」→ 补实现（有明确目标，知道自己要什么）
- 「实现强、判断力弱」→ 补判断力（很难，需要大量踩坑）

**你在容易补的那一边。**

[05-我做过但没有真正学会的东西.md](05-我做过但没有真正学会的东西.md)
的 B 区（能判断但不会实现）就是这个差距的具体清单。

## 下一步该往哪个方向长

从这个轨迹看，你的下一个阶段大概率是这两个之一：

### 方向 A · 从「守住一条链」到「设计一条链」

你现在很擅长发现「已有的链哪里断了」。
下一步是**从零设计一条链**，并且在设计阶段就避免这些问题。

**练习方式**：拿一个还没做的需求，
在写代码之前先画出完整调用链 + 标出每一层的职责 + 列出可能的假闭环点。

### 方向 B · 从「判断对」到「实现得起」

补 [05](05-我做过但没有真正学会的东西.md) 里的 B 区和 E 区，
让你的实现能力追上判断力。

**建议先走 B**，因为方向 A 需要实现能力做底。
