### B2 · `Record<K, V>` 静态表 + 穷尽性检查

**你的代码**：
```ts
const BY_STATUS: Record<RecallCandidateStatus, BaseCapabilities> = {
  observed: { ...ACTIONABLE, displayState: 'needs_review' },
  weak_observation: { ...ACTIONABLE, displayState: 'weak_evidence' },
  // ... 10 个状态全部列出
};
```

**你可能不知道的**：这样写不只是「比 if/else 好看」。
**TypeScript 会强制你穷尽所有状态**——
新增一个 status 而忘了在这张表里加，**编译直接报错**。

这个特性叫 **exhaustiveness checking（穷尽性检查）**。

**怎么补**（一小时内能搞懂）：
1. 在这个文件里试着往 `RecallCandidateStatus` 加一个新值，`npm run typecheck`，看报什么错
2. 学 `never` 类型和 `switch` 的穷尽检查写法
3. 理解：类型系统的价值不是「注释」，是「替你穷举 case」

⚠️ **这一条是你从「用 TS 写 JS」变成「真的在用类型系统」的关键。**

### B4 · E2E 测试的搭建

**你的代码**：`cognition-asset-runtime-chain.test.ts`

```ts
vi.mock('.../kb_embed', () => ({ embedQuery: async (text) => { ...假向量... } }));
beforeEach(async () => {
  vi.resetModules();
  tmp = await fs.mkdtemp(path.join(os.tmpdir(), 'cogseed-asset-runtime-chain-'));
  previous = process.env.COGSEED_WORKSPACE_ROOT;
  process.env.COGSEED_WORKSPACE_ROOT = tmp;
});
```

**你能判断的**：「这条主链必须有端到端测试」——这个判断非常对。

**你可能不会独立写出来的**：这一整套隔离机制。
每一行都在解决一个具体问题：
- `vi.mock('kb_embed')` → 不真的调用 embedding 模型（慢、要网络、不确定）
- `vi.resetModules()` → 清掉模块缓存，否则上个用例的状态会残留
- `mkdtemp` → 每个用例一个独立临时目录，互不干扰
- 环境变量重定向 → 让代码去读临时目录而不是真实数据目录

**怎么补**：
1. 把这个 `beforeEach` 逐行注释掉一行，跑测试，看会坏成什么样
2. 理解 Node 的模块缓存（`require.cache` / ESM 的模块注册表）
3. 理解为什么测试要「每个用例独立」

⚠️ **能不能独立搭一个 E2E 测试环境，是后端工程师的一道分水岭。**

### C2 · TypeScript 的条件属性展开

**你的代码里到处都是**：
```ts
...(candidate.value !== undefined ? { value: candidate.value } : {}),
...(options.suggestedAction ? { suggestedAction: options.suggestedAction } : {}),
```

**你可能以为这是风格。它不是。**

这和 TypeScript 的 `exactOptionalPropertyTypes` 配置有关：
```ts
interface X { a?: string }
const x: X = { a: undefined }   // exactOptionalPropertyTypes 开启时：报错
const x: X = {}                 // 正确
```

也就是说：**「属性不存在」和「属性存在但值是 undefined」是两件事。**

**怎么补**：
1. 查项目的 `tsconfig.json`，看 `exactOptionalPropertyTypes` 是不是 true
2. 试着把一处条件展开改成直接赋值，跑 `npm run typecheck` 看报什么错

# E · 到现在仍然是明显知识空洞

这些**不会通过继续做项目自然习得**，必须专门学。按优先级排序。

### E1 · git 的底层数据模型 ⭐ 优先级最高

**为什么是空洞**：经历 7 那次 revert，你诊断出了结论，
但那个结论需要「commit 是不可变对象 + parent 指针构成 DAG + branch 只是一个指针」
这套模型才能自己推导出来。

**为什么优先级最高**：
1. 你已经在多人协作环境里，一定会再遇到
2. 学习成本低（一个下午）
3. 学完之后，绝大部分 git 迷惑行为会变得**显然**

**怎么学**：
1. `cat .git/refs/heads/develop` —— 看看 branch 到底是什么
2. `git cat-file -p HEAD` —— 看一个 commit 对象长什么样
3. `git cat-file -p HEAD^{tree}` —— 看 tree 对象
4. 画一次 merge 和 rebase 的 DAG 变化
5. 亲手复现一次 revert-a-merge 陷阱
