# 02 · 我的工作成长时间线

不按时间顺序流水账，按**五条成长线**。
每条线告诉你：这类问题你是怎么一步步摸清的。

---

## 线索一 · 从「看页面现象」学会追真实状态

**这条线的起点**：页面不对劲，第一反应是改页面。
**这条线的终点**：页面不对劲，先问「后端到底是什么状态」。

### 串起来的经历

```
① 认知资产页永远显示「加载中」
   现象在渲染层，根因也在渲染层——但不是"渲染代码写错了"
   而是一个变量同时当了 UI 状态和函数重入锁
        ↓
② 修完 ① 之后，才走得到候选详情页
   立刻暴露：点「确认并限域」后端报"参数非法"
   报错来自后端，但后端拒得完全正确——渲染层发过去的确实是空串
        ↓
③ 真机验收发现：同一条提交路径会**静默清空**用户已有的边界数据
   界面看着对、写进去的东西不对
        ↓
④ 学会的判断：
   "后端报错" ≠ "后端有问题"
   "页面卡住" ≠ "接口没返回"
   先确认真实状态，再决定往哪一层查
```

详见 [03-我经历过的核心问题.md](03-我经历过的核心问题.md) **经历 1**。

## 线索二 · 我开始发现「有接口 ≠ 真闭环」

**这条线是你这段时间最核心的成长。**

### 串起来的经历

```
① 「有页面、有按钮、有数据结构，但没有任何消费者」
   → 逐条排查认知资产链路，发现三条零消费者的假链路
   → 决定：删掉，而不是硬接上
        ↓
② 气泡「认知」沉淀写进了一个**没有任何人读**的旧存储
   → 而且它连续两轮代码审计都被判成"休眠通道"
   → 因为渲染层用 URL 字符串调用，grep 通道名恒为 0 命中
   → 于是写了一条机械化门禁，逼审计者必须回答"谁在调它、落到哪里"
        ↓
③ 资产真的被注入了 26 次，回执只有 4 张
   → 两条注入路径，只有一条落回执
   → "落回执"和"运行簿记"被错误地共用了一道门
        ↓
④ 资产改版了，Runtime 还在用旧版本，而且没有任何地方会告诉用户
   → 这条边界此前无人测试
   → 补 E2E 测试把它钉住
        ↓
⑤ 学会的判断：
   看到一个功能，先问三句话——
   "谁在调它？" "调用结果被谁消费？" "有没有第二条路径漏接了？"
```

详见 **经历 4**、**经历 5**。

## 线索三 · 我开始理解「候选 → 正式资产」不是简单保存

**起点**：以为确认候选 = 把一条记录的 status 改成 confirmed。
**终点**：理解它是一次**跨越四道闸门、三个正交维度、两次写入**的状态迁移。

### 串起来的经历

```
① 状态与「够不够格」是两个正交维度
   status      → 这条候选走到哪一步了
   eligibility → 它的内容够不够格成为这一类资产
   压成一个枚举，就表达不了"待处理但内容不合格"这个状态
        ↓
② 晋升入口不止一个
   会话线、KStar 线、用户手动确认、失败重试——每条都能直接调 promote
   → 校验必须钉在一个函数里，不能只在抽取时做一次
        ↓
③ 同一道闸，user 和 system 的门槛不一样
   缺边界的规则候选：系统线不许晋升（没有人可确认）
                     用户线可以（他看到了提示仍然决定沉淀，那是有效决策）
        ↓
④ 成熟度（maturity）和生命周期（lifecycleStatus）也是正交的
   maturity        → 验证到哪一步了（seed → bud → ... → stable）
   lifecycleStatus → 这条资产是谁写进来的（用户确认 / 自动抽取 / 系统沉淀）
   → 这两个字段自相矛盾时，就是 bug（经历 2 的根因）
        ↓
⑤ 作用域（scope）不是一个字符串，是一套策略
   "限定给零个 Agent" 和 "不限定" 是两件事
   → 空数组被归一成 undefined，两个状态就撞成了同一个值
        ↓
⑥ 学会的判断：
   一个领域概念如果有多个"看起来差不多"的字段，
   先搞清楚它们各自回答什么问题，再决定要不要合并。
```

详见 **经历 2**、**经历 3**。

## 线索四 · 我开始用测试判断修复到底有没有成立

**起点**：修完跑一下，没报错就算好了。
**终点**：主动验证「把修复还原回去，测试会不会红」。

### 串起来的经历

```
① 发现测试盲区
   "此前所有加载态用例都是直接设 state 再调 render，
    没有一条走过真实的初始化路径，死锁因此一路漏到实机"
        ↓
② 发现测试桩失真
   "之前的测试用'完整资产'当桩，把这条整个掩盖了"
   → 治理页列表返回的其实是**精简视图**，没有边界字段
   → 测试桩比真实数据更完整，于是测试永远绿
        ↓
③ 开始验证修复的有效性
   commit body 里反复出现这句话：
   "已验证：把修复还原成旧写法，该用例会以 XXX 失败"
        ↓
④ 开始写不同种类的测试
   E2E 主链：candidate → 确认 → 资产 → Runtime 真实消费
   契约测试：绕过 UI 直接调 promote 仍然被拒
   架构门禁：IPC 通道必须有 handler、认知域取词必须有四语
        ↓
⑤ 学会的判断：
   "测试通过" ≠ "功能成立"。
   要问：这条测试走的是真实路径吗？桩的形状和真实读口一样吗？
```

## 线索五 · 我开始碰真正的多人协作工程

```
① 已经合入主线的一批能力，因为一次 merge 撤销从主线消失
        ↓
② 第二天重新合同一个分支——**什么都没回来**
   （git 认为那些提交已经合过了）
        ↓
③ 判断：不能原样搬回去
   因为这两天主线上发生了大量变化（空间化重构等），原样搬必然冲突
        ↓
④ 重新实现时，反而修正了旧版的四个设计问题
   其中一个是"为了满足 schema 而编造的 365 天假有效期"
        ↓
⑤ 发现一处语义损失，但**没有偷偷修复**
   而是明确写进 commit body，把决策交给该做决定的人
        ↓
⑥ 学会的判断：
   "功能实现过" 和 "当前主线上存在" 是两件事。
   重做一件事时，先问"现在的契约是什么"，而不是"我原来怎么写的"。
```

详见 **经历 7**、[11-Git与多人协作经历.md](11-Git与多人协作经历.md)。

## 五条线在时间上是怎么交织的

```
08-05 ─┬─ 引擎工具补齐、重复 schema 废弃
       │
08-11 ─┼─ 【线索三 起步】认知继承与复用链（两天 47 个提交）
08-12 ─┤     资产语义、出生继承、复用回执、能力包导出
       │  ⚡ 已合入主线的这批能力被撤销
       │
08-13 ─┼─ 【线索五】重新实现，按新契约重接
       │  【线索三 深化】发现 seed/bud 死锁 —— 新数据 + 存量数据两步修
       │
08-16 ─┼─ 四视图收敛，「与 gate 同源」第一次被明确写下来
       │
08-17 ─┼─ 【线索三 收口】候选能力层 Phase 1-4
       │  【线索一】loading 死锁 → closest bug（一个 bug 挡住另一个）
       │
08-18 ─┼─ 【线索二 爆发】假闭环大排查、回执闭环、E2E 主链
       │  【线索四】架构门禁、i18n 门禁
       │
08-19 ─┴─ 【线索二 + 三 汇合】
          假审批修复（eligibility 并入唯一判据）→ 合入主线
          第 101 条来源被误拒（把展示分页当真实性结论）
```

**注意 08-17 那个交叉点**：你在同一天既做了「有计划的判据收口重构」，
又修了两个「实机撞出来的 bug」。这两件事的思维方式完全不同，
而你已经能在同一天切换——这是这段时间里能力变化最明显的一个信号。
