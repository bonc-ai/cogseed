## 你负责的那个产品能力，是什么

CogSeed 想做一件事：**让 AI 记住你，并且能证明它真的用上了。**

具体来说：

1. 你和 AI 聊天、做任务的时候，系统在旁边**观察**，
   发现「这个人好像有个固定偏好」「这条规则他反复强调」——这叫**候选（Candidate）**。
2. 系统不能自作主张，得**问你**：「我观察到这条，要不要留下来？」
3. 你确认了，它才变成**正式资产（Ability Asset）**。
4. 以后新建一个 Agent、或者执行一个任务时，系统要判断
   **「这一次该带上哪几条认知」**，然后把它注入到 Agent 的提示词里。
5. 用完之后，要留下**证据**：这次真的用了哪几条、用了以后效果变好了没有。

**你负责的就是这整条链，从头到尾。**

## 你这段时间实际在干的事，可以归成六件

### 一、把「候选能不能确认」这件事收成一个判据

**问题**：「这条候选现在能不能确认？」这个判断，
在渲染层写了一遍、在待办列表写了一遍、在认知树写了一遍、在 IPC 返回里又写了一遍。

四份判断，迟早分叉。而且**真的分叉了**——同一条候选，
认知树上不显示，待办列表里却让你点确认，点完报错。

**你做的**：建了 `candidate-capabilities.ts`，
所有人都必须读它，不许自己写 `status === 'pending_review'`。

### 二、修「资产存下来了，但永远不会被用」

**问题**：用户认真确认了一条认知，它存进去了，但**永远不会进任何 Agent**。
界面上一切正常，「已验证资产」永远是 0。

**你做的**：发现这是一个**闭合的死锁环**——新资产的初始等级决定了它不会被注入，
不被注入就产生不了使用证据，没有证据就永远升不了级。而且这个环**没有任何出口**。

### 三、攻击「假闭环」

**问题**：有页面、有按钮、有数据结构、有 IPC 通道，
但中间某一段**根本没有消费者**。功能看起来做完了，其实是断的。

**你做的**：逐条排查，然后——这一点很关键——
**零消费者的假链路你选择删掉，而不是硬把它接上**。

### 四、让「用过」这件事留下真凭据

**问题**：实机数据显示资产真的被注入了 26 次，但只有 4 张回执。
于是效果评价全部失败，链路看起来是断的。

**你做的**：发现「落回执」和「运行簿记」被错误地共用了一道判断门，
以及第二条注入路径（Runtime）**根本没接回执**。

### 五、把界面从散页收敛成四个任务视图

**问题**：认知资产的页面越加越多，用户不知道该去哪。

**你做的**：收敛成「待我处理 / 我的认知树 / 管理来源 / 版本与治理」四个任务视图，
并且要求**待办的数量必须和真正决定「能不能确认」的那道闸读同一个判据**。

### 六、用测试和门禁把这些问题钉死

**问题**：修好的东西会被下一个人改回去。

**你做的**：写了端到端主链测试、契约测试，
以及两条**机械化的架构门禁**（IPC 通道可达性、认知域 i18n 覆盖）——
它们会在别人破坏约定时自动报红。

## 有一件事值得单独说

这段时间中间发生过一次协作事故：你已经实现完成、并且已经合入主线的一批能力，
因为一次 merge 被撤销，从主线上消失了。第二天你需要重新实现它们。

**你没有把旧代码搬回去。** 你按当时新的主线契约重新接了一遍，
并且在这个过程中修正了旧实现里的四个设计问题——
包括一个「为了满足 schema 而编造出来的 365 天假有效期」。

这件事在 [11-Git与多人协作经历.md](11-Git与多人协作经历.md) 里展开讲。
重点不是「谁 revert 了什么」，而是**你从中学到的那几个判断**。

## 用一句话形容你这段时间的工作性质

> **你不是在写新功能，你是在让已经写出来的功能真的成立。**

这解释了为什么你的提交里 `fix(` 那么多，也解释了为什么
你的 commit message 里反复出现这些词：

- 「假闭环」「零消费者」「没有任何消费者」
- 「唯一判据」「同源」「与 gate 同源」
- 「界面看着对、写进去的东西不对」
- 「没有为了让链路变绿而伪造任何加载事实」

**这些词就是你这段时间形成的工程直觉。**
