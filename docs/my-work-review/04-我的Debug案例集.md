## 第一部分：12 个可复用的排查模式

每一条都绑定你的真实经历。遇到新问题时，可以当检查清单用。

---

### 模式 1 · 一个变量承担了两个职责

**典型症状**：死锁、状态互相干扰、改一个地方另一个地方坏

**怎么识别**：搜这个变量的**所有写入点**，
看它们各自出于什么目的写。目的不同 = 职责不同。

**你的例子**：`loading` 同时是「UI 加载态」和「函数重入锁」（经历 1）

**下次怎么查**：
```bash
grep -n "loading" src/renderer/modules/skills.js | grep -E "=|\.loading"
```
把每一处的意图列出来，如果超过一种，就是它。

---

### 模式 2 · API 的语义和直觉不符

**典型症状**：数据读成空、拿到的不是你以为的那个对象

**你的例子**：`Element.closest()` **包含元素自身**（经历 1）

**下次怎么查**：怀疑某个内置 API 时，**别猜，去查文档的边界条件**：
- 包不包含自身？
- 空输入返回什么？
- 找不到返回 `null` 还是 `undefined`？
- 是否会修改原对象？

**常见的同类坑**：
| API | 反直觉的地方 |
|---|---|
| `Element.closest()` | 包含自身 |
| `Array.sort()` | 原地修改，且默认按字符串比较 |
| `parseInt('08')` | 老环境里可能按八进制 |
| `Object.keys()` | 不含继承属性和 Symbol |
| `JSON.stringify()` | 丢掉 `undefined`、函数、`Symbol` |

---

### 模式 3 · 两个各自正确的改动，组合起来是错的

**典型症状**：单看任何一个 diff 都正常，合起来就坏

**你的例子**：绑定侧用 `closest`（正确）+ 详情页按钮带 id（正确）→ 坏（经历 1）

**下次怎么查**：
```bash
git log -S '关键字符串' --oneline -- <文件>   # 找这行代码何时引入
git log --oneline -L <行号范围>:<文件>        # 追某几行的演进
```
分别找到两边的引入点，看它们是不是不同的人/不同的时间做的。

**这类 bug 的特征**：**没有人做错事，但结果是错的。**
所以 code review 抓不到，只有真的跑一遍才会暴露。

---

### 模式 4 · 一个 bug 挡住了另一个 bug

**典型症状**：修完 A，立刻冒出一个"新" bug B

**你的例子**：loading 死锁挡住了 `closest` bug（经历 1）

**你自己的原话**：
> 此前它一直够不到——认知资产页被上一个 loading 死锁挡住，根本走不到候选详情。
> 列表页的「修改后保存」是同一条路径，同样一直是坏的。

**下次怎么做**：**修完一个 bug，把完整路径重走一遍**，
不要修完就以为结束了。尤其是这个 bug 阻断了后续流程时。

---

### 模式 5 · 两个字段自相矛盾

**典型症状**：状态机走不动、某个流程永远进不去

**怎么识别**：把一条记录的所有字段打出来，逐个读它们的**定义**（不是名字），
看有没有两个字段在说互相矛盾的话。

**你的例子**（经历 2）：
```
lifecycleStatus = 'user_confirmed_unverified'   ← 用户确认过了
maturity        = 'seed'                         ← 规范里 seed = 候选档
```

**下次怎么查**：找规范/类型定义里每个枚举值的**原文定义**，
不要凭字段名猜语义。

---

### 模式 6 · 一个闭合的死锁环

**典型症状**：某个指标恒为 0、某个状态永远停在原地

**怎么识别**：画出状态迁移图。对每一条边，问「代码里真的存在这条边吗」。

**你的例子**（经历 2）：
```
seed → 不注入 → 无使用证据 → 无 transfer proof → 升不了级 → 还是 seed
```
而 `seed → bud` **没有任何代码路径**。

**下次怎么查**：
```bash
grep -rn "setAbilityAssetMaturity" src/     # 找所有能写这个字段的地方
```
逐个看它们能写出什么值。如果某个值没有任何地方能写出来，环就坐实了。

**关键**：找到环之后**别急着开后门**。先问「这条记录一开始就归错档了吗」。

---

### 模式 7 · UI 判据与后端闸门分叉

**典型症状**：点了按钮报错、两个界面对同一条数据显示不一致

**怎么识别**：搜「同一个判断在几个地方被写过」。

**你的例子**（经历 3）：`status === 'pending_review'` 在四个地方各写了一遍

**下次怎么查**：
```bash
grep -rn "pending_review" src/ | wc -l    # 如果 > 2，很可能有分叉
```

**修的方向**：**让 UI 去读后端的判据**，
而不是放宽后端去迁就 UI。

---

### 模式 8 · 把展示分页当成真实性结论

**典型症状**：数据量小时正常，数据多了才出错

**怎么识别**：搜所有 `limit:` 后面接判断的地方。

**你的例子**（经历 6）：`listCognitionSources({ limit: 100 })` 的结果被当成「存在性」判据

**下次怎么查**：
```bash
grep -rn "limit" src/main/features/ | grep -iE "has\(|includes\(|find\(|some\("
```

**核心问题**：
> 一个函数如果**同时**回答「给用户看什么」和「什么是真的」，它一定会出错。

---

### 模式 9 · 两条路径只接了一条

**典型症状**：部分场景有数据，部分场景没有

**怎么识别**：搜关键函数的**全部调用方**，数量少于你预期的路径数 = 漏接。

**你的例子**（经历 4）：
> 全仓 `prepareReceipt` 调用方此前**只在 `bus.ts`**

而实际上有两条注入路径。

**下次怎么查**：
```bash
grep -rn "prepareReceipt" src/           # 调用方有几个？
grep -rn "buildRuntimeAssetContext" src/ # 和路径数对得上吗？
```

---

### 模式 10 · 测试桩比真实数据更完整

**典型症状**：测试全绿，实机报错或丢数据

**怎么识别**：把测试桩的字段列表，和**真实读口返回的字段列表**对比。

**你的例子**（经历 8）：桩用「完整资产」，真实读口返回「精简视图」

**下次怎么查**：打开测试里的桩数据，
问一句「真实的那个接口，真的会返回这么多字段吗？」

---

### 模式 11 · DOM 没渲染 ≠ 用户想清空

**典型症状**：静默数据丢失，用户说「我的设置不见了」

**你的例子**（经历 1 / `220fa035`）：候选详情页没有边界输入框，
提交时读不到就提交空数组 → 边界被清空

**下次怎么查**：搜所有「读不到就给默认值」的地方：
```bash
grep -n "?.value || ''" src/renderer/modules/*.js
grep -n "|| \[\]" src/renderer/modules/*.js
```
每一处都问：**这个默认值会不会覆盖掉已有数据？**

---

### 模式 12 · 内部标识泄漏到用户界面

**典型症状**：用户看到一串 id、hash、内部枚举名

**你的例子**（经历 8 / `220fa035` 缺陷 3）：
`Task <taskRunId> · projection <projectionId>` 被当成展示文案

**下次怎么查**：搜展示文案里的标识拼接：
```bash
grep -nE "\\\$\{.*(Id|Ref|Hash|Key)\}" src/renderer/modules/*.js
```

## 第二部分：你反复使用的三个诊断动作

这三个动作在你的 commit body 里反复出现，
它们是你已经形成的**方法**，不是偶然。

### 动作 1 · 先量化，再定位

| 经历 | 你先拿到的数字 |
|---|---|
| 4 | 「注入 26 次，回执 4 张，19/23 条 receiptId=null」 |
| 9 | 「32 条 capture 里 10 条 no_candidate」 |
| 6 | 「limit 上限就是 100」 |

**为什么有效**：数字直接把「哪一段是好的、哪一段是坏的」分开了。

经历 4 里，「注入 26 次」这个数字一下子证明了**注入功能是好的**，
问题只可能在「注入之后」。这一步省掉了一半的排查范围。

**下次怎么做**：面对一个「不工作」的功能，
先找一个能把链路切成两段的数字。

---

### 动作 2 · 找系统里已经做对的参照系

**你的例子**（经历 4）：
> 出生继承那条路径（`recordInheritedCognitionReuse`）**本来就是**
> 「回执无条件落、只有簿记看 taskRun」的形状。

**为什么有效**：如果系统里同一件事有两个实现，一个对一个错，
那么「正确的那个长什么样」就是现成的答案。

**下次怎么做**：怀疑某处写错了，先问
「系统里还有别的地方做同样的事吗？它是怎么写的？」

---

### 动作 3 · 验证修复本身是否有效

**你的例子**：
> 已验证：把修复还原成旧写法，该用例会以
> `expected 0 to be greater than 0` 失败。

> 已验证：还原成旧写法该用例以
> 「必须发出 update: expected undefined to be truthy」失败。

**为什么有效**：这一步防的是「写了一条永远不会失败的测试」。

**这个方法有个正式名字**：**变异测试（mutation testing）** 的思想 ——
故意把代码改坏，看测试会不会发现。

**下次怎么做**：写完回归测试后，把修复 revert 掉跑一次，
**确认测试真的红了**，再改回来。

> 这一步大部分工程师不做。你做了，而且写进了 commit body。
> **保住这个习惯。**

## 第三部分：一张「新问题该从哪查」的决策表

| 现象 | 先查什么 | 别先查什么 |
|---|---|---|
| 页面卡住不动 | 请求**有没有发出去**（Network / 后端日志） | 别先改渲染代码 |
| 后端报「参数非法」 | 前端**实际发了什么**（打印 payload） | 别先怀疑后端校验太严 |
| 某个指标恒为 0 | 把链路切两段，看数据断在哪一段 | 别先查报错的那一层 |
| 数据量大才出错 | 所有 `limit` / `slice` / 分页 | 别先怀疑性能 |
| 两个界面显示不一致 | 它们各自读的是不是同一个判据 | 别先改其中一个界面 |
| 用户数据神秘消失 | 所有「读不到就用默认值」的地方 | 别先怀疑存储 |
| 测试绿但实机错 | 测试桩的字段 vs 真实读口的字段 | 别先加更多测试 |
| 某个功能好像没生效 | 它的**调用方有几个**，路径全不全 | 别先看它自己的实现 |
| 状态永远停在某一步 | 画状态图，找有没有出边 | 别先放宽策略 |
| 改了 A 结果 B 坏了 | A 和 B 是不是共用了什么 | 别先改 B |

## 第四部分：三条纪律

从你的 commit body 里提炼出来的，这三条你已经在做，写下来是为了守住。

### 纪律 1 · 不为了让链路变绿而伪造事实

> **没有为了让链路变绿而伪造任何加载事实。**（经历 4）

面对一个恒为 0 的指标，最容易的做法是让它变成非 0。
如果那个非 0 不是真的，你只是**把问题藏起来了**，而且藏得更深。

### 纪律 2 · 零消费者就删掉，不要硬接

> **删除（零消费者，删而不是接）**（经历 5）

发现一条没接通的链路，先问「有人需要它吗」。
没有的话，删掉比接上更负责——接上意味着从此要维护它、测试它。

### 纪律 3 · 不是我该决定的事，记录并移交，不要偷偷修

> 这条留给能力包交付那边决定，**不在这里偷偷加回一个竞争字段**。（经历 7）

发现一个不属于你职责范围的设计问题时，
「顺手改一下」制造的是两个语义重叠的东西——技术债的标准来源。
