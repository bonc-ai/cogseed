# 一、Git 与协作

## G1 · commit / branch / DAG

**为什么存在**：git 需要一种既能记录历史、又能并行开发的结构。

**在这个项目里**：一个 commit 是不可变对象，
branch 只是 `.git/refs/heads/<name>` 里的一行 hash。

**我碰到它的地方**：经历 7 —— revert 之后再 merge 什么都没发生。

**不懂它容易犯的错**：以为 merge 是「比较文件内容」，
所以想不通为什么内容明明没了 git 还说 "Already up to date"。

**验证命令**：
```bash
cat .git/refs/heads/develop        # branch 就是一行 hash
git cat-file -p HEAD               # commit 对象长什么样
```

---

## G2 · merge-base

**为什么存在**：merge 需要知道「两条分支从哪里分开的」。

**我碰到它的地方**：
- 判断分支是否已合入：`git merge-base --is-ancestor 分支 develop`
- 发现本地 `main` 与 `origin/main` **无共同祖先**（返回空）

**不懂它容易犯的错**：把「文件内容一样」当成「历史同源」。

---

## G3 · revert 一个 merge

**为什么危险**：它撤销**内容**，不撤销**祖先关系**。

**我碰到它的地方**：经历 7（完整机制解释在那里）

**不懂它容易犯的错**：以为重新 merge 一次就能恢复。

---

## G4 · worktree

**为什么存在**：同时在多个分支上工作，又不想 clone 多份。

**我碰到它的地方**：你有三个 worktree
（`mate-agent-develop` / `mate-agent-p3` / `mate-agent-public`）。

**不懂它容易犯的错**：以为它们是三个独立仓库（其实共用一个 `.git`）。

---

## G5 · 追踪已删除的文件

**我碰到它的地方**：查那 29 个消失的文件去哪了。

# 二、TypeScript

## T1 · union type（联合类型）

**为什么存在**：一个值只能是有限几种取值之一。

**我的代码**：
```ts
// candidate-capabilities.ts
export type RecallCandidateEligibility = 'eligible' | 'soft_warning' | 'ineligible';
export type RecallCandidateDisplayState =
  | 'needs_review' | 'weak_evidence' | 'deferred' | 'confirmed' | ...
```

**为什么用它而不是 string**：写错拼写编译就报错，
而且 IDE 能自动补全所有可能值。

**不懂它容易犯的错**：用 `string` 当状态类型，
于是 `status === 'pending_reviw'`（拼错）永远是 false，且不报错。

---

## T2 · `Record<K, V>` + 穷尽性检查 ⭐

**为什么存在**：把「每个枚举值对应什么」写成一张表，
并让编译器强制你填满。

**我的代码**：
```ts
const BY_STATUS: Record<RecallCandidateStatus, BaseCapabilities> = {
  observed: {...}, weak_observation: {...}, pending_review: {...},
  deferred: {...}, failed: {...}, confirmed: {...},
  rejected: {...}, ignored: {...}, expired: {...}, superseded: {...},
};
```

**关键价值**：往 `RecallCandidateStatus` 加一个新值而忘了在这张表里加
→ **编译直接报错**。这就是穷尽性检查。

**不懂它容易犯的错**：写成 `if/else if/else`，
新增状态时忘了处理，默默走进 `else` 分支。

⚠️ **这一条是 [05](05-我做过但没有真正学会的东西.md) 里的 B2，优先补。**

---

## T3 · `Omit<T, K>` / `Pick<T, K>`

**我的代码**：
```ts
type BaseCapabilities = Omit<
  RecallCandidateCapabilities,
  'canBatchSelect' | 'batchBlockedReason' | 'eligibility' | ...
>;
```

**为什么在这**：静态状态表只给一半能力，
另一半（eligibility 三件套）是算出来的。用 `Omit` 精确表达「这张表不负责那几个字段」。

---

## T4 · 条件属性展开

**我的代码**（到处都是）：
```ts
...(candidate.value !== undefined ? { value: candidate.value } : {}),
```

**为什么不直接 `value: candidate.value`**：
因为「属性不存在」和「属性存在但值是 undefined」在 TS 里是两回事
（`exactOptionalPropertyTypes`）。

**不懂它容易犯的错**：以为这是啰嗦的风格，
改成直接赋值后 typecheck 报一堆错，然后加 `as any` 绕过去。

---

## T5 · `as const`

**我的代码**：
```ts
const ACTIONABLE = { canView: true, canEdit: true, ... } as const;
```

**它做了什么**：把类型从 `{ canView: boolean }` 收窄成 `{ readonly canView: true }`。

**为什么需要**：这个对象被用来 spread 进多个状态，
`as const` 保证它不会被意外修改，且字面量类型被保留。

---

## T6 · 类型守卫 / 收窄（narrowing）

**我的代码**：
```ts
const judgment = typeof candidate.judgment === 'string' ? candidate.judgment.trim() : '';
```
```ts
if (!Object.prototype.hasOwnProperty.call(BY_STATUS, candidate.status)) return undefined;
return getRecallCandidateCapabilities(candidate as RecallCandidateCapabilityInput);
```

**为什么在这**：输入可能来自未经校验的旧数据 / 外部构造，
类型标注不代表运行时真的是那个类型。

**不懂它容易犯的错**：相信类型标注，
于是一条旧数据让整个列表读取崩溃。

---

## T7 · `readonly` 数组

**我的代码**：
```ts
sourceRefs?: readonly unknown[];
conflictingTypes?: readonly string[];
```

**为什么**：这是一个**纯函数**的输入，明确宣告「我不会改你的数组」。

# 三、JavaScript 运行时

## J1 · async 函数的同步前缀 ⭐

**为什么重要**：async 函数在遇到第一个 `await` 之前是**同步执行**的。

**我碰到它的地方**：经历 1 的 loading 死锁修复，**全部理由就在这里**。

**不懂它容易犯的错**：以为调用 async 函数后立刻返回，函数体一行都没跑。

**验证**：
```js
async function f() { console.log('A'); await 0; console.log('C'); }
f(); console.log('B');   // 输出：A B C
```

---

## J2 · 事件循环 / 微任务

**我碰到它的地方**：J1 是它的一个推论。

**不懂它容易犯的错**：所有异步时序问题都只能靠试。

⚠️ [05](05-我做过但没有真正学会的东西.md) 的 E2，优先补。

---

## J3 · `Map` / `Set`

**我的代码**：
```ts
const knownRefs = new Map([...evidenceRefs, ...sourceRefs, ...pickedRefs]
  .filter(ref => ref && ref.kind && ref.id)
  .map(ref => [refKey(ref), ref]));
```
```ts
const conflictingTypes = [...new Set(candidates.map(c => c.suggestedType))];
```

**为什么用它们**：
- `Map` —— 需要按 key 快速查找（O(1)），且 key 是构造出来的字符串
- `Set` —— 去重

**不懂它容易犯的错**：用数组 + `includes()` 做查找，
数据量大时 O(n²)。这正是经历 6 里的性能问题。

---

## J4 · Promise 与跨进程异步

**我的代码**：
```js
const result = await window.cogseed.invoke('recall.candidates.update', payload);
```

**为什么必须是异步的**：这是**跨进程**调用（renderer → main）。
进程之间只能传消息，没有同步返回值。

**这不是风格选择，是物理约束。**

---

## J5 · 事件委托

**我的代码**：
```js
const recallAction = event.target.closest('[data-recall-candidate-action]');
```

**为什么这样写**：列表项是动态渲染的，
逐个绑定监听器意味着每次重绘都要重新绑。
委托到父容器上，只绑一次。

**不懂它容易犯的错**：用 `event.currentTarget`（是绑定监听器的那个元素），
而不是 `event.target`（是真正被点击的元素）。

**关键**：**从元素自身开始匹配**。

# 四、Electron

## E1 · 主进程 / 渲染进程

**为什么存在**：渲染进程跑在浏览器沙箱里（安全），主进程有完整 Node 能力（危险）。

**在这个项目里**：
```
src/renderer/    渲染进程，纯 HTML/CSS/JS，无框架无打包器
src/main/        主进程，TypeScript
src/main/preload.js  桥梁
```

**不懂它容易犯的错**：在渲染层写 `require('fs')`，然后困惑为什么报错。

---

## E2 · contextBridge 与 allow-list

**我的代码**：
```js
// src/main/preload.js
function invoke(channel, payload) {
  return ipcRenderer.invoke('cogseed.invoke', { channel, payload: payload || {} });
}
```

**为什么必须是白名单**：渲染层加载的可能是不可信内容
（比如用户生成的 artifact）。如果它能拿到完整 Node 能力，
就等于拿到了整台电脑。

**项目规则**（AGENTS.md）：
> Renderer access goes through the canonical contextBridge allow-list API
> `window.cogseed.{invoke, stream}`

---

## E3 · preload 必须是 `.js`

**项目规则**：
> `src/main/preload.js` must remain `.js`; preload does not run the tsx hook.

**为什么**：preload 在渲染进程启动前加载，那时 TypeScript 的运行时转译还没就绪。

# 五、后端分层

## B1 · IPC 层只校验不做业务

**项目规则**（AGENTS.md）：
> `ipc/`: validate args and call features; **no business logic**.

**我的代码**：
```ts
'recall.candidates.update': async ({ candidateId, ... } = {}, ctx) => {
  if (!safeId(candidateId)) throw new Error('invalid recall candidate update');
  return { ok: true, candidate: await recallCandidates.updateRecallCandidate(ctx.userId, candidateId, {...}) };
},
```

**为什么业务逻辑不能放这**：同一个业务能力有多个入口
（用户点击、KStar 线、会话线、重试）。放在 IPC 层，其他入口就绕过去了。

**这正是 `promotion.ts` 存在的理由**：
> 晋升入口不止一个——会话线、KStar 线、用户手动确认、失败重试。

---

## B2 · Repository 模式（这个项目的变体）

**我的代码**：`store.ts` 的 `updateRecallJsonRecord` / `writeRecallJsonRecord` / `appendRecallJsonlRecord`

**它负责什么**：路径解析、并发锁、写前校验。
**它不负责什么**：任何业务判断。

**为什么要分出来**：如果每个 service 自己拼路径、自己读写文件，
那么「所有记录写前必须校验」这条规则就守不住了。

---

## B3 · 唯一闸门（choke point）

**我的代码**：`formal-assets/promotion.ts::validatePromotionByAssetType`

**为什么这个概念重要**：
一个必须永远成立的规则，只能写在**一个**地方，
且所有路径都必须经过它。

**你用了三次**：promotion（晋升）、candidate-capabilities（用户能力）、
source-catalog（存在性）。

**我的代码**：

以及 `1eb0b6d0` 的迁移：
> 修完就没有符合判据的记录，重启再跑是空转。

## B8 · 文件锁与 lost update

**我的代码**：
```ts
return fileEditLock(recordPath).runExclusive(async () => {
  const current = await read(...);
  const next = await updater(current);
  await writeJson(recordPath, next);
});
```

**不加锁会怎样**：两个并发请求各读一份旧值，各写一次，后写的覆盖先写的。

**为什么 `updater` 是回调**：因为读和写必须在同一把锁里。
拆成两个 API 调用，锁就跨不过去了。

# 六、数据与持久化

## D1 · JSON vs JSONL

| | `.json` | `.jsonl` |
|---|---|---|
| 形态 | 一条记录一个文件 | 一行一条记录 |
| 操作 | 读-改-写 | 只追加 |
| 并发 | 需要文件锁 | 天然安全（单次 write 原子） |
| 你的例子 | `candidates/<id>.json` | `versions/<id>.jsonl`、`audit/<id>.jsonl` |

**为什么审计和版本用 JSONL**：它们本质上是**事件日志**，
只追加、不修改。

---

## D2 · 数据域划分

**项目规则**：
```
data/<uid>/cloud/    可同步的用户私有状态
```

**我碰到它的地方**：`debb7f6a` 的 M-7

**不懂它容易犯的错**：把证明链写进 `local/`，用户换电脑证据就没了。

## D3 · 数据迁移

## D4 · 内容哈希

**我的代码**（`e11e22c5`）：
> `content_hash` 覆盖 `type/title/statement/scope/version`，**不只是版本号**：
> 历史数据里存在改了正文没动版本的记录，只比版本号发现不了漂移。

**原则**：校验和要覆盖**你真正关心的内容**，不是覆盖一个代表它的标识。

# 七、AI 系统领域概念

这些不是通用技术，是**这个产品的领域概念**。但它们是你的核心资产。

## AI1 · Candidate（候选）

系统观察到的、**还没被用户确认**的认知。

**关键**：候选不是资产。它的生命周期到「确认」为止，
之后的修改走正式资产的版本链。

---

## AI2 · Ability Asset（能力资产）

用户确认后的正式认知。四类：

| 类型 | 最低准入门槛（PRD 3.1） |
|---|---|
| `personal` | 身份/角色/偏好/关系/长期环境与边界 |
| `rule` | 用户确认来源、作用域、**适用与禁止范围** |
| `template` | 用户确认**可复用结构**、来源、敏感边界、适用范围 |
| `skill_method` | Goal / Action Plan / 输入输出 / Ontology Binding / 工具 / 流程 / Evaluation |

---

## AI3 · Maturity（成熟度）

`seed → bud → transfer_validated → effectiveness_validated → stable`

**回答的问题**：这条资产**验证到哪一步了**。

**和 lifecycleStatus 正交**（后者回答「谁写进来的」）。

**我碰到它的地方**：经历 2 —— 这两个字段自相矛盾就是那个 bug。

---

## AI4 · Evidence / Proof（证据与证明）

```
证据（evidence）  这条认知是从哪来的（来源引用）
迁移证明（transfer proof）    它被真的带进任务了吗
效果证明（effectiveness proof） 带进去之后效果变好了吗
复用回执（reuse receipt）      本回合真的注入了这几条（事实记录）
```

**我碰到它的地方**：经历 4 —— 回执缺失导致效果证明全部失败。

---

## AI5 · Projection（投影）

**回答的问题**：**这一次任务**该带哪些认知。

**关键设计**：用户确认投影时**冻结资产版本快照**。
资产之后改版了，Runtime 仍注入确认时的版本 ——
**不能在用户背后换掉他确认过的内容**。

---

## AI6 · Scope / Policy（作用域与策略）

`resolveDefaultUsePolicy(maturity, lifecycleStatus, status) → never | ask | always`

**我碰到它的地方**：经历 2 的死锁环里，`seed → never` 是环的一段。

---

## AI7 · 出生继承（Agent Inheritance）

一个 Agent 被创建时继承哪些认知。

**关键设计**（`e11e22c5`）：
- 存资产引用（`asset_id` + `version` + `content_hash`），不内嵌能力包
- 没带走的要记**原因**（6 种）

# 九、i18n

## I1 · 文案要改在 locale 上，不是代码 fallback

**我碰到它的地方**：`0b1acf82`
> 「非正常状态」→「需要关注」改在 **locale 上**，代码 fallback 改不动它。

**为什么**：代码里的 `_t('key', '默认文案')` 第二个参数只在 key 缺失时生效。
key 存在时改它没有任何效果。

## I2 · i18n 覆盖门禁

**我的代码**：`cognition-i18n-coverage.test.ts`

**它守什么**：认知域用到的每一个 key，四种语言都必须有。

**扩展的难点**（`6b76ea94`）：门禁原本只扫 `_cognitionText(` / `_t(` / `t(` 三种写法，
但代码里还有 `_tv` / `_label(` / `titleKey` 属性式 / 变量间接取词。

**你的处理**：把间接取词**内联成直接调用**，让门禁能扫到。
—— 为了让检查生效，去改被检查的代码。
