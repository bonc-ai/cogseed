# 经历 1 · 页面卡住，修完才发现后面还堵着两个

**涉及提交**：`d881aab8` → `3e80ec87` → `220fa035`（缺陷 2）
**时间**：08-17 至 08-18

## 我当时在解决什么

打开认知资产页面，**永远显示「加载中」**，什么都不出来。

这是一个实机问题——自动化测试全绿，但真的打开应用就是转圈。

## 我当时为什么会觉得这里有问题

**从提交和修复路径推测**：

第一直觉一定是「IPC 没返回」或者「后端挂了」。
但如果去查，会发现**后端一次都没被调用过**——网络/IPC 层面完全安静。

这个观察把问题锁死在渲染层：不是请求失败，是**请求根本没发出去**。

## 真正的根因是什么

```js
// 初始化里的写法
_skillsCognitionState.loading = true;   // ① 为了首屏就显示加载态
loadSkillsCognitionSnapshot();          // ② 但这个函数第一行是 if (loading) return
```

`loading` 这一个变量，同时被当作两个东西用：

| 用途 | 谁在用 | 语义 |
|---|---|---|
| UI 状态 | 渲染函数 | 要不要显示「加载中」 |
| 函数重入锁 | `loadSkillsCognitionSnapshot` | 防止并发重复拉取 |

初始化为了达成用途 1 手动置真，结果**撞上了用途 2 的重入锁**：

```
loading = true
   → loadSnapshot() 第一行 return，什么都不做
   → 快照永远不加载
   → loadedAt 永远是 0
   → _cognitionSnapshotPending() 永远为真
   → 永久「加载中」
```

**这是一个自己造出来的死锁。**

## 我最后改了什么

`src/renderer/modules/skills.js`——**调换顺序，不加新标志位**：

```js
loadSkillsCognitionSnapshot();   // 先调用
render();                        // 再渲染
```

## 为什么这个修改能解决问题

关键在 JS 的一个机制：**async 函数在遇到第一个 `await` 之前是同步执行的。**

```js
async function loadSkillsCognitionSnapshot() {
  if (_skillsCognitionState.loading) return;
  _skillsCognitionState.loading = true;      // ← 这一行是同步跑的
  const data = await window.cogseed.invoke(...); // ← 从这里才异步
  ...
}
```

所以调用它之后**立刻返回的那一瞬间**，`loading` 已经是 `true` 了。
后面的 `render()` 拿到的就已经是加载态。

**既满足了首屏显示加载态，又没有碰重入锁。**

你自己在 commit body 里写的：
> 修法是调换顺序而不是加新标志位。

## 然后：修完这个，才走得到下一个 bug

修好加载后，页面终于能打开，进入候选详情，点「确认并限域」——
**后端报 `invalid recall candidate update`。**

### 这个新 bug 的根因

```js
recallAction.closest('[data-recall-candidate-id]')
```

**`Element.closest()` 是从元素自身开始匹配的**，然后才向上找父节点。

而列表页和详情页的 DOM 结构是这样的：

```html
<div data-recall-candidate-id="c-123">      ← 外层容器（编辑字段在这里）
  <input data-recall-edit-judgment>
  <input data-recall-edit-scope>
  <button data-recall-candidate-id="c-123"  ← 按钮上也带！
          data-recall-candidate-action="save-and-promote">确认并限域</button>
</div>
```

于是 `closest()` 直接返回**按钮自己**。按钮里没有任何 `data-recall-edit-*` 字段
→ `judgment` 和 `suggestedType` 全读成空串 → IPC 参数校验直接拒绝。

**后端拒得完全正确。前端发过去的确实就是空串。**

### 修法

```js
const parent = recallAction.parentElement;
const card = parent.closest('[data-recall-candidate-id]');   // 从父节点起找，跳过按钮自身
```

### 这个 bug 最值得学的地方

你在 commit body 里写下的这句话：

> **这不是本分支引入的**：绑定侧来自 `e4782aa3`，详情页按钮带 id 来自 `3118c79e`，
> **两边各自都合理，凑在一起才坏**。

以及：

> 此前它一直够不到——认知资产页被上一个 loading 死锁挡住，根本走不到候选详情。

**两个各自正确的改动，组合起来是错的。** 单看任何一个 diff 都发现不了。
而且它被前一个 bug 遮蔽了，直到你把前一个修好才暴露出来。

## 然后：真机验收发现同一条路径还在丢数据

`220fa035` 缺陷 2：

```
候选详情页**没有**「适用范围 / 禁止范围」这两个输入框
   ↓
但提交时无条件读取选择器，读不到就当成空数组提交
   ↓
实机上有带 2 条适用 + 2 条禁止的候选
   ↓
一次「确认并限域」→ 边界被清空
   ↓
晋升出来的规则也就没了边界
```

修法：

```js
const conditionLines = (selector, current) => {
  const el = card.querySelector(selector);
  if (!el) return Array.isArray(current) ? current : [];  // ← 页面没渲染 → 保持原值
  return String(el.value || '').split('\n').map(v => v.trim()).filter(Boolean);
};
```

**这条纪律你要记住一辈子**：

> **DOM 里没有这个框 ≠ 用户想把它清空。**

同一个 commit 里还有一处同样形状的防御：

```js
// 容器可能没有 querySelectorAll（旧渲染路径/精简容器）。
// 缺方法就当"这一屏没渲染证据区"，沿用候选原有引用——
// 绝不能让取不到 DOM 变成"清空证据"。
```

## 我当时实际上碰到了哪些技术知识

| 知识点 | 出现在哪 |
|---|---|
| **async 函数的同步前缀** | 修法成立的全部理由 |
| **重入锁 / 幂等保护** | `if (loading) return` 的本意 |
| **单一职责（变量级）** | 一个变量两个语义 = 定时炸弹 |
| **DOM 事件委托** | `event.target.closest('[data-...]')` |
| **`Element.closest()` 语义** | 包含自身，这是坑的来源 |
| **`data-*` 属性作为视图与逻辑的契约** | 按钮和容器都带同一个 attr 就出事 |
| **fail-safe 默认值设计** | 读不到 → 保持原值，而不是清空 |
| **回归测试（regression test）** | 三个 bug 各补了一条 |

**我当时大概率已经理解的**：
- 「后端没被调用」说明问题在前端，这个推理是对的

  而不是一个有确定性保证的修法。

**AI 帮我跨过去、现在值得重新学的**：
- `Element.closest()` 的精确语义（含自身、向上遍历、匹配的是选择器不是属性名）

**目前仍然明显缺基础的**：
- **JS 事件循环（Event Loop）与微任务队列**。

# 经历 2 · 资产存下来了，但永远不会被用 ⭐

**涉及提交**：`2854f1f9`（加选择层）→ `33a16ade`（修新数据）→ `1eb0b6d0`（修存量数据）
**时间**：08-13

> **如果这套档案你只读一段，读这一段。**
> 它包含了你这段时间形成的全部思维模式。

## 我当时在解决什么

我刚做完「选择层」——从 Agent 的出生继承里算出**这一次任务真该用哪几条认知**。

做完之后去验证，发现一个更严重的问题：

**当前主线上，每一条新沉淀的资产，都永远不会被自动带入任何 Agent。**

不是偶尔，不是某些条件下——是**每一条，永远**。

界面上一切正常：确认成功了、资产列表里有、详情页能打开。
但「已验证资产」永远是 0，Agent 的提示词里从来不出现它们。

## 我当时为什么会觉得这里有问题

这一次的判断过程可以从 commit body 直接读出来，**不是推测**：

> 接上选择层之后暴露的死锁

也就是说：**你是在做另一件事的时候，把这个问题逼出来的。**

选择层的职责是「从候选池里挑出这次该用的」。你接上它之后去验证输出，
发现挑出来的**永远是空**。往上追一层，发现使用策略（use policy）对这批资产
一律返回 `never`。再往上追，发现它们的成熟度全是 `seed`。

## 真正的根因是什么

### 第一层：一个闭合的死锁环

```
    资产创建时 maturity = 'seed'
              ↓
    seed → use_policy 一律 never
              ↓
    永远不被注入任何 Agent
              ↓
    产生不了使用证据
              ↓
    做不了 transfer proof
              ↓
    升不到 transfer_validated
              ↓
    永远停在 seed  ──────┐
              ↑          │
              └──────────┘   ← 环闭合了
```

### 第二层：这个环没有任何出口

你去查了 `seed → bud` 有没有升档路径，结论是**没有**：

> `setAbilityAssetMaturity` 只有 `proof-service` 一个调用方，
> 且只能升到 `transfer_validated` / `effectiveness_validated`；
> `downgradeAbilityAssetMaturityForRevokedEvidence` 是降档。
> **没有 IPC 频道、没有 UI。**

**这一步的排查方法值得学**：怀疑一个状态出不去，就去找**所有能写这个字段的地方**，
逐个看它们能写出什么值。找完发现没有一个能写 `bud` —— 环就坐实了。

### 第三层：真正的根因不在策略，在归档

**这是整个 case 最精彩的地方。**

如果只看到前两层，最自然的修法是「放宽 use_policy，让 seed 也能被注入」
或者「补一条 seed → bud 的升档路径」。

**这两个都是修症状。**

你注意到的是：`promote` 的时候，代码写下的**两个字段自相矛盾**：

```
lifecycleStatus = 'user_confirmed_unverified'   ← 用户确认过了
maturity        = 'seed'                         ← 规范 10.2 里 seed 的定义是「Candidate 档」
```

而 `bud` 的定义原文是：

> 「User Confirmed / Unverified：用户确认了内容，不代表效果已验证」

**和 lifecycleStatus 说的是同一件事。**

你的原文结论：

> 候选在这个系统里是 `RecallCandidateRecord`，不是已 promote 的资产。
> 资产走到 `createAbilityAsset` 时用户确认那一关**已经过了**，再归进候选档是错的。
> 所以这**不是放宽策略，是把归档纠正到它本来该在的那一级**。

## 我最后改了什么

**分成两步，这个拆分本身就是教材。**

### 第一步 `33a16ade`：修新数据

`asset-service.ts` + `candidate-service.ts`：新沉淀的资产起点从 `seed` 改为 `bud`。

### 第二步 `1eb0b6d0`：修存量数据

新数据修好了，但**已经存在的资产还卡在 seed，而且没有任何路径能救它们**。

判据不是「凡 seed 皆升」，而是**那对矛盾本身**：

```
lifecycleStatus === 'user_confirmed_unverified'  且  maturity === 'seed'
```

> 满足这两条的资产，它的 seed 是 promote 时**系统写错的**——
> lifecycleStatus 已经说了用户确认过，maturity 却归在候选档。
> **让用户逐条去修系统的错不合理。**
>
> 其余一概不碰：已撤销、已彻底清除、已经是 bud 以上的。

### 三个附加决策，每一个都值得单独学

**① 审计写 `maturity_corrected`，不复用升档语义**

> 这是修正归档错误，不是靠证据挣来的晋级。
> 日后回看审计流时，**不能让人以为这条资产做过 transfer proof**。

**② 放在启动任务里，而不是一次性脚本**

> **脚本只修得了这一台机器。** 其他人机器上同样有归错档的资产，得跟着版本走。
> 按规范注册进 `boot_init` 的 deferred 阶段（重磁盘档，跟着其他扫描一起）。

**③ 幂等 + 单条失败不阻断**

> 修完就没有符合判据的记录，重启再跑是空转，测试里验证了不会重复写审计。
> 单条修不动只 warn 跳过——它下次启动还会被扫到，**不该拦住其余的**。

## 为什么这个修改能解决问题

因为它**打断了环的成因，而不是给环开一个后门**。

```
改动前：资产被错误地归进「候选档」→ 策略正确地拒绝注入 → 环闭合
改动后：资产被正确地归进「用户已确认档」→ 策略正确地允许注入 → 环不成立
```

注意：`use_policy` 一个字没改。策略从头到尾都是对的——
**它只是在正确地执行一个错误的输入。**

## 为什么这个修改能解决问题

因为它把「两处独立判断」变成了「一处判断 + 一处投影」：

```
改动前：UI 判据 ≠ 后端闸门        → 必然分叉，只是时间问题
改动后：UI 判据 = 调用后端闸门的同一个函数  → 结构上不可能分叉
```

**关键设计：这一层是纯投影，不落盘。**

## 一个必须理解的分层细节：跨候选判断为什么要从外面传进来

有一类不合格是**单条候选算不出来的**：同一句话被分成了两种类型
（一条判成 rule、另一条判成 template）——说明至少有一边分错了。

```ts
/**
 * 候选池里同文本、不同类型的其它条目的类型。跨候选判断，单条算不出来，
 * 必须由持有完整候选列表的读口（recall.candidates.list、inbox adapter、
 * tree）算好传进来——promoteRecallCandidate 也是这么算的。不传 = 不判冲突。

conflictingTypes?: readonly string[];
```

**这是一个非常重要的分层思想**：

> **一个纯函数不应该自己去查数据库。**
> 需要全局信息时，让调用方查好传进来。

好处：这个函数可测试、无副作用、可以在任何地方调用（包括渲染层的运行时投影）。
如果它自己去 `await listRecallCandidates()`，它就变成异步的、有 IO 的、难测的。

## 真正的根因是什么

**两处，都不在报错的那一层。**

### 根因 1：两件不同的事共用了一道判断门

```js
// group_chat/bus.ts —— 错误的写法
if (state.taskRun) {
    落回执;               // ← 事实记录：本回合真的注入了这几条
    登记 reuseTurnIds;    // ← 运行簿记：这次任务用到了哪些回合
}
```

你的判断（原文）：

> 回执记的是「本回合真的注入了这几条」这个**事实**，
> 与此刻有没有开着任务运行**无关**；`reuseTurnIds` 才是运行簿记。
> 合成一道门的结果是**注入过却没有加载凭证**，终态自然找不到，
> 连 M-6 恢复也只能去扫不存在的回执。

**「事实」和「簿记」是两种不同性质的数据**：

| | 回执（receipt） | 运行簿记（reuseTurnIds） |
|---|---|---|
| 记录什么 | 一个已发生的事实 | 一次运行的账目 |
| 条件 | 注入发生了就该记 | 只有在任务运行时才有意义 |
| 能不能事后补 | 不能（事实错过就没了） | 能（可以重新汇总） |

**把它们放进同一个 `if` 里，等于用后者的条件去限制前者的记录。**

### 你找到了一个「已经做对的参照系」

> 出生继承那条路径（`recordInheritedCognitionReuse`）**本来就是**
> 「回执无条件落、只有簿记看 taskRun」的形状。

**这是排查里非常有效的一招**：
系统里同一件事如果有多个实现，先找那个**已经对的**，然后问「为什么这条不一样」。

### 根因 2：第二条路径根本没接

> CogSeed Runtime 那条路径**注入了资产却从不落回执**
> （全仓 `prepareReceipt` 调用方此前**只在 `bus.ts`**），
> 且 `cogseed_backend/recall-bridge` 的终态事件不传 `reuse_turn_ids`

**「全仓 prepareReceipt 调用方只在 bus.ts」这句话是怎么得到的**：
一次 `grep -rn "prepareReceipt" src/`。

> **这是你要养成的第一反射**：
> 怀疑「某个功能漏了一条路径」时，去搜关键函数的**全部调用方**。
> 调用方少于你预期的路径数量，就是漏接。

# 经历 6 · 来源多的用户才会出错

**涉及提交**：`3672427d`（证据引用改受控选择）→ `2ebc0d55`（存在性校验不依赖展示窗口）
**时间**：08-19

## 我当时在解决什么

这个问题分两步出现，**是我自己的上一个改动引出来的**。

### 第一步：我把证据引用改成受控选择

原来候选详情页的「证据引用」是**自由输入**——用户可以随便打一个 id 进去。

问题在于：证据是否非空，是「这条候选能不能确认」的判据之一。
自由输入意味着**用户可以凭空造一条 ref 来满足这个判据**。

于是 `3672427d` 把它改成：只读展示 + 逐条删除 + 从来源列表里挑，
并在服务端加了一道校验——新加的 ref 必须在来源目录里查得到，
查不到就报 `recall_candidate_unknown_source`。

### 第二步：这道新校验本身是错的

实机上出现：用户从来源列表里**正常挑选**的一条来源，
被判成「未知来源」拒绝掉。

## 我当时为什么会觉得这里有问题

**从提交和修复路径推测**：

这个 bug 有一个非常明显的特征——**只有来源多的用户才会遇到**。
来源少的时候完全正常。

「数据量到某个规模才出错」这个模式，几乎总是指向**分页 / 截断 / 限制**。

## 真正的根因是什么

```ts
// assertResolvableNewSourceRefs —— 错误的写法
const known = listCognitionSources(userId, { limit: 100 });   // 取前 100 条
if (!known.has(ref.id)) throw recall_candidate_unknown_source; // 不在前 100 条 = 不存在
```

`limit: 100` 的上限就是 100，而且是在 adapter **内部**截断的
（`conversations.slice(0, query.limit)`、`files.slice(0, query.limit)`）。

**这段代码把「展示分页」伪装成了「真实性结论」。**

用户的第 101 条来源，明明存在，但因为不在展示窗口里，被判为不存在。

### 为什么这是一类通病，不是一次手滑

你自己在 commit body 里指出了两件事：

**① 调大 limit 不是解法**
> 调大 limit 只是推迟，不是根治。

**② 同一个错误在代码库里出现了两次**
> 仓库原有的 `resolveCognitionSource` 带着**同一个 bug**（limit: 100）。

同一个错误出现两次，说明这是**思维模式问题**：

```
我需要判断 X 是否存在
   ↓
手边正好有个 list API
   ↓
调它，在返回结果里找
   ↓
【只要那个 list API 有分页，这个判断就是错的】
```

## 我最后改了什么

**没有改 limit，而是新增了一个职责明确的能力**：

```
listCognitionSources           → UI 列表展示，可以有 limit
cognitionExistingSourceIds     → ★ 服务端真实性判定，不依赖展示窗口
assertResolvableNewSourceRefs  → 只调用存在性能力，不再自己构造前 100 条 key 集合
```

新函数 `cognitionExistingSourceIds(userId, kind, ids)` 的实现要点：

- **不设 limit**（`Number.MAX_SAFE_INTEGER`，即无窗口）
- **先用 `source-control` 记录答一批**（暂停/移除过的来源确实存在过），全齐则直接返回
- 否则按 kind **枚举一次**底层来源，命中即收，本批齐了就 `break`
- **读失败时不武断判「不存在」**，交调用方按「无法确认」处理
- **不建第二套 registry、不缓存真值**

### 一个诚实的限制说明

> 多数来源 id 是 `stableId('msg', conversationId, messageId)` 这类**单向哈希**，
> 无法从 id 反解原记录，所以枚举是当前能做到的最精确形式；
> **要做到 O(1) 需要先给来源建索引，那是另一件事。**

**明确说出「这个方案的上限在哪、要更好需要做什么」**——
这是成熟工程师的写法，而不是假装方案是完美的。

### 顺带的性能修复

> assert 先按 kind 归并再查，一个 kind 只枚举一次；
> 此前逐条调用会让新增 N 条同类引用时全量扫 N 遍。

从 `O(N × 全量)` 降到 `O(kind 数 × 全量)`。

## 为什么这个修改能解决问题

因为它把**两个不同的问题分给了两个不同的函数**：

| 问题 | 谁回答 | 能不能有 limit |
|---|---|---|
| 「给用户看哪些来源？」 | `listCognitionSources` | 能，而且应该有 |
| 「这个 id 到底存不存在？」 | `cognitionExistingSourceIds` | **不能** |

以前是同一个函数回答两个问题，于是第二个问题被第一个问题的分页污染了。

## 真正的根因是什么（git 的机制）

git 的 merge 是基于**提交祖先关系**的，不是基于文件内容。

```
主线:   A ── B ─────── M ────── R
                      /
分支:       C ── D ──┘

M = merge commit（把 C、D 合进主线）
R = 撤销 M（把 C、D 带来的【内容变更】撤销）
```

**关键**：R 撤销的是**内容**，不是**祖先关系**。

在 R 之后，`C` 和 `D` **仍然是主线的祖先**（通过 M 这条路径）。

于是当你再次 `git merge 分支` 时：

```
git merge-base 主线 分支  →  D 本身
   ↓
git 认为：分支上的所有提交都已经在主线里了
   ↓
Already up to date，什么都不做
```

**而实际内容早就被 R 删掉了。**

### 三种正确的处理方式

| 方案 | 做法 | 什么时候用 |
|---|---|---|
| A. 撤销那次撤销 | `git revert R` | 原撤销是误操作，代码本身没问题 |
| B. 手动重做 | 在新分支上重新实现 | 原代码需要按新契约调整 ← **你选的** |
| C. 挑单个提交 | `git cherry-pick C D` | 只需要其中几个 |

**缺陷**：资产编辑器打开时，三个输入框全是空的；用户一保存，

```
     ↓

     ↓

```

**为什么测试没抓到**（你的原文）：

```
     ↓
```

> 实机 32 条 capture 里 10 条 no_candidate，**系统里没有任何地方记着原因**。

10/32 是一个很高的比例。如果这 10 次都是「内容里确实没东西可沉淀」，那没问题；
但如果其中有一部分是**系统自己的解析出了错**，那就是在悄悄丢数据。

**而当前的代码根本无法区分这两种情况。**

## 真正的根因是什么

```js
// 错误的写法
filterReason = parsed.length === 0 ? 'model_no_candidate' : ...
```

只按 `parsed.length` 二分，于是**两件性质完全相反的事落进同一个码**：

| 实际发生的事 | 该怎么处理 |
|---|---|
| 模型显式判空：内容里确实没有可沉淀的东西 | **正常**，不用管 |
| 候选被逐条丢弃：模型抽出来了，解析侧没接住（`suggestedType` 非法等） | **是 bug**，该去修 schema 或提示词 |

你的判断（原文）：

> 后者本该去修 schema 或提示词，**混在 `model_no_candidate` 里就永远看不见**。

**这是一个「可观测性（observability）」问题**：
不是功能坏了，是**你没法知道它有没有坏**。

## 我最后改了什么

### ① 拆出真正的判据：模型「声称」产出了几条

```ts
新增 parseRecallCaptureResult() → { candidates, emittedCount, noCandidateReason }
```

`emittedCount` 是模型**声称**产出的条数。

> **与 `candidates` 长度不等即说明是解析侧丢的。**

这一个字段就把两种情况分开了：

```
emittedCount = 0，candidates = 0   →  模型判空（正常）
emittedCount = 3，candidates = 0   →  解析侧丢了 3 条（是 bug）
```

### ② 新增一个独立的原因码

```
model_no_candidate      模型显式判空
candidate_unparsable    ★ 新增：抽出来了但解析侧没接住
```

### ③ 让模型自己说原因

提取提示词改成要求空返回时一并给出理由：

```json
{"candidates": [], "reason": "一句话说明缺了什么"}
```

用会话语言书写。

**并且做了向后兼容**：

> 模型不给也**不算解析失败**（旧记录/旧提示词没有该字段），只是那条说不出所以然。

### ④ 保留旧签名

> 旧签名 `parseRecallCaptureOutput` 保留为**薄封装**
> （多处单测直接断言它，且它是纯函数）。

**又一次「新增而不是修改」**——和经历 4 里
`buildConfirmedProjectionPromptContext` 的处理是同一个手法。

## 为什么这个修改能解决问题

因为它让**两种不同的失败变得可区分**。

区分之后：
- `model_no_candidate` 的那些 → 忽略，正常
- `candidate_unparsable` 的那些 → 有了明确的修复目标（schema 或提示词）

**修改本身没有让抓取变得更准，但它让「抓取哪里不准」变得可见。**

这是可观测性工作的典型价值：**不解决问题，但让问题可被解决。**

## 我当时实际上碰到了哪些技术知识

| 知识点 | 出现在哪 |
|---|---|
| **可观测性（observability）** | 整个 case 的主题 |
| **错误分类的粒度** | 一个码 → 两个码 |
| **声明值 vs 实际值的比对** | `emittedCount` vs `candidates.length` |
| **LLM 结构化输出（structured output）** | 要求模型返回 `{candidates, reason}` |
| **schema 校验与解析失败** | `suggestedType` 非法导致逐条丢弃 |
| **向后兼容的字段新增** | 旧记录没有该字段不算失败 |
| **薄封装（thin wrapper）保持旧 API** | `parseRecallCaptureOutput` |
| **字段的形状校验与长度上限** | `noCandidateReason` 上限 500 字符 |

## 哪些部分我当时可能只是「会判断，不是真懂」

**我当时大概率已经理解的**：
- 「两件相反的事落进同一个码」——这个观察非常准确
