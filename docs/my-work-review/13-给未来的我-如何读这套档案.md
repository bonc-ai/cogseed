# 13 · 给未来的我：如何读这套档案

写给几个月后打开这份文件的你。

---

## 先说清楚这套档案是干什么的

**它不是用来证明你做了多少工作的。**

它是把你「靠判断力和 AI 一起完成、但没有真正学懂」的那段真实工程经历，
拆开、讲清楚、变回你自己的能力。

所以读它的方式和读技术文档不一样：
**你不是在学新东西，你是在认领本来就属于你的东西。**

---

## 第一天看什么

**不要打开代码。不要从第 01 篇按顺序读。**

按这个顺序，大约两小时：

| 顺序 | 读什么 | 为什么 |
|---|---|---|
| 1 | [01-我这段时间到底做了什么](01-我这段时间到底做了什么.md) | 先把整体印象建立起来 |
| 2 | [03](03-我经历过的核心问题.md) 的**经历 2**（资产存下来了但永远不会被用） | 它包含了你几乎所有的思维模式 |
| 3 | [06-我的工程思维是怎么变化的](06-我的工程思维是怎么变化的.md) | 看你自己是怎么长起来的 |

**第一天的目标只有一个**：产生「哦，原来我当时是在解决这个」的感觉。

**第一天不要做的事**：
- 不要打开 IDE
- 不要试图记住任何 API
- 不要因为看到「我没学会的东西」那份清单而焦虑

## 遇到看不懂的代码怎么办

按这个顺序，**不要跳步**：

### 第 1 步 · 先确认你在看哪一层

打开 [08](08-把我的工作放回整个项目里.md) 的分层规则，
确认这段代码属于哪一层（ipc / features / store / renderer）。

**很多「看不懂」其实是「不知道它该负责什么」。**

### 第 2 步 · 读它的注释，不是读它的代码

你写的代码注释密度很高，而且注释写的是**「为什么」**不是「是什么」。

比如 `candidate-capabilities.ts` 的头部注释，
它直接告诉你这一层为什么存在、以及两条绝对不能违反的规则。

**先读完注释，再看代码，通常就懂了一半。**

### 第 3 步 · 找到它对应的 commit，读 body

```bash
git log --oneline -- <文件路径>          # 找到相关的 commit
git log -1 --format='%B' <hash>          # 读完整 body
```

**你的 commit body 是这套档案最有价值的原始材料。**
它记录了当时的现象、诊断过程、根因、以及守住了什么边界。

### 第 4 步 · 找到它的测试

```bash
ls test/ | grep <相关关键词>
```

**测试是可执行的文档。** 它告诉你这段代码「在什么输入下该给什么输出」。

### 第 5 步 · 还是不懂，就把它标记下来，跳过

**这不是考试。** 标记下来，继续往下走。
很多东西在你读完后面的部分之后会自己变清楚。

### 第 6 步 · 允许问 AI「这是什么概念」，不允许问「帮我解释这段代码」

这个区别很重要：

| ✅ 可以问 | ❌ 不要问 |
|---|---|
| 「什么是穷尽性检查？」 | 「帮我解释 candidate-capabilities.ts」 |
| 「Element.closest 的语义是什么？」 | 「这个函数在干什么？」 |
| 「文件锁解决什么问题？」 | 「这段代码为什么这么写？」 |

**左边那类问题补的是你的知识，右边那类问题只是又一次让 AI 替你理解。**

## 每读一个 commit 应该问什么

按顺序问这四个问题：

### 1. 当时用户看到的现象是什么？

**如果答不出来，说明你在读代码而不是在读问题。**

回去读 commit body 的第一段——你当时通常都写了。

### 2. 我是怎么从现象定位到根因的？

body 里通常记录了这个过程。

**注意那些数字**：「26 次注入 / 4 张回执」「32 条 capture 里 10 条」——
这些是你当时的定位手段。

### 3. 如果现在让我重新修，我会怎么修？

**先自己想一个方案，再看实际的 diff。**

如果你的方案和实际的不一样，问一句「为什么当时选了那个」——
答案通常在 body 里。

### 4. 这个改动**没有**做什么？

**这一问最重要，而且最容易被跳过。**

例子：
- `4e8d937d` —— **promotion.ts 一个字没动**
- `5bcce94d` —— **targetAgentIds 不恢复**
- `231ff5be` —— **没有为了让链路变绿而伪造任何加载事实**
- `6b76ea94` —— **全库其他域的缺口不在本提交内**

**「没做什么」往往比「做了什么」更能说明工程判断。**

## 怎么从「我记得这个 bug」走到「我真正理解这个 bug」

这中间有五个台阶。**大部分人停在第二级。**

```
第 1 级 · 我记得有这么个 bug
          「哦对，就是那个加载中的问题」
              ↓
第 2 级 · 我知道当时是怎么修的
          「把两行代码调换了顺序」
              ↓   ← 大部分人停在这里
第 3 级 · 我知道为什么那样修有效
          「因为 async 函数在第一个 await 之前是同步的」
              ↓
第 4 级 · 我能说出根因的类别
          「一个变量承担了两个职责」
              ↓
第 5 级 · 我能在新场景里认出同一类问题
          「这里的 isLoading 也同时在当锁用，迟早出事」
```

### 怎么爬这五级

**从第 2 级到第 3 级**：问「如果不这样修，还有别的修法吗？为什么当时不选？」

对于加载死锁：加一个 `isInitializing` 标志位也能修。
**为什么当时没选？** 因为那是绕过问题，而不是消除问题（变量还是有两个职责）。

**从第 3 级到第 4 级**：在 [04-我的Debug案例集](04-我的Debug案例集.md)
里找到这个 bug 对应的「模式」，看它的抽象描述。

**从第 4 级到第 5 级**：拿这个模式去审别的代码。

比如学完「一个变量两个职责」之后，
去 `grep` 一下项目里其他的 `loading` / `busy` / `pending` 变量，
看有没有同样的问题。

**能在新地方找到同类问题，才算真的会了。**

## 怎么判断自己是真的学懂，而不是重新看懂了 AI 的解释

这是这份文档里最重要的一节。

### 这套档案本身就有这个风险

**你现在读的这份档案，也是 AI 写的。**

如果你读完觉得「都懂了」，那很可能只是**又一次看懂了 AI 的解释**，
而不是学会了。

### 三个检验方法

#### 检验 1 · 合上材料，讲给别人听

**关掉所有文档和代码**，向一个不了解这个项目的人讲清楚：

> 「为什么资产被存下来了，却永远不会被 Agent 用到？」

讲的时候如果出现下面这些情况，说明你没学会：
- 需要「等一下我看看代码」
- 用了一堆项目专有名词但解释不了它们
- 讲到一半发现自己也不知道为什么

**能讲清楚 = 真的会了。**

#### 检验 2 · 把修复还原掉，预测会发生什么

挑一个 commit：

```bash
git show <hash>                    # 看 diff
```

**先不要看后面**，自己回答：
- 如果把这个修复 revert 掉，用户会看到什么现象？
- 对应的测试会以什么信息失败？

然后真的做一次：
```bash
git revert <hash> --no-commit      # 在临时分支上
npx vitest run <对应的测试文件>
git reset --hard                   # 恢复
```

**预测和实际一致 = 你真的理解了因果链。**

> ⚠️ 一定要在临时分支上做，做完 `git reset --hard` 恢复。

#### 检验 3 · 合上代码自己重写一遍

**这是最硬的标准。**

挑一个不太长的文件（比如 `store.ts` 的 `updateRecallJsonRecord`，只有 14 行），
合上它，自己重新写一遍。

**写不出来的地方，就是你真正不会的地方。**

不是「忘了 API 名字」那种不会，是「不知道为什么需要这一步」那种不会。

---

### 一个具体的自检清单

学完任何一段经历后，问自己：

| 问题 | 答不出来说明 |
|---|---|
| 用户看到的现象是什么？ | 你在读代码，没在读问题 |
| 根因在哪一层？ | 你还没建立分层心智模型 |
| 为什么这个修法有效？ | 你只记住了操作，没理解机制 |
| 这个改动**没做**什么？ | 你还没看到工程判断的部分 |
| 在别的地方见过同类问题吗？ | 你还停在第 4 级，没到第 5 级 |

**五个都能答 = 这一段真的学会了。**

## 几条给未来的你的提醒

### 提醒 1 · 你的判断力比你以为的强

这套档案里反复出现你的原话：

> 没有为了让链路变绿而伪造任何加载事实。

> 这条留给能力包交付那边决定，不在这里偷偷加回一个竞争字段。

> 一致是巧合不是设计。

**这些不是 AI 能替你想出来的。** 它们是产品判断、职业操守、和边界意识。

**不要因为「我不会写那些类型体操」就否定这些。**

### 提醒 2 · 你缺的是实现，不是判断，这是容易补的那一边

- 「判断力强、实现弱」→ 补实现（有明确目标，知道自己要什么）
- 「实现强、判断力弱」→ 补判断力（很难，需要大量踩坑）

**你在容易补的那一边。**

### 提醒 3 · 不要一次读完这套档案

它是按「一天学一小块」设计的。
连着读会让你产生「都懂了」的错觉，而那正是这套档案要解决的问题。

### 提醒 4 · 如果只能做一件事，做这个

**去把 [10](10-我的个人学习路线.md) 路线 C 阶段 3 的那个练习做了**：

> 独立给认知资产加一个新的治理动作（比如「标记为过时」），
> 从后端状态、策略、IPC、渲染层、四语文案到测试，全部自己做。
> **全程不问 AI「怎么写」。**

做完这一件事，胜过读十遍这套档案。

## 最后

这套档案的目的不是让你觉得自己很厉害，也不是让你觉得自己差得远。

**是让你准确地知道自己站在哪里。**

你现在的状态是：**判断力已经跑到了实现能力前面**。
这不是问题，这是一个很好的起点——
因为你已经知道要什么了，剩下的只是把手补上。
