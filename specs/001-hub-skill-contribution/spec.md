## 一句话说明

用户无论是否登录都能看到本机自定义 Skill 的「贡献」入口；未登录时点击弹出可复用的登录提示，按钮引导至 Web 登录。登录后，客户端核对并补齐提交资料，检查最终副本，让贡献者预览将发出的全部内容并完成来源声明、条款接受与维护责任确认后提交；贡献者在客户端「我的贡献」中看到提交与审核状态、提交新版本、申请撤回。审核、发布、目录、安装、更新、停用全部在 Hub 侧与迭代一链路完成，本文不重复其规则。只做 Skill。

| FR-001、FR-003～FR-008、FR-011、FR-012、FR-018、FR-019、FR-022～FR-025 | 本文 C-FR 对应条目逐条映射 |

**入口口径（客户端侧待 Hub 回改）**：卡片上的「贡献」是始终可见的操作入口，不等于已获提交权限。未登录时先弹出登录提示；登录成功后若 Hub 没有生效条款，提示「当前未开放贡献」，不启动本地检查或上传。已登录但条款未生效时，点击入口直接显示同一关闭提示。Hub 侧已接受规格中的「未登录不提供入口」及条款未生效时「不开放入口」，与本文当前客户端交互口径不一致；需由 Hub 侧按 Change Candidate 更新已冻结契约及 C-01 条款合同，本文不视为 Hub 已接受该改动。服务端逐次鉴权和条款闸门保持不变。

## 用户场景与测试

### 用户故事 1：用户从本机 Skill 发起贡献并通过本地检查（优先级：P1）

用户在客户端「自定义 Skill 列表」点击本机 Skill 卡片上的「贡献」。该按钮与「使用」并列，以次按钮样式呈现，不受登录状态影响；未登录时在当前页面弹出统一的「此功能需要登录」提示，点击「前往 Web 登录」后进入现有 Web 登录流程，成功返回时继续同一 Skill 的贡献流程。三点菜单承载编辑、停用和卸载等管理操作。客户端在任何 Skill 内容离开本机之前，按迭代一 §6.3 执行包规则、结构质量门与禁止内容检查，并复用客户端现有安全扫描与声明校验能力。任一阻断项存在时提交流程停在本机，错误定位到具体文件、字段或规则；贡献者补齐或修正后可重试。

**优先级原因**：本地检查是「内容不得离开本机」这一隐私承诺的唯一守门人，也是所有后续步骤的前提。

**独立测试**：准备合规、含本机绝对路径、超过 200 个文件、缺版本、缺安全声明的本机 Skill，分别点击卡片「贡献」；验证合规者进入预览，危险或超限者被阻断，缺项者进入补齐流程，未完成前无 Skill 内容上传。未登录状态也应显示入口，点击后在列表上方弹出登录提示；点「前往 Web 登录」完成登录后返回刚才选择的 Skill，关闭弹窗或登录失败则留在列表且不启动检查。用有图标、无图标和图标加载失败的 Skill 核对卡片展示。

**验收场景**：

1. **假如**用户已登录且本机存在自定义 Skill，**当**打开自定义 Skill 列表，**那么**每张本机 Skill 卡片在「使用」旁直接展示次按钮「贡献」，点击后进入该 Skill 的本地检查与提交预览；无需打开三点菜单。
2. **假如**用户未登录，**当**打开自定义 Skill 列表并点击「贡献」，**那么**入口仍可见，客户端在列表上方弹出统一的「此功能需要登录」提示，并提供「前往 Web 登录」按钮；成功返回客户端后继续刚才所选 Skill 的贡献流程，关闭弹窗、登录取消或失败时留在列表且不检查、不上传该 Skill。平台内置 Skill、Hub 安装的官方副本不提供该入口。
3. **假如**用户选择「贡献到 Hub」，**当**客户端执行本地检查，**那么**检查覆盖迭代一 §6.3 全部规则：`SKILL.md` 入口与 `name`、安全边界（路径穿越、绝对路径、重复/大小写冲突路径、符号链接、异常压缩比）、上限（压缩后 ≤ 8 MiB、≤ 200 个文件、解包 ≤ 10 MiB）、禁止内容（真实凭据、用户任务正文、Prompt、私人实例 ID、本机绝对路径）、结构质量门 `EXTREME` 级；并调用现有规则包 v1.0.0、`skill-sentry` 2.1.0 的社区来源档深扫及 `declaration-core` 1.3.0 的安全声明完整性与一致性预检。
4. **假如**本地检查发现任一阻断项，**当**检查完成，**那么**客户端展示每个阻断项对应的文件路径、字段或规则名，不进入预览，不上传 Skill 内容，贡献者可修改后重试；检查器不可用时说明「未能完成检查」，也不允许提交，不把它误报为 Skill 有风险。
5. **假如**本地检查只发现 `MEDIUM` / `LOW` 级提示项，**当**检查完成，**那么**提示项随预览一并展示，不阻断。
6. **假如**本地检查通过，**当**检查完成，**那么**客户端进入提交预览（用户故事 2）。
7. **假如**Hub 侧尚未标记生效的条款版本（C-FR-007），**当**用户选择「贡献到 Hub」，**那么**客户端保留可见入口并说明当前未开放贡献，不进入检查。
8. **假如**一个 Skill 有可用图标，**当**展示技能卡片，**那么**名称旁显示其图标；**假如**图标缺失或加载失败，**那么**同一位置显示有底色的名称首字母或汉字，卡片布局和操作仍可用。

### 用户故事 2：贡献者预览、完成三项声明并提交（优先级：P1）

客户端先汇总本机 Skill 与账号、Hub 条款提供的提交资料，标出缺失、格式不合法和相互冲突的字段；贡献者可在提交环节补齐，例如为没有版本信息的自定义 Skill 填写符合 SemVer 的版本。完成补齐与本地检查后，客户端展示最终提交副本的预览：完整文件清单、每个文件的只读内容、将随提交发出的元信息（名称、说明、版本、来源声明、条款版本、贡献者显示名）。贡献者填写来源声明、勾选接受《CogSeed 社区贡献条款》、确认维护责任后提交。提交成功后贡献者在「我的贡献」看到该提交为「待审核」。

**优先级原因**：这是迭代二唯一新建的机制（客户端 → Hub 的上传方向）；没有它社区贡献不存在。

**独立测试**：用登录账号对合规 Skill 走完预览、声明、提交，对照 Hub 后台的待审核提交逐项核对文件清单与元信息；分别以缺版本、名称、说明、安全声明必填项、来源声明、条款接受、维护责任确认的样例验证定位与补齐；用非法 SemVer、包内外字段冲突及派生关联被删除的样例验证阻断；对补齐版本后的最终副本重新检查并核对预览与实际上传一致；在提交中断网后重试，验证 Hub 侧只有一条待审核提交。

**验收场景**：

1. **假如**提交资料完整且最终副本的本地检查通过，**当**进入预览，**那么**贡献者看到将发出的完整文件清单、可逐个打开的只读内容、以及元信息：名称、说明、版本、来源声明、条款版本、贡献者显示名。
2. **假如**贡献者在预览中，**当**查看任何文件，**那么**内容只读，不可在预览内编辑；需修改 Skill 正文则退出预览、在本机修改后重新发起，需修正提交资料则返回补齐环节并重新检查与预览。
3. **假如**贡献者填写来源声明，**当**选择类型，**那么**至少可选「原创」「派生自 Hub 内容」「基于第三方材料」，并可填写补充说明。
4. **假如**被贡献的 Skill 是迭代一 §7.7 产生的派生副本（带 `forked_from`），**当**进入来源声明，**那么**类型固定为「派生自 Hub 内容」，预填「派生自 Hub 内容 {content_id} v{version}」；贡献者可补充说明但不能改类型、不能删除关联。
5. **假如**贡献者勾选接受条款，**当**勾选，**那么**客户端展示条款全文（或可打开的全文）及其版本号，提交时记录所接受的条款版本与勾选时间。
6. **假如**贡献者确认维护责任，**当**确认，**那么**客户端记录确认时间；确认文案说明该承诺不构成 Hub 对贡献者的强制义务。
7. **假如**来源声明、条款接受、维护责任确认三项任一缺失，**当**点提交，**那么**提交按钮不可用或提交被拒绝，并指出缺项。
8. **假如**三项齐全，**当**提交，**那么**客户端只发出预览中展示的文件与元信息；安装清单、用户设置、任务正文、设备信息、其他 Skill 均不随提交发出。
9. **假如**提交过程中网络中断，**当**恢复后贡献者重试，**那么**Hub 侧不产生重复的待审核提交；客户端明确告知本次提交是「已完整到达」还是「未到达，请重试」。
10. **假如**同一本机 Skill 已有一条待审核提交，**当**贡献者再次提交，**那么**客户端提示本次提交将替换原待审核提交，确认后替换而非并存。
11. **假如**服务端拒绝提交（未登录、待审核数量超上限、身份不符等），**当**收到拒绝，**那么**客户端展示服务端返回的原因；待审核超上限时提示等待审核完成。
12. **假如**提交成功，**当**回到「我的贡献」，**那么**能看到该提交，状态为「待审核」。
13. **假如**本机 Skill 缺少版本，**当**贡献者填写版本，**那么**客户端校验 SemVer；首次提交允许填写首版版本，新版本还须高于当前最高已发布版本。版本随最终提交副本和预览一致；未填或不合法时不允许提交。
14. **假如**包内缺少名称或说明，**当**贡献者在提交环节补齐，**那么**客户端将其写入本次提交副本的规范位置并重新检查，预览与实际上传中的名称、说明一致；若贡献者未补齐则不允许提交。
15. **假如**安全声明缺失或必填项未填，**当**贡献者查看检查结果，**那么**客户端明确列出缺项及其作用，允许在提交环节补充真实声明并重新预检；不得以空值、占位符或默认“无权限／无网络访问”代填事实。
16. **假如**补充资料与包内已有字段、派生关联或账号／条款事实冲突，**当**贡献者继续提交，**那么**客户端指出冲突并要求修正；不得静默取一个值覆盖另一个值，也不得让贡献者改写账号、条款版本或不可变的派生关联。
17. **假如**贡献者补齐资料或提交副本的任一文件变化，**当**继续预览或点击提交，**那么**客户端重新执行完整性、安全及包规则检查，并让贡献者确认更新后的完整预览；之前的检查结果不可沿用。

**提交资料补齐规则**：名称与说明来自本次将上传的 Skill 包，版本是本次提交的版本号；两者均须在预览中对应同一份最终提交副本。客户端按以下来源核对，不把可选项缺失当作必填错误：

| 信息 | 缺失或冲突时的处理 |
|---|---|
| `SKILL.md` 及名称、说明 | 缺少文件时先恢复入口；缺少名称或说明时允许填写，但须进入本次提交副本并重新检查，不能只在上传请求中另带一份与包不同的值。名称仍受 Hub 的长度与同名规则约束。 |
| 版本 | 本机自定义 Skill 没有版本时必须在提交环节填写标准 SemVer；已有版本可预填。填写值与包内 `_meta.json`、安全声明等已有版本字段不一致时要求贡献者明确修正并重新校验，不静默覆盖。新版本必须高于当前最高已发布版本。 |
| 安全声明 | 缺少声明文件、声明必填项、权限／网络／运行边界等事实不明，或声明与文件不一致时，提示具体字段并要求补齐或修正，再由 `declaration-core` 预检；不得自动臆造。 |
| 来源与派生关系 | 贡献者填写真实来源；可预填 `forked_from` 和上一版来源，但派生关联不可删改。第三方材料须由贡献者说明来源。 |
| 贡献者、条款与维护确认 | 显示名来自当前账号，条款版本来自 Hub 当前生效文本，均不可由 Skill 包或手工输入替代；显示名缺失时引导去账号资料补齐，条款未生效或两项确认未完成时不能提交。 |
| 分类、图标、兼容版本及其他字段 | 按 Hub 提交契约区分必填与可选；必填项缺失逐项提示并允许补齐，可选项缺失按约定展示缺省效果，不伪造值。图标缺失不阻断，兼容版本留空按 Hub 既有“不限”语义处理。 |

### 用户故事 3：贡献者查看「我的贡献」并撤回审核前的提交（优先级：P2）

贡献者在客户端「我的贡献」看到自己提交过的内容：稳定 ID、名称、当前发布版本、提交 / 审核 / 撤回状态；被退回时可看到退回原因；审核前可自行撤回提交，无需运营处置。

**优先级原因**：没有状态可见性，贡献者无从得知审核结果，也无法履行维护责任；审核前撤回是贡献者纠错的最低成本路径。

**独立测试**：在 Hub 后台分别把三条提交置为待审核、已退回（带原因）、已接受并发布，验证客户端列表状态与原因一致；对待审核提交执行撤回，验证 Hub 侧状态变为已撤回。

**验收场景**：

1. **假如**贡献者已登录，**当**打开「我的贡献」，**那么**看到自己提交过的内容列表，每项含稳定 ID（有则显示）、名称、当前发布版本（有则显示）、最近一次提交状态（待审核 / 已接受 / 已退回 / 已撤回）、撤回申请状态（有则显示）。
2. **假如**某条提交被退回，**当**查看该项，**那么**退回原因可见，并提供「修改后重新提交」的入口（走用户故事 1、2，作为新提交）。
3. **假如**某条提交处于待审核，**当**贡献者选择撤回提交并确认，**那么**该提交状态变为「已撤回」，不需运营处置。
4. **假如**列表数据来自上一次同步且当前网络不可用，**当**打开列表，**那么**展示上次同步结果并标注时间，恢复网络后自动刷新。
5. **假如**用户未登录，**当**点击「我的贡献」，**那么**在当前页面复用「此功能需要登录」弹窗，按钮引导至 Web 登录；成功后展示当前账号的贡献记录，关闭弹窗、登录取消或失败时保持原页面且不展示历史数据。切换账号后只展示新账号的数据，不展示其他账号的贡献记录。

### 用户故事 4：贡献者对已发布的社区内容提交新版本（优先级：P2）

贡献者修改本机对应的 Skill 后，从「我的贡献」对自己已发布（含已停用/已撤回）的社区内容选择「提交新版本」：关联原稳定 ID，版本号必须高于当前最高已发布版本，来源声明沿用上一版并可修改；其余走用户故事 1、2。

**优先级原因**：维护责任要靠新版本链路履行；问题版本没有新版本只能靠撤回。

**独立测试**：对一个已发布社区 Skill 提交新版本，验证提交携带原稳定 ID、版本号校验、来源声明预填；对已撤回的内容提交修复版本，验证允许提交并提示发布后仍需治理角色恢复。

**验收场景**：

1. **假如**贡献者在「我的贡献」对自己已发布的内容选择「提交新版本」，**当**进入提交，**那么**提交自动关联原稳定 ID，且客户端不允许修改该关联。
2. **假如**贡献者填写的版本号不高于当前最高已发布版本，**当**提交，**那么**客户端在本机阻断并说明当前最高已发布版本。
3. **假如**进入来源声明，**当**展示，**那么**预填上一版的来源声明，贡献者可修改（派生关联仍不可删）。
4. **假如**上一次新版本提交仍在待审核，**当**再次提交，**那么**按用户故事 2 场景 10 提示替换。
5. **假如**该内容处于停用或已撤回状态，**当**提交修复版本，**那么**允许提交，并提示：发布后仍需内容治理角色执行恢复，贡献者不能自行恢复。
6. **假如**本机已不存在与该稳定 ID 对应的 Skill，**当**选择「提交新版本」，**那么**客户端让贡献者从本机自定义 Skill 中选择一个作为新版本来源，并保留原稳定 ID 关联。

---

### 用户故事 5：贡献者申请撤回已发布的社区内容（优先级：P2）

贡献者在「我的贡献」对自己已发布的社区内容申请撤回并填写原因；撤回由内容治理角色处置后生效。客户端展示申请状态：待处置 / 已撤回 / 已拒绝（含拒绝原因）。不支持版本级撤回。

**优先级原因**：完成标准要求「撤回按规则生效」；贡献者不获得直接停用权，客户端必须把这一点表达清楚。

**独立测试**：申请撤回一条已发布内容，在 Hub 后台分别执行同意与拒绝，验证客户端状态与原因；尝试只撤回单个版本，验证被明确拒绝并建议提交修复版本。

**验收场景**：

1. **假如**贡献者对自己已发布的社区内容选择「申请撤回」，**当**填写原因并确认，**那么**客户端说明撤回需治理角色处置后生效，提交申请，状态显示「待处置」。
2. **假如**申请被治理角色同意，**当**客户端下次同步，**那么**该内容显示「已撤回」；已安装侧行为沿用迭代一 §6.7（官方副本阻断新使用、不删除、不动用户设置、派生副本不受影响、运行中使用不中止），本文不重复定义。
3. **假如**申请被治理角色拒绝，**当**客户端下次同步，**那么**显示「已拒绝」与拒绝原因，内容保持发布。
4. **假如**贡献者试图只撤回某一个版本，**当**操作，**那么**客户端不提供版本级撤回入口，并在内容级撤回入口旁说明「不支持撤回单个版本，建议提交修复版本」。
5. **假如**目标是未发布的提交或草稿，**当**申请撤回，**那么**按用户故事 3 场景 3 处理，不进入治理处置。
6. **假如**已存在待处置的撤回申请，**当**再次申请，**那么**客户端不重复提交，展示现有申请状态。

### 边界情况

- 贡献过程中账号登出或切换：进行中的检查/预览立即终止，不发出提交；重新登录后不得沿用旧账号的预览与声明，「我的贡献」按新账号重新加载。
- 本地检查耗时（大包、深扫描）：显示可见进度，允许取消；取消后不留下任何临时上传产物。
- 检查器、规则包或声明引擎缺失、版本不符、完整性校验失败、超时或返回不可判定结果：明确显示「检查未完成」及原因，停止提交，不能降级为较弱检查后继续。
- 声明文件缺失与声明校验失败应区分：前者提示补齐，后者定位到字段或规则；仅有安全扫描通过不等于安全声明完整，反之亦然。
- 补齐名称、说明、版本或声明后，若提交副本产生新文件或改变摘要：重新执行全套包规则、安全扫描与声明预检，再更新预览；不把旧报告用于新副本。
- 预览中的文件为二进制或超长文本：以只读方式提示「二进制文件，{size}」或分段展示，不省略清单项。
- Skill 在预览期间被本机修改：提交前重新计算摘要，若与预览时不一致则要求重新检查与预览。
- 客户端版本低于 Hub 要求的最低版本：卡片入口仍可见，点击后沿用迭代一「需要 CogSeed x+」的不兼容提示，不进入提交。
- 服务端检查结果比本地严格（提交进入待审核但附检查结果）：客户端展示服务端附带的检查结果，不视为失败。
- 来源声明为「派生自 Hub 内容」但上游内容已停用：允许提交，照记来源。
- 提交名称与本机其他 Skill 同名：沿用客户端既有规则；与 Hub 既有内容同名：客户端不预判，由 Hub 接受时阻断并通过退回原因回传。
- 「我的贡献」条目对应的本机 Skill 已被删除：条目保留，「提交新版本」走用户故事 4 场景 6。
- 条款改版：既有贡献不重签；新提交按当前生效版本展示并记录。

## 需求

### 功能需求

**入口与准入**

- **C-FR-001**（映射 FR-001）：客户端 MUST 在自定义 Skill 卡片上、主按钮「使用」旁直接展示次按钮「贡献」，不藏于三点菜单，且登录与未登录状态均可见。已登录时点击进入该 Skill 的贡献流程；未登录时点击在当前页面弹出统一的「此功能需要登录」提示，主操作为「前往 Web 登录」并接入现有 Web 登录流程。登录成功返回客户端后继续该 Skill 的流程；关闭弹窗、登录取消或失败时留在原页面，不检查、不上传 Skill。该提示组件 MUST 可被其他需登录的功能复用，并保存发起操作的目标上下文。平台内置 Skill 与 Hub 安装的官方副本不提供该入口。
- **C-FR-001a**：技能卡片 MUST 在名称旁显示 Skill 图标；图标缺失或加载失败时，MUST 以名称中的首个汉字或拉丁字母及有底色的圆形头像回退，且不影响卡片布局与操作。
- **C-FR-002**（映射 FR-002）：客户端的登录引导与入口限制不替代服务端鉴权；客户端 MUST 把服务端对提交、新版本、撤回申请的拒绝原因原样展示给贡献者。
- **C-FR-002a**（映射 FR-002a）：待审核数量超上限被服务端拒绝时，客户端 MUST 提示等待审核完成。

**本地检查**

- **C-FR-003**（映射 FR-003）：客户端 MUST 在任何 Skill 内容离开本机之前，对本次实际提交副本执行迭代一 §6.3 的全部规则：入口与元信息、安全边界、上限（压缩后 ≤ 8 MiB、≤ 200 个文件、解包 ≤ 10 MiB）、禁止内容（真实凭据、用户任务正文、Prompt、私人实例 ID、本机绝对路径）、结构质量门（`EXTREME` 阻断，`MEDIUM` / `LOW` 提示）。
- **C-FR-003a**：任一阻断项存在时，客户端 MUST NOT 上传 Skill 内容；错误 MUST 定位到具体文件路径、字段或规则名。登录及获取条款等不携带 Skill 内容的请求不受此限制。
- **C-FR-003b**：本迭代 MUST NOT 做自动脱敏或自动改写；禁止内容由贡献者自行修改后重试。
- **C-FR-003c**：贡献校验 MUST 复用客户端既有的安全能力，以当前基线规则包 v1.0.0 与深扫引擎 `skill-sentry` 2.1.0 按社区来源档扫描，并用 `declaration-core` 1.3.0 检查安全声明的必填项、结构及与实际内容的一致性。安全扫描与声明校验是两项独立结果，不能互相代替；报告 MUST 展示实际使用的引擎、规则包版本与结论。
- **C-FR-003d**：`skill-sentry` 在社区档判为 `CAUTION` 或 `DO_NOT_INSTALL`、结构质量门命中 `EXTREME`、`declaration-core` 报缺项／不一致时 MUST 阻断提交；`MEDIUM` / `LOW` 和可接受的声明警告 MUST 明示给贡献者。任一必需检查因缺失、版本不符、完整性失败、超时或不可判定而未完成时 MUST 停止提交并说明「检查不可用／未完成」，不得显示为通过或误称内容危险。

**提交预览**

- **C-FR-004**（映射 FR-004）：客户端 MUST 在提交前展示完整文件清单、每个文件的只读内容，以及将发出的元信息：名称、说明、版本、来源声明、条款版本、贡献者显示名。
- **C-FR-004a**：预览之外的任何本机数据（安装清单、用户设置、任务正文、设备信息、其他 Skill、账号凭据）MUST NOT 随提交发出；实际发出的文件清单 MUST 与预览逐项一致。
- **C-FR-004b**：客户端 MUST 在预览前核对提交必需信息的来源、格式、完整性及一致性；缺失时逐项展示可补齐的字段与不可手填的字段。名称、说明和安全声明可在本次提交环节补入提交副本；缺失的版本可作为本次提交元信息填写。补齐不得静默修改本机原 Skill；提交副本的文件、元信息与预览 MUST 一致。
- **C-FR-004c**：补齐或更改提交副本的任一文件、版本、来源声明后，客户端 MUST 重新执行 C-FR-003～C-FR-003d、更新摘要和完整预览；提交前若最终副本或元信息与最近一次预览不一致，MUST 阻断并要求重新检查与确认。

**三项声明**

- **C-FR-005**（映射 FR-005）：来源声明、条款接受、维护责任确认三项缺一，客户端 MUST 拒绝提交并指出缺项。
- **C-FR-006**（映射 FR-006）：来源声明 MUST 至少支持「原创」「派生自 Hub 内容」「基于第三方材料」并允许补充说明；带 `forked_from` 的派生副本 MUST 自动预填「派生自 Hub 内容 {content_id} v{version}」，类型与关联不可修改或删除。
- **C-FR-007**（映射 FR-007）：客户端 MUST 展示当前生效的《CogSeed 社区贡献条款》全文与版本号，贡献者勾选接受时记录条款版本与时间；条款改版后既有贡献不重签。Hub 未提供生效条款时，入口仍可见，但点击后只显示暂未开放，不启动本地检查或上传；未登录用户先按 C-FR-001 完成登录引导，再判定条款闸门。
- **C-FR-008**（映射 FR-008）：维护责任确认 MUST 记录确认时间；文案说明该承诺不构成 Hub 对贡献者的强制义务。

**提交行为**

- **C-FR-011**（映射 FR-011）：同一本机 Skill 审核前重复提交时，客户端 MUST 提示将替换原待审核提交，确认后替换。
- **C-FR-012**（映射 FR-012）：提交 MUST 幂等：网络中断后重试不产生重复待审核提交；客户端 MUST 明确告知「已完整到达」或「未到达，请重试」，不出现中间态。
- **C-FR-012a**：提交前 MUST 重新校验包摘要及将提交的元信息；与预览时不一致则要求重新检查与预览。

**我的贡献**

- **C-FR-018**（映射 FR-018）：客户端 MUST 提供「我的贡献」列表：稳定 ID、名称、当前发布版本、最近提交状态（待审核 / 已接受 / 已退回 / 已撤回）、撤回申请状态（待处置 / 已撤回 / 已拒绝）、退回与拒绝原因。
- **C-FR-018a**：列表只展示当前登录账号的数据；账号切换时 MUST 重新加载，不得展示其他账号数据。未登录点击「我的贡献」时 MUST 复用 C-FR-001 的登录提示弹窗和 Web 登录引导；成功后进入当前账号的「我的贡献」，取消或失败时保持原页面，不展示历史数据。
- **C-FR-018b**：列表 MUST 支持离线展示上次同步结果并标注同步时间，网络恢复后自动刷新。
- **C-FR-025**（映射 FR-025）：待审核提交 MUST 可由贡献者自行撤回，状态置为「已撤回」，不需运营处置。

**提交新版本**

- **C-FR-019**（映射 FR-019）：客户端 MUST 支持对自己已发布（含已停用 / 已撤回）的社区内容提交新版本：自动关联原稳定 ID 且不可修改；缺版本时允许按 C-FR-004b 补齐，版本号必须高于当前最高已发布版本（客户端本机阻断）；来源声明预填上一版并可修改；本地检查、补齐、预览、三项声明按 C-FR-003～C-FR-008 执行。
- **C-FR-019a**：对停用 / 已撤回内容提交修复版本时，客户端 MUST 提示发布后仍需内容治理角色执行恢复。
- **C-FR-019b**：本机已无对应 Skill 时，MUST 允许贡献者选择一个本机自定义 Skill 作为新版本来源，并保留稳定 ID 关联。

**撤回申请**

- **C-FR-022**（映射 FR-022）：客户端 MUST 支持对自己已发布的社区内容申请撤回并填写原因；展示状态待处置 / 已撤回 / 已拒绝（含拒绝原因）。
- **C-FR-023**（映射 FR-023）：客户端 MUST 在申请前说明撤回经治理角色处置后生效，贡献者无直接停用权。
- **C-FR-024**（映射 FR-024）：客户端 MUST NOT 提供版本级撤回入口，并在内容级撤回处说明不支持并建议提交修复版本。
- **C-FR-024a**：已有待处置申请时 MUST NOT 重复提交申请。

**已安装侧（沿用迭代一，不新增需求）**

- **C-FR-030**：社区内容撤回后的已安装侧行为（阻断新使用、不删除、不动用户设置、派生副本不受影响、运行中使用不中止）与修订版本发布后的自动更新，MUST 沿用迭代一 §6.7、§7.5 的客户端实现；本文不重复定义，也不因本迭代新增分支。
- **C-FR-031**（映射 FR-016）：目录中社区内容的「社区贡献 + 贡献者显示名」来源标识属于迭代一 G-B 客户端目录改造，本文只要求不与其冲突。

**跨切面**

- **C-FR-040**：所有新增可见文案 MUST 进入 renderer/main locales 并支持中英文；卡片按钮使用「贡献」，目标与流程说明可用「贡献到 Hub」，列表入口使用「我的贡献」。
- **C-FR-041**：本地检查、上传、列表刷新等耗时操作 MUST 提供可见进度；上传 MUST 可取消。
- **C-FR-042**：日志与遥测 MUST NOT 记录包正文、文件内容、条款全文或贡献者身份以外的账号信息；只记录提交 ID、稳定 ID、状态、计数、耗时与粗粒度错误类型。

### 关键实体

- **本机自定义 Skill**：用户在客户端创建或导入、位于自定义 Skill 列表的 Skill；可能带 `forked_from`（派生副本）。是贡献的唯一来源类型。
- **本地检查结果**：对本次提交副本执行 §6.3 包规则、`skill-sentry` 安全扫描和 `declaration-core` 声明预检后的产物：各自的阻断／提示／不可判定结果、文件路径或字段及规则名、实际引擎与规则包版本、规范化文件清单、包摘要。只存在于本机，不等同于 Hub 审核结论或正式冻结测试。
- **提交资料**：从本机 Skill、当前账号和 Hub 生效条款汇总的字段；包括必填值、可选值、来源及补齐状态。提交环节只允许补齐可由贡献者声明的资料，不允许伪造账号、条款或派生关联。
- **提交副本与预览**：在本机准备、补齐并重新检查的最终文件集合及元信息；预览是该副本的只读快照，含文件清单、每个文件内容、名称、说明、版本、来源声明、条款版本、贡献者显示名及包摘要。补齐不会静默修改原本机 Skill。
- **三项声明**：来源声明（类型 + 说明 + 可选派生关联 {content_id, version}）、条款接受（条款版本 + 时间）、维护责任确认（时间）。
- **提交（客户端视角）**：一次贡献动作在客户端保留的记录：提交 ID（Hub 分配）、关联本机 Skill、关联稳定 ID（可空）、版本、状态、退回原因、提交时间。用于「我的贡献」展示与幂等重试。
- **我的贡献条目**：一个稳定 ID 或一条未获稳定 ID 的提交在客户端的聚合视图：名称、当前发布版本、最近提交状态、撤回申请状态与原因。
- **撤回申请（客户端视角）**：稳定 ID、原因、状态（待处置 / 已撤回 / 已拒绝）、处置说明。
- **社区贡献条款**：Hub 提供的单一条款文本及其版本号与生效时间；客户端只读取与展示。

## 成功标准

### 可衡量结果

- **C-SC-001**（承接 SC-003）：含 §6.3 禁止内容或超限的包 100% 在本地检查阶段被阻断，Skill 内容上传请求为零，每个阻断项定位到文件、字段或规则；macOS 与 Windows 各验一遍。
- **C-SC-002**（承接 SC-004）：贡献者在预览中看到的文件清单与 Hub 侧收到的文件清单逐项一致，预览外无任何本机数据发出；用抓包对照验证。
- **C-SC-003**（承接 SC-001 客户端部分）：一名登录用户对真实 Skill 从选择入口到提交成功，在资料齐全时 5 分钟内可独立完成，无需查阅文档；提交必填资料与三项声明缺项 100% 被拦截并指出缺项。
- **C-SC-004**（承接 FR-012）：在上传过程中人为断网并重试 10 次，Hub 侧待审核提交始终只有 1 条，客户端 10 次均给出明确的「已到达 / 未到达」结论。
- **C-SC-005**（承接 FR-018）：Hub 侧状态变更（退回、接受、撤回处置）在客户端下一次刷新周期内可见，退回与拒绝原因与后台一致。
- **C-SC-006**（承接 FR-019 / FR-024）：非贡献者账号在客户端看不到他人内容的「提交新版本」「申请撤回」入口；版本号不高于当前最高已发布版本的新版本提交 100% 在本机被阻断；不存在任何版本级撤回入口。
- **C-SC-007**：日志与遥测抽样 100% 不含包正文、文件内容、条款全文。
- **C-SC-008**：在已登录和未登录状态下，所有本机自定义 Skill 卡片无需展开菜单即可找到「贡献」按钮；未登录点击 100% 在当前页面展示可复用登录提示弹窗，按钮引导至 Web 登录，成功后继续原 Skill，关闭或登录失败后不启动检查。「我的贡献」和贡献入口复用同一提示组件。用有图标、无图标及图标加载失败的样例核对，所有卡片均显示可辨识的图标或文字回退，且按钮仍可操作。
- **C-SC-009**：用缺版本、缺名称／说明、缺安全声明、声明字段不完整、包内外值冲突和补齐后文件变化的样例验证：每个必填缺口均被指出并可按来源补齐或修正；未完成时提交为零；补齐后 100% 对最终副本重新执行全部检查，预览与 Hub 接收的元信息和文件逐项一致。
- **C-SC-010**：对规则包 v1.0.0、`skill-sentry` 2.1.0、`declaration-core` 1.3.0 分别验证正常、不可用、版本不符及不可判定结果；报告 100% 展示可读到的实际版本或明确标注版本不可读，并展示各自结论；必需检查未完成时提交为零，且不把不可用写成危险结论。

## 假设

- **迭代一客户端切片是前置依赖**：本文所有「沿用迭代一」处依赖 cogseed-hub PRD doc-v0.5 的客户端实现（Hub 目录协议 A-01/A-02、`forked_from` 派生副本 §7.7、内容级停用 §6.7、自动更新 §7.5、来源标识）。截至 2026-09-20，本仓库尚无这些能力的规格与实现（本地记录 `EV-CLIENT-OPEN2-BASELINE-001` 于 `fc3b9c19` 重跑核查：`src/main` 中无 `forked_from`，来源标识仅按 `create_uid` 二分 official / community，无内容级停用字段，`marketplace-update-policy.ts` 的更新语义未与 §7.5 比对；Hub 侧 `EV-HUB-OPEN1-CLIENT-BASELINE-001` 记录的 5 项协议差异原文未在本仓库重读）；迭代一 G-A / G-B 未关闭。因此 C-FR-006 的派生预填、C-FR-030、C-FR-031 以及 Hub 侧 SC-001 / SC-005 / SC-006 在迭代一客户端切片交付前不能验收。Plan 阶段需决定先补迭代一客户端切片还是并行。
- **上传方向契约在 Plan 阶段冻结**：提交 / 新版本 / 撤回申请的接口契约与幂等键、本地检查结果的结构、条款版本与全文的获取方式、「我的贡献」状态同步方式，Hub 侧 `specs/010-client-contribution/contracts/` 已有草案，尚待客户端 RD 与 Hub RD 共同冻结并以合同测试覆盖；入口可见性差异先按上文走 Hub 侧 Change Candidate。本文只约束行为，不约束契约形态。
- **条款后台开关是运行时闸门**：Hub 侧未配置并标记生效条款版本前，卡片「贡献」入口仍可见，但点击后说明当前未开放贡献，不进入检查；「是否开放」的判定依据在 Plan 阶段与条款获取方式一并冻结。
- **本地检查复用既有能力**：客户端已有的导入检查（8 MiB / 200 文件 / 10 MiB 上限、`EXTREME` 阻断级、深度扫描、安全阈值社区档）作为 C-FR-003 的基础。当前资源基线为规则包 v1.0.0、`skill-sentry` 2.1.0、`declaration-core` 1.3.0；贡献流程须明确接入并报告实际版本，不把既有安装流程的可覆盖判定或声明校验的建议性状态直接当成贡献准入规则。`declaration-core` 目前只预检已有安全声明且缺声明时不运行；贡献流程须把缺声明列为待补齐项，并在最终提交副本上预检。禁止内容清单中「用户任务正文」「Prompt」「私人实例 ID」的识别规则若既有扫描未覆盖，Plan 阶段补充并记录识别边界。不做自动脱敏。
- **提交资料来源**：本机自定义 Skill 列表目前不保证提供版本字段；不得假设每个 Skill 都已有版本。补齐仅作用于本次提交副本，版本由贡献者明确填写或确认；名称、说明必须成为提交包内事实，分类等按 Hub 提交契约确认是否必填。Hub 侧导入／发布规则对包内名称说明与版本的口径、以及新增的安全声明随包要求，须在 Plan 合同中对齐；若与已接受的 Hub 契约冲突，按本文状态说明走 Change Candidate，不得以客户端单独附带的元信息绕过包内校验。
- **贡献者显示名**：取账号服务已有的社区资料显示名；显示名为空时不能提交并引导用户先设置（本迭代不在客户端提供设置入口，与 Hub 侧「不提供匿名贡献」一致）。
- **提交幂等**：由客户端为每次贡献动作生成一个稳定的幂等键并在重试中沿用；键的形态在 Plan 冻结。
- **「我的贡献」数据以 Hub 为准**：客户端本地只缓存上次同步结果供离线展示，不做本地权威状态。
- **客户端改动边界**：按 Handoff 假设为「复用 Marketplace 定点改造」；若 Plan 发现需要超出该边界（例如新建独立数据域或新增 npm 依赖），回 Owner 决定。
- **不做**（照 COGSEED-313.1 评论第 2 节，勿在客户端扩）：用户反馈、评论评分、其他内容类型（Agent / 模板）、自动脱敏、匿名贡献、贡献者协作维护、激励排行、审核 SLA、批量审核、版本级撤回、派生副本与上游差异比较、受邀机制 / 邀请码。提交对象按通用内容对象设计，但本迭代不为 Agent / 模板预留表单或校验分支。
