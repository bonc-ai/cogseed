# 验证契约

交付前核对：完整性、实际来源、否定与条件、数字与日期、人工补充、模型建议、版本关联和未确定字段。meeting_record 与纪要同版本：D/Q/A 编号与正文一一对应、修订沿用原编号、entity_id 仅唯一命中时填写、confirmed=false、resolves=[]；遗留跟进只给建议。逐条自检：每条 D/Q/A 至少一条“source_id · segment_id”且段落标识真实存在；无泛称出处；new_entities 只针对完全未命中的名称、全部 confirmed=false、引用编号与种类一致；落实决议的行动项已填 derived_from，独立安排已注明。不得伪造外部任务标识、归档路径、审计引用或已确认状态。

边界案例见 eval-cases.yaml 和 evals/evals.json，要求均是待模型评估的验收判据，不是已通过的运行结果。

HITL：本 Skill 无写动作，返回待审草稿。用户对归档已有明确授权时 Agent 可按已授权范围新增归档；不得覆盖原文。实际外部写入必须由 Agent 执行“预览 → 用户确认具体预览 → 执行”，纪要确认与任务清单确认不能替代外部创建确认。新内容、账号或范围变化后重新确认。

Agent 将纪要保存成版本文件并登记本轮产物，应用在任务 completed 后自动归档。知识库归档待处理或索引未就绪不阻塞内容整理与用户确认；不要求手动导入。本 Skill 不能代写知识库目录或以生成 Markdown 宣称入库成功。

## 第一段验收

纪要可以包含原有后续安排，但不得生成独立候选任务清单或任务系统参数问卷；完整纪要可审阅，摘要至多 3 条，修改另存新草稿。用户要求修改后必须确认新版本；即使回复同时选择确认并附带内容改动，也先改再审。确认后单独询问是否拆分，不能在同一审阅表单中加入任务选择。

### 输入前置检查（执行步骤 0）

- [ ] 输入是**已纠错**的转写，而非腾讯会议原始转写；否则返回 `needs_input` 并在 `pending_questions` 说明理由。
- [ ] 纠错结果中的待确认项（`risk=high`）**已经过用户逐条确认**；未经确认的候选词**没有**被写进词表。
- [ ] 用户确认后**重跑过一次纠错**（词表新增项要在本次产物里生效，而不是留到下次会议）。
- [ ] 纠正稿已**另存为独立文件**，原始转写未被覆盖；`source_refs` 指向纠正稿，若引用未纠正原文则显式标注。
- [ ] 平台生成的"元宝纪要"（`get_meeting_minutes`）**未**被送入纠错（它本身通顺，纠错会引入误改风险）。

**为什么这条检查是硬的**：未经纠错的转写会把同音错字和人名错认写进纪要，再经 `meeting-task-breakdown` 拆成任务**派给具体的人**——错误在那一刻被固化到执行层，事后极难追溯是谁在哪一步引入的。
