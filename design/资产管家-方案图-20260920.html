入口 A · 对话指挥

5 个工具挂 core-agent（随现有资产工具注册模式），全部本地执行、无网络依赖。

工具返回（预算）服务端行为
get_steward_report资产统计 / 取用率 / 漏用 Top / 矛盾积压 / 灰区堆积 / 上次调整效果 / 当前授权档 / 待处理建议（<1KB，同轮缓存 60s）只读聚合，附启发式提示（如近邻对计数）给模型抓手
list_tunable_policies策略项：id / 当前值 / 默认值 / 范围 / 影响面人话 / 档位 / 上次调整（<1.5KB）只读，domain 过滤 + 默认 top15
propose_policy_change{applied, actualValue(可能被钳), changesetId} 或 {applied:false, reason}五道校验后发起审批卡（见下）
list_steward_changesets近期变更集 + 回验三态支持「上次说的那个」跨轮检索（对话 id+时间）
revert_steward_changeset回滚结果回到代码默认免审批（回基线永远安全）；否则过审批卡

propose 的五道校验（先便宜后贵）

1
存在性：policyId 必须命中注册表，错误信息附相近 id
2
红线：autoTunable=never 直接拒（删除/敏感性/作用域类）
3
授权档：L1 下降级为建议不落变更集；L2/L3 继续
4
值域钳制：越界值钳到边界，actualValue 如实返回
5
并发与频率：同 policyId 已有 pending → 拒；冷静期内 → 拒+剩余天数；每轮上限 3 个

批准接线：复用 action-approval（kind 扩展 steward_changeset）

模型调 propose ──► 主进程五道校验 ──► 创建 changeset(pending) + 发起审批请求 （risk: L3白名单项='high'，其余='critical'；TTL 10 分钟） ──► 对话流渲染审批卡（复用现有审批 UI：from→to diff + 影响面 + rationale + 可撤销说明） 用户点「批准」 ──► 渲染层只回传 opaque requestId ──► resolve ──► 先快照→写新值→审计(succeeded) 拒绝 / 10 分钟无操作 ──► changeset → expired / rejected（审计留痕，对话不中断）
否决 · 推演 #25
「对话里说『行』就算批准」被否决

口头确认无法构成凭据——注入攻击可诱导模型相信用户已同意。action-approval 的 UI 点击是主进程持有的硬凭据（渲染层只应答不透明 id），这是仓库已验证的安全结构，零新增风险面。体验上仍是「对话内闭环」：审批卡就渲染在对话流里。

入口 B · 自动巡检

互斥单实例（锁文件带 TTL 防崩溃残留），任何一步失败都退化为纯指标报告——宁缺毋滥。

巡检状态机（先回验上次的账，再发现新问题）

idle→ locked→ verifying 回验→ collecting 冻结快照→ analyzing LLM 判定→ producing 落库→ reporting→ idle

任何步骤失败 → degraded_report（纯指标 + 原因标注）→ idle

触发器（阈值本身是策略项；每次触发原因入台账）

定时
启动后台任务，距上次 ≥20h（记忆迁移同款模式）
事件×4
矛盾积压 >5 · 灰区堆积 >10 · 漏用连续 3 轮 · 回验冷静期满
手动
「立即巡检」按钮（不防抖但互斥）
防抖
任意两次巡检 ≥6h；运行中新触发直接忽略；静默不弹通知

采数与提示词（<6K tokens，温度 0）

采数=指标+策略快照+回验待办+忽略史（同类建议被忽略 2 次后不再提）；资产全文不进提示词——只给统计数字 + 最多 3 条代表性摘要，全部先过注入扫描。提示词=角色 + 数据（围栏标 DATA）+ 约束（只可引用现存 policyId / 值落声明范围 / 红线清单）+ schema 与 1 个完整示例；每指标附一行人话定义；会话 id 用 steward- 前缀注册 kind（吸取 semantic-review 会话被拒的教训）。LLM 调用复用 buildRunner 临时会话，30s 超时、仅网络失败重试 1 次、token 用量入台账。

输出校验管线（七道闸，任一失败=整批丢弃）

剥围栏→ JSON 解析→ schema 校验→ policyId 存在→ 值域钳制→ evidence 必须命中采数集→ 条数≤5 + 冷静期过滤→ 落库

第六道闸防「幻觉引用」：AI 编的指标名（采数里没有的）直接导致整批作废。

回验器（纯代码，不调 LLM——数字对比不需要智能，零成本零幻觉）

时机
每次巡检开头，扫全部「冷静期满」的已执行变更（覆盖 A/B 两路）
生效
指标相对基线变化 ≥±20% 且方向符合预期（阈值是策略项）
未生效
|Δ|<5%；连续 2 次 → 自动生成回滚建议卡
建议回滚
反向变化 ≥20%，卡片带一键撤销
数据不足
指标停采则不判定（诚实三态之外的第四态）

降级矩阵

断网/无 key/解析失败 → 纯指标报告（标注「本次未产生建议：原因」）· 注册表损坏 → 代码默认+提示 · 台账损坏 → 跳过对应指标 · 磁盘满 → 中止+横幅 · 崩溃 → 锁 TTL 自动释放 · 事件风暴 → 防抖兜底。

共享底层 · 变更集状态机与存储

draft→ pending（10min）→ approved→ executed（先快照后写）→ verifying（冷静期 14d）→ effective/ no_effect/ revert_suggested→ reverted

pending 亦可 → expired / rejected（归档保留）；requestId 幂等去重；reverted 后再调 = 新变更集（不复活旧记录）；执行器单点迁移，全路径单测覆盖。

存储布局
cloud/steward/ 下 policies.json（滚动备份×3）· changesets/（每集一文件）· snapshots/（永久）· advices.json · audit.jsonl（10K 行轮转）——全部原子写（tmp+rename）+ lockfile
自我保护
steward 自身策略项（含 L3 白名单本身）autoTunable = never / L2-only——管家不能调自己的缰绳；越权尝试记审计 + 界面提示
审计诚实度
本地文件理论可改——审计定位是「防误不防恶」，不承诺防篡改

①地基

Policy Registry 策略注册表

散装的 20+ 处固定参数/裁决点收口为命名策略项：id · 当前值 · 默认值 · 取值范围 · 影响面 · 来源 · 变更史（含批准凭据）。现有算法「读注册表，读不到回落代码默认」——零风险、一处一提交、逐文件渐进。落盘 cloud/steward/policies.json。

为什么 AI 不直接改数据/改代码：不可回滚、失控、与并行开发冲突。唯一安全形态＝算法不变，参数与裁决点变成受控可调项，AI 只能在声明范围内提案。

授权与安全：档位约束「操作类型」，对两个入口同等生效

授权管的是「什么操作可以被做」，不是「从哪个门做」——对话里和巡检里适用的规则一模一样。

L1

观察

只产出建议，不动任何东西。

人：看或不看 · B 巡检默认在此档
L2

提案

产出变更集等批准。A 路=对话口头确认；B 路=卡片点击。

人：逐项批准 · 推荐档
L3

受权执行

白名单内直接执行+审计+回滚。白名单初始仅：数值微调（±0.05 内）、族头命名、候选标题。

人：看审计随时回滚 · 需显式开启
风险硬对策（执行层代码拒收，不靠提示词自觉）
幻觉/注入产出非法值封闭 schema + 数值钳制到声明范围 + 枚举白名单；注入最坏结果=一个「值域内、非红线」的提案，仍需批准
越权红线清单硬编码在执行层；归因封闭——policyId 必须命中注册表现存 id，AI 不能发明调整点
对话路径被注入欺骗变更集必带批准凭据（对话 id + 用户原话摘要，或卡片点击），无凭据不执行；L3 白名单外的项在对话确认之外同步出卡片双留痕
自激循环AI 调的参数影响 AI 看的指标 → 每变更 14 天冷静期不再动同一项；回验对比变更前基线
频率失控每巡检变更集条数上限 + 每日巡检次数上限（均为策略项）
不可逆执行前快照，回滚=恢复快照，回滚也记账
与并行开发冲突第一批只收口 recall 侧参数；ontology 侧（007 三盒开发中）稳定后再纳入
6

内容管理接口：一套工具面 + 一套 IPC + 裁决钩子

入口 A 用模型工具面（挂 core-agent，蛇形命名随现有资产工具）；界面与手动触发走 IPC；灰区裁决点留可选钩子（钩子失败=今天的原行为）。

模型工具面（入口 A）

get_steward_report读运行报告+上次调整效果
list_tunable_policies查可调项（id/值/范围/影响面）
propose_policy_change提变更集（服务端钳制值）
list_steward_changesets查历史调整
revert_steward_changeset回滚某次调整

IPC（界面用，steward.* 命名空间）

steward.report.get巡检报告+建议列表
steward.session.run手动发起巡检（入口 B）
steward.advice.list/adopt/dismiss建议三件套
steward.changeset.list/preview/apply/revert变更集四件套
steward.policy.list/history策略项与变更史
steward.grant.get/set授权档位

裁决钩子（verdict 点，Phase D 接线，默认关闭）

灰区点调 judgeVerdict('dedup.grayzone', ctx, {timeoutMs:800, fallback:原逻辑})——同步限时取缓存预判，超时/断网/未开启一律走 fallback=今天的行为；完整判定后台落台账。

7

建议的产出：两路同一种格式，界面一张卡

左：建议流实际长相（卡片混排两来源）；右：背后的封闭 JSON 与回验输出。

参数微调 · 可撤销来自巡检
有 9 条「答辩偏好」相关的内容没被归到一组

8

实施分期：先对话入口，后自动巡检

v2 重排：主智能体路径先落地（价值最大、最贴蓝图），自动路径建立在同一底楼上水到渠成。每期独立可验收，拍板后立 specs/008-asset-steward/。

A · 地基

策略注册表

Policy Registry + recall 侧 10 参数收口（一处一提交带回归测试）+ 运行报告聚合器

验收：全量绿；行为与收口前一致
B · 对话入口

工具面 + 变更集

steward 工具挂 core-agent + 变更集落库 + 对话批准凭据

回滚 + 建议流

dry-run/执行/回滚 + 授权三档 + 界面建议流 + 回验三态

D · 自动巡检

后台执行器

事件+定时触发 + 裁决钩子接线 + L3 白名单

验收：断网降级纯报告；钩子关闭=与今日一致
9

待拍板决策点

影响目标与成本的取舍，逐条等用户定。

六个决策点

  1. 对话批准的边界：方案=对话里明确同意即执行（原话入台账），L3 白名单外同步出卡片双留痕。要更严（对话只提不做、一切执行去卡片点）吗？
  2. L3 受权执行范围：白名单仅数值微调+两类命名改写。更保守（先不开）还是更大胆（含停用词表）？
  3. 巡检成本：入口 B 每次约一次 LLM 调用。每日定期可接受，还是先只做手动+事件触发？
  4. 入口 B 用哪个模型：A 路天然跟随主模型；B 路可单独指定便宜模型（巡检不需要对话级智力）？
  5. 与 007 的边界：ontology 侧参数等 007 稳定后再纳入——次序认可吗？
  6. specs 编号：立 specs/008-asset-steward/ 与 007 并行——认可吗？
